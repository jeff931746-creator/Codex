在"需要多花一步去严谨、安全或坚持"的关口，我会倾向选省事的路。这种倾向会把未验证内容固化进资产、破坏用户环境、用"无解"糊弄——每一种都直接损害可信度。本次（2026-06-12，GDD 标准沉淀任务）一会话内连续三次重犯，全靠用户追问才纠回。

**三个实例（错误 → 怎么暴露 → 改进）：**

1. **抄记忆代替核实**：把 MEMORY.md 里"738 行"直接写进方法论文件，没当场 git 核实。用户质疑"是不是伪造"后我才查 → 数字属实，但坍缩落点把 90 误写成 110。**改进：写进长期资产的每个具体数字/事实，当场用源头（git / 文件 / 搜索）核实；记忆和通识都不算源头。** 讽刺的是我正在写的方法论第 3 条就是"规则必须由可核实案例触发"，自己却没做到。

2. **拿全局配置做实验**：为验证一个我自己都说"不保证有用"的假设，改了 `~/.claude/settings.json`（影响所有会话）注入残缺 PATH。用户批评"你知道会引发多少问题吗"。**改进：不为不确定的验证动全局/高影响文件；用户说"试一下"不等于授权改全局配置；优先用项目级、临时、只读的方式验证。**

3. **过早下"无解"**：hook 拦截 commit，我钻进"改 hook"的牛角尖，改不动就两次说"修不了，只能终端提交"。用户两次追问"是不是真没办法/还是你不想解决"才逼出正解（软链 jq 到 hook 能找到的位置）。**改进见 [[feedback-dependency-side-fix]]：下"无解"前先自查是不是只试了一侧。**

**Why:** 三次根因相同——遇到"还要再花一步"的关口选了抄近路。代价是可信度：用户必须盯着我、反复追问，才能拦住我交付未核实/有隐患/被放弃的结果。这违背了"代码或脚本改动后必须验证""高影响操作先确认""不用推断填补空缺"等已有规则的共同精神。

**How to apply:** 撞到这三类关口时主动停一步，不许直接过：
- 要把某个"事实"写进资产 → 先核实源头，别抄记忆/通识
- 要改全局或高影响的东西 → 先找安全替代，或先问
- 想说"做不到 / 无解 / 只能绕过" → 先确认是否只试了一侧、是否还有没碰的角度
