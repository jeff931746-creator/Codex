# gdd-write

## 触发时机

用户说“帮我写 XX 功能的 GDD”“帮我起一个 XX 的设计文档”，或者提供了功能方向/需求背景需要展开成设计文档时。

## 执行定位

本 Skill 是执行入口，不拥有标准解释权。

- 流程线路以 `多Agent设计文档工作流.md` 为准。
- 状态、回滚、熔断、checkpoint、上下文装配以 `多Agent设计文档调度规则.md` 为准。
- 阶段质量判断以当前节点对应的判断原则为准。
- Agent 执行身份和输出边界以 `role-cards/` 为准。
- GDD 正文判断以 G4、M3、G5、M4 对应原则为准；`GDD输出模板.md` 只提供正文占位结构。

不得在本 Skill 中复制或改写上述标准的细节。

## 执行流程

1. 读取工作流和调度规则。
2. 只用路由上下文确认输入：功能名称、用户原始请求、目标文档路径、参考路径清单、目标交付类型、可用子 Agent 能力。
3. 在 G1 之前不得读取并解释参考 GDD、历史机制记忆、竞品资料、业务文档正文或已有设计文档正文；这些业务证据必须作为 G1 任务包交给子 Agent 首次还原设计目的。
4. 按 `多Agent设计文档工作流.md` 的阶段表从 G1 开始执行。
5. 每到一个节点，只读取阶段加载表中对应的角色卡和判断原则。
6. 每次阶段推进、打回、回滚、熔断、checkpoint，均按 `多Agent设计文档调度规则.md` 执行。
7. 到 G5 时读取当前节点的写作原则和 GDD 输出模板，再进入正文写作；模板不提供判断标准。
8. 如用户要求或流程启用 DeepSeek 等 LLM 优化，在 G5 后执行 G5-D：只生成候选稿，不覆盖原稿；按调度规则落盘提示词版本、候选稿和差异守门报告。
9. G5-D 后必须进入 M4，一致性通过后才能进入 G6；M4 未通过时按调度规则回 G5-D、G5 或更早阶段。
10. G6 把目标 GDD 作为只读输入，单独输出交付验收记录，不得把验收结论或通过依据追加到正文；G6 通过后，方向验证稿可交付，正式 GDD 必须继续调用非生产者 `gdd-review`。
11. 所有必要验收通过后，按用户指定路径写入最终文档；最终正文沿用 M4 已确认内容，不附带 G6 或 `gdd-review` 报告。

## 权限边界

- 子 Agent 只产材料，不做方案选择。
- 主策节点负责选择、确认、打回和阶段推进。
- 主 Agent 在 G1 前只做路由和任务包整理，不做业务证据解释、设计目的判断、手段框架判断、对象拆解或功能判断。
- G1 负责还原设计目的；M1 未锁定目的前，不得进入 G3。
- 写作 Agent 只表达已确认方案，不重新设计。
- 交付验收 Agent 只确认阶段证据、版本一致性、阻塞项状态和产物分离，不重开方案，不重新判断正文质量。
- DeepSeek 等 LLM 只优化文本，不做方案选择、交付验收或正式审核。
- 参与上下文装配、提示词编写、候选稿修改或 blocking issue 修复的主 Agent，不得把自己的自检结论作为正式通过验收。
