# gdd-write

## 触发时机

用户说"帮我写 XX 功能的 GDD"、"帮我起一个 XX 的设计文档"，或者提供了功能方向/需求背景需要展开成完整 GDD 时。

## 边界

- 本 Skill 只负责写新文档；审核已有文档请用 `gdd-review`
- 本 Skill 按框架逐步推导，每步暂停确认后再继续，不一次性输出全文
- 本 Skill 不替代策划的判断；AI 推导的结果需要策划逐步确认

---

## 执行步骤

### Step 0：读取标准 + 确认输入

1. 读取 `/Users/mt/Documents/Codex/reference/部门标准/策划/gdd/GDD写作标准.md`，理解写作框架、禁止行为和 Self-Review 判据
2. 读取 `/Users/mt/Documents/Codex/reference/部门标准/策划/gdd/GDD输出模板.md`，确认输出格式
3. 向用户确认以下输入（已有的直接采用，未给的简短问）：
   - 功能名称
   - 需求背景（这个功能要解决什么问题）
   - 目标文档路径（写到哪里）
4. 从目标文档路径推断项目根目录（取 `workspace/projects/{项目类型}/{项目名}/` 层级），查找 `项目标准.md`：
   - 找到：读取，后续步骤中规则层约束优先，项目标准在此基础上叠加
   - 找不到：跳过，纯走写作标准

### Step 1：需求目的 + 需求概述（暂停确认）

1. 根据用户提供的需求背景，推导需求目的（解决什么问题 / 手段是什么）
2. 写出需求概述（功能整体定义，2–3 句话）

输出后停下，等待用户确认或修改，再继续。

禁止：需求目的只写"做一个X功能"，没有说明解决什么问题。

### Step 2：脑图/流程图（暂停确认）

1. 根据功能整体定义，梳理主要子功能/阶段和它们的关系
2. 用 Mermaid flowchart 画出整体结构图（注：用户可替换为飞书脑图）
3. 对每个主要阶段做删除测试：删掉它，需求目的还能达到吗？不能 → 保留；能 → 删除

流程图完成后暂停，等待用户确认结构再继续。

### Step 3：各子功能（暂停确认）

按脑图/流程图的阶段顺序，逐阶段描述：

- **功能说明**：一句话说明这个模块是什么
- **操作流程**：完整序列（用户操作 + 系统响应），有分支逐一说明
- **配置项**（如有）：参数表格
- **规则/边界**（如有）：`若X则Y` 格式，写在子功能里

含委托子系统的模块，只写接口边界（传入什么 → 返回什么），不重写子系统内部。

各子功能描述完成后暂停，等待用户确认再继续。

### Step 4：UE 交互（按需，暂停确认）

询问用户是否需要补充 UE 交互章节。需要则补充界面入口、按钮状态、弹窗内容等；不需要则跳过。

### Step 5：自检

对照写作标准 Self-Review 三项主要判据做自检：

- **判据一**：需求目的存在且清晰（每条可验证）
- **判据二**：脑图/流程图存在且覆盖整体结构
- **判据三**：功能模块完整（每个子功能有说明和操作流程；规则内嵌；覆盖异常情况）

若项目标准有额外 Self-Review 补充判据，一并检查。

输出自检结论：每项"通过 / blocking issue（含位置）"

有 blocking issue → 返回对应步骤修改，不输出最终文档

### Step 6：输出最终文档

自检全部通过后，按 GDD 输出模板格式输出完整文档，写入用户指定路径。

## 质量检查

- [ ] 需求目的每条可验证（能判断"做到了吗"）
- [ ] 有脑图或 Mermaid 流程图，覆盖所有主要子功能/阶段
- [ ] 每个子功能有功能说明和操作流程
- [ ] 规则/边界内嵌在对应子功能，格式"若X则Y"
- [ ] 边界条件和异常处理有覆盖
- [ ] Self-Review 三项主要判据全部通过后才输出最终文档
