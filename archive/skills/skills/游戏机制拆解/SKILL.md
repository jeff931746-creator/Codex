# 游戏机制拆解

对指定游戏完成机制拆解，并按机制库标准存入对应目录。

## 三阶段流程总览

拆解分为三个独立阶段，每阶段有明确的输入、输出和评审标准。**前一阶段评审不通过，不得进入下一阶段。**

```
阶段一：系统穷举 → 评审 → 通过
                         ↓
阶段二：结构与循环 → 评审 → 通过
                         ↓
阶段三：目的与设计思路 → 评审 → 通过
                         ↓
                      入库完成
```

评审不通过时：
1. 写一段经验总结（哪里出了问题、为什么、重做时注意什么）
2. 根据问题性质决定：补充当前阶段重做，还是回退到更早的阶段
3. 同类错误反复出现（≥3次）时，沉淀到拆解质量标准

## 阶段一：系统穷举

### 目标

穷举这个游戏的所有可见系统，不预判重要性，不跳过"看起来不重要"的系统。

### 输入

- 游戏资料来源（官方介绍、wiki、攻略站、游玩记录、已有分析文档）
- 明确标注哪些是第一手资料（实际游玩）、哪些是二手资料（攻略/介绍）

### 信息收集规则（硬规则）

**先搜后整，不能反过来。**

LLM（包括 DeepSeek、Claude 等）的训练数据不等于事实。任何事实性判断（某个系统是否存在、某个机制的具体参数、某个功能的实际表现）都必须有联网搜索获取的原始信息支撑，不能用 LLM 通识知识填补。

执行顺序：
1. **先联网搜索**：用 WebSearch 按维度搜索游戏的系统信息（官网、TapTap、攻略站、wiki、视频攻略等），收集原始素材
2. **再让 LLM 整理**：把搜索获取的原始信息作为上下文输入 LLM，让 LLM 基于这些素材进行结构化整理
3. **标注信息来源**：每条信息标注实际来源 URL 或资料名称，不能标注"玩家攻略"这类模糊来源

禁止行为：
- ❌ 直接让 LLM 凭通识回答"这个游戏有什么系统"
- ❌ 把 LLM 的推断包装成"攻略/推断"来源
- ❌ 对不确定的信息不搜索就直接写"存在"或"无"

允许行为：
- ✅ 搜索后仍然找不到某维度信息 → 标注"未确认（已搜索，无相关结果）"
- ✅ 搜索结果互相矛盾 → 标注矛盾点，提交用户判断
- ✅ 用 LLM 对已收集的素材做结构化整理和分析

### 工作内容

对照以下六个维度逐一检查，每个维度下列出所有找到的系统：

| 维度 | 检查内容 |
|---|---|
| 核心玩法 | 执行层（玩家直接操作什么）、构筑层（玩家做什么决策）、验证层（怎么检验决策好坏） |
| 成长养成 | 局内成长（单局内的变强路径）、局外成长（跨局积累）、重置机制（如有） |
| 经济系统 | 所有货币种类、来源、消耗去向 |
| 社交多人 | PVP、公会/军团、组队、排行榜、聊天、好友系统、社交分享 |
| 赛季活动 | 赛季机制、限时活动、轮转内容 |
| 商业化 | 商店、礼包、广告变现、通行证/月卡、抽卡 |

### 输出：系统全景清单

写入总档 `00_总档.md` 的"系统全景"一节，格式：

| 系统名称 | 所属维度 | 一句话职责 | 信息来源 | 本次是否深拆 | 不深拆的理由 |
|---|---|---|---|---|---|

每个维度至少有一行。如果某个维度确认不存在对应系统（比如纯单机游戏没有社交系统），必须显式写"该维度无对应系统"并注明判断依据，**不能留空白**。

### 评审标准

1. **六维度全覆盖**：每个维度都有明确结论（有系统/无系统），没有空白维度
2. **信息来源诚实标注**：每个系统标注了信息来自第一手还是二手，来自二手的标注具体来源
3. **"无"和"未知"严格区分**：确认不存在写"无"并给依据；查不到信息写"未确认"，不写"无"
4. **不遗漏主要系统**：对照同品类已入库游戏的系统清单交叉检查（如有）

评审由用户完成。提交时明确说明：哪些维度信息充分、哪些维度信息不足需要用户补充。

## 阶段二：结构与循环

### 目标

基于全景清单，理清系统之间的层级关系和资源/行为的流转循环。

### 输入

- 阶段一评审通过的系统全景清单

### 工作内容

1. **系统分层**：把全景清单中的系统按层级归类（执行层/构筑层/成长层/经济层/社交层/商业化层等），标注每层的职责边界
2. **循环链路**：画出主要的资源流转和行为循环（玩家做 A → 产生 B → 用 B 做 C → C 反馈回 A），标注每个环节的输入输出
3. **系统间接口**：标注哪些系统之间有直接的数据/行为依赖，接口是什么
4. **断点识别**：循环链路中哪些环节是脆弱的（去掉会断裂）、哪些是冗余的（去掉不影响）

### 输出

- `01_系统结构/` 下的结构文件：层级图 + 接口关系
- `04_经济循环/` 下的循环文件：资源流转图 + 断点标注
- 更新 `00_总档.md` 的系统总览表（补充层级和联动关系）

### 评审标准

1. **全景清单全映射**：阶段一清单里的每个系统都出现在结构图中，没有遗漏
2. **循环闭合**：每条循环链路的输入输出都有着落，没有悬空节点（某资源只有产出没有消耗，或反之）
3. **接口明确**：系统间的依赖关系写清了"传递什么"，不只是"有关联"
4. **层级归属合理**：每个系统只属于一个主层级，归属理由清晰

评审由用户完成。提交时标注信息置信度：哪些结构关系有充分依据、哪些是推断。

## 阶段三：目的与设计思路分析

### 目标

基于系统结构，分析每个系统为什么存在、整体设计逻辑是什么。

### 输入

- 阶段二评审通过的结构图和循环链路

### 工作内容

1. **每个系统的存在理由**：回答"如果删掉这个系统，游戏在哪里会出问题"
2. **设计因果链**：每个关键设计决策走完因果链（设计前提→激活条件→心理机制→用户动作→业务结果→失效条件）
3. **失效条件**：每个设计决策的"做错了会坏在哪里"，两个方向（过强/过弱）都要覆盖
4. **整体设计逻辑**：所有系统共同指向什么底层目的？用一个模型概括整个游戏的设计思路
5. **可迁移结论**：提炼 If-Then 格式的设计公式，脱离本游戏语境仍然成立

### 输出

- `02_模块拆解/` 下的专题文件：每个系统的拆解（按专题模板）
- `90_结论提炼/` 下的结论文件：If-Then 格式，≥5 条
- 更新 `00_总档.md` 的总判断

### 评审标准

1. **存在理由完整**：每个主要系统都回答了"为什么存在"，而不只是"它做什么"
2. **因果链完整**：关键设计不只是贴标签（"归属感"、"竞争感"），有具体的心理机制命名和行为推导
3. **失效条件标注**：每个关键设计至少有一个失效方向的说明
4. **结论质量**：If-Then 格式、通过太宽测试和太窄测试、有适用前提
5. **模块边界清晰**：每个模块说清了"不负责什么"
6. **证据等级标注**：每条结论标注 evidence_grade（S/A/B/C）

评审由用户完成。

## 两个库的关系（必读）

项目知识库（如 `向僵尸开炮知识库/`）和机制库是**两个不同层级**，不互相替代：

| | 项目知识库 | 机制库 |
|---|---|---|
| 存什么 | 这个游戏怎么做、具体设计决策、执行资料 | 这个游戏的结构拆解、可迁移结论 |
| 谁来用 | 项目组成员 | 所有游戏的设计参考 |
| 格式要求 | 项目自定义 | 必须遵循本 Skill 的质量标准 |

**规则：做了一次拆解，两个库都要写。**

## 常见错误

- **跳过阶段一直接写专题**：没有全景清单就开始拆解，必然遗漏系统
- **把"未收录"当"不存在"**：机制库没写 ≠ 游戏没有，必须区分
- **先写结论再补拆解**：结论提炼必须在所有专题完成后写
- **把现有资料直接复制进来**：项目知识库里的原始拆解是输入，必须按质量标准重新整理
- **模块分类用名词而不是职责**：不要写"战斗系统"，要写"战斗系统负责什么、不负责什么"
- **结论只对这个游戏成立**："这个游戏的经济系统设计得很好"不是可迁移结论
- **只存项目目录不存机制库**：项目知识库拆解完成 ≠ 机制库入库完成
- **阶段间跳跃**：结构没理清就开始分析目的，结果因果链建在错误的结构理解上
