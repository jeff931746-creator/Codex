# gdd-review

## 触发时机

用户说"帮我审核这个 GDD"、"review 一下这个设计文档"、"这个文档通过标准吗"，或者在写完文档后需要做 Self-Review 时。

## 边界

- 本 Skill 只审核，不修改文档；发现 blocking issue 后由策划或 `gdd-write` 处理
- 本 Skill 按写作标准的五项判据审核，不自定义评审维度
- 本 Skill 适用于系统设计/玩法设计/战斗设计等同类功能设计规格文档

---

## 执行步骤

### Step 0：读取标准

1. 读取 `/Users/mt/Documents/Codex/reference/部门标准/策划/gdd/GDD写作标准.md`，重点加载：
   - 四层框架定义（体验目标 / 流程图与节点定义 / 规则层 / 拼装示例）
   - 禁止行为清单
   - Self-Review 评审判据表格（五项判据的通过/不通过标准）
2. 从目标文档路径推断项目根目录（取 `workspace/projects/{项目类型}/{项目名}/` 层级），查找 `项目标准.md`：
   - 找到：读取并纳入，审核时在规则层判据基础上叠加项目标准的特殊约束（如接口边界定义要求、离线场景覆盖要求等）
   - 找不到：跳过，纯走规则层

不使用写作标准和项目标准以外的评审维度。

### Step 1：读取目标文档

读取用户提供的目标文档路径，理解文档结构和内容。

如果用户未提供路径，询问。

### Step 2：逐系统按五项判据审核

对文档中每个系统逐项检查：

**判据一：体验目标存在**
- 每个系统是否有明确的 Step 1 句式？
- 情绪/认知状态是否具体可判断（无"有趣""好玩""爽"等模糊描述）？

**判据二：流程图与功能模块概述存在且完整**
- 是否有 Mermaid flowchart（文字箭头不通过）？
- 是否有整体流程图 + 各主要阶段子流程图两层？
- 循环节点是否标注循环条件？阶段间是否有数据流标注？
- 每个节点是否标注了所有退出路径（正常 / 主动中断 / 失败 / 异常）？
- 是否有功能模块概述（2.1.5），且按执行职责划分（非属性维度）？
- 每个功能模块描述能否概括为"[主语]执行了[什么]"（"负责/处理/管理/包含"不通过）？
- 2.2 小节与 2.1.5 是否一一对应？

**判据三：节点定义与规则层完整**
- 节点是否用自然小节描述（非"字段/内容"二列表格）？
- 框架字段名是否未出现在标题或表头？
- 所有"当[条件]时，系统必须/禁止[行为]"格式的约束是否均在规则层列出？
- 规则层是否覆盖操作规则 / 规则优先级 / 异常处理？
- 含发奖系统是否覆盖发奖时机和离线处理？
- 含类型枚举节点：每种类型是否有触发操作、内容规格和退出路径定义？
- 委托子系统的节点是否有接口边界定义（传入什么 → 返回什么）？
- 规则层与节点定义 `系统自动执行` 块是否对同一规则描述一致（以规则层为准）？

**判据四：拼装示例存在且可操作**
- 是否覆盖第一层全部体验目标（至少 2 个）？
- 每个示例是否含决策理由？
- 含程序化生成系统：是否说明了生成模式和随机/约束逻辑，覆盖所有主要生成模式？

**判据五：内容配置区合规（有内容配置时适用）**
- 内容配置表是否在规则层之后出现？
- 内容配置区是否混入了系统规则？

### Step 3：输出审核报告

格式：
```
## [系统名称] 审核报告

### 判据一：体验目标存在
通过 / blocking issue：[具体位置 + 问题描述]

### 判据二：流程图与功能模块概述存在且完整
通过 / blocking issue：[具体位置 + 问题描述]

### 判据三：节点定义与规则层完整
通过 / blocking issue：[具体位置 + 问题描述]

### 判据四：拼装示例存在且可操作
通过 / blocking issue：[具体位置 + 问题描述]

### 判据五：内容配置区合规
通过 / 不适用 / blocking issue：[具体位置 + 问题描述]

---
**结论**：可通过 / 需打回修改
**Blocking issues 清单**：
- [位置]：[问题]
```

每条 blocking issue 必须标注具体位置（行号、节点名或章节标题），不允许泛化描述（如"规则层不完整"而不说哪条规则缺失）。

## 质量检查

- [ ] 只使用写作标准 Self-Review 判据，未自定义评审维度
- [ ] 每条 blocking issue 标注了具体位置（行号/节点名/章节）
- [ ] 五项判据逐条给出结论（通过 / blocking issue / 不适用）
- [ ] 最终结论明确（可通过 / 需打回修改）
- [ ] 前四项有任意 blocking issue 时，结论必须为"需打回修改"
