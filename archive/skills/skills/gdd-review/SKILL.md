# gdd-review

## 触发时机

用户说"帮我审核这个 GDD"、"review 一下这个设计文档"、"这个文档通过标准吗"、"审核这个案子"、"看下这个系统/玩法/养成/活动/商业化方案"，或者在写完文档后需要做 Self-Review 时。

## 边界

- 本 Skill 只审核，不修改文档；发现 blocking issue 后由策划或 `gdd-write` 处理
- 本 Skill 按写作标准的判据审核，不自定义评审维度
- 本 Skill 适用于需求 GDD、功能需求规格文档及同类游戏功能设计产出物。系统策划、数值、立项等标准只能作为补充判据，不能替代 GDD 写作标准。
- 当本 Skill 作为正式 GDD 交付链路的最终审核时，执行者必须是非生产者：参与 G5 正文写作、G5-D DeepSeek 等 LLM 上下文装配、提示词编写、候选稿修改或 blocking issue 修复的主 Agent / 写作 Agent，不能作为该稿件的唯一正式通过验收者。
- Self-Review 只能作为自检材料；若缺少非生产者审核，结论必须写明“已完成自检，未完成正式独立验收”，不能写“正式通过”。

---

## 执行步骤

### Step -1：确认审核身份

1. 判断本次审核是 Self-Review、过程自检，还是正式 GDD 交付审核。
2. 若是正式 GDD 交付审核，确认审核者没有参与该版本的 G5 正文写作、G5-D DeepSeek 等 LLM 优化上下文装配、提示词编写、候选稿修改或 blocking issue 修复。
3. 若无法确认非生产者身份，不输出“正式通过”；只能输出“已完成自检，未完成正式独立验收”，并列出仍缺少的审核角色。

### Step 0：读取标准

1. 读取当前工作区的 `reference/部门标准/策划/gdd/GDD写作标准.md`，重点加载：
   - 写作框架（四节结构）
   - 禁止行为清单
   - Self-Review 评审判据（需求目的、手段框架、脑图/流程图、功能模块完整、内容配置区、设计层/技术层边界）
2. 读取当前工作区的 `reference/部门标准/策划/gdd/GDD输出模板.md`，用于识别目标文档是否偏离 GDD 输出结构。
3. 若目标文档具有系统策划、数值、立项、美术、开发等明显属性，读取对应 `reference/部门标准/` 下的专项标准作为补充；补充标准不能替代 GDD 标准。
4. 从目标文档路径推断项目根目录，查找 `项目标准.md`：
   - 找到：读取，审核时在主标准判据基础上叠加项目标准的特殊约束和补充判据
   - 找不到：跳过，纯走主标准

主要依据写作标准和项目标准判据审核。以下专项判据按文档特征条件激活，不适用时跳过：（1）模块分类合理性；（2）委托接口完整性；（3）专项标准补充项。

### Step 1：读取目标文档

读取用户提供的目标文档路径，理解文档结构和内容。

如果用户未提供路径，询问。

### Step 2：按 GDD Self-Review 判据审核

**判据一：需求目的存在且清晰**
- 文档是否有需求目的章节？
- 每条目的是否只描述玩法目的层的目标状态，而不是实现手段、交付对象或正文结构？
- 每条目标是否可验证（能判断"这个功能做到了吗"）？
- 是否存在只说"做一个X功能"而没有说为什么的条目？
- 是否把统计、接入、归属、互斥、计分、展示、配置、结算写成需求目的？

**判据二：手段框架成立**
- 文档是否能从需求概述、结构图或主体设计中识别“通过什么规则，把什么输入转成什么结果”？
- 该手段框架是否能承接需求目的，而不是只罗列功能清单？
- 是否把不承担转化关系的配套内容写成玩法本体？
- 主体章节是否能说明自己如何参与手段框架？
- 若手段框架缺失或断裂 → blocking issue。

**判据三：脑图/流程图存在且覆盖整体结构**
- 是否有脑图（飞书脑图截图）或 Mermaid 流程图？
- 是否覆盖了所有主要子功能/阶段？
- 各阶段之间的关系或流转是否清晰？
- 是否展示主要对象、手段框架中的转化关系和关键分支？

**判据四：功能模块完整**
- 每个子功能是否有功能说明？
- 每个子功能是否有操作流程（完整的用户操作 + 系统响应序列）？
- 规则/边界是否内嵌在对应子功能里（而非单独集中章节）？
- 是否覆盖了正常流程和异常/边界情况？
- 规则描述是否有触发条件（若X则Y，而非只写Y）？
- 是否使用了实现层技术术语替代设计层用词（如"货币账户""购买引擎"等）？是否有未附定义的自创专项术语？有 → blocking issue
- 每个配置项是否声明了生效范围（全局 / 实例 / 其他需说明）？未声明 → blocking issue

**判据五：内容配置区合规（有内容配置时适用）**
- 内容配置是否在功能描述完成后才出现？
- 内容配置区是否混入了系统规则？

**判据六：设计层 / 技术层边界**
- 文档是否只写功能行为、玩家可见响应、规则和边界？
- 是否写入事务、锁、并发、防重复、幂等、失败重试、补发队列、日志、监控、接口字段结构、数据存储等技术实现内容？
- 如出现技术实现细节 → blocking issue，说明应移出 GDD 或转入开发/技术设计文档。

**专项判据一：模块分类合理性**（文档含 ≥ 2 个功能模块时激活）
- 是否存在核心操作流程相同、仅配置参数不同的多个模块被拆分为独立子功能？
- 若存在：标注为 blocking issue，说明可合并为一个模块，差异通过配置项体现

**专项判据二：委托接口完整性（功能级契约）**（文档含"委托给 X 系统"、"X 系统接管"、"传入 X 系统"等描述时激活）
- 每处委托是否说明了委托给哪个系统、传入什么（**意图 / 数据类别，非字段结构**）？
- 每处委托是否说明了期望返回什么类型的结果（**功能层面，非字段结构**）？
- 每处委托是否说明了异常 / 对方未就绪时功能上如何降级或兜底？
- 缺任一项 → blocking issue
- 注：本判据查的是**功能级契约**，不要求定义技术字段结构、数据类型、协议（那属开发文档，GDD 不写）

**项目特殊约束（如有项目标准）**：
按项目标准的特殊约束和补充判据逐条检查。

**专项标准补充项（如适用）**：
按已读取的系统策划、数值、立项、美术、开发等标准逐条检查，但必须放在 GDD 判据之后输出，不得用专项结论覆盖 GDD 结论。

### Step 3：输出审核报告

格式：
```
## [功能名称] 审核报告

### 判据一：需求目的存在且清晰
通过 / blocking issue：[具体位置 + 问题描述]

### 判据二：手段框架成立
通过 / blocking issue：[具体位置 + 问题描述]

### 判据三：脑图/流程图存在且覆盖整体结构
通过 / blocking issue：[具体位置 + 问题描述]

### 判据四：功能模块完整
通过 / blocking issue：[具体位置 + 问题描述]

### 判据五：内容配置区合规
通过 / 不适用 / blocking issue：[具体位置 + 问题描述]

### 判据六：设计层 / 技术层边界
通过 / blocking issue：[具体位置 + 问题描述]

### 专项判据一：模块分类合理性
通过 / 不适用 / blocking issue：[具体位置 + 问题描述]

### 专项判据二：委托接口完整性
通过 / 不适用 / blocking issue：[具体位置 + 问题描述]

### 项目特殊约束（如有）
通过 / blocking issue：[逐条列出检查结果]

### 专项标准补充项（如适用）
通过 / blocking issue：[逐条列出检查结果]

---
**审核类型**：Self-Review / 过程自检 / 正式 GDD 交付审核
**结论**：
- 正式 GDD 交付审核：正式通过 / 需打回修改
- Self-Review 或过程自检：自检通过 / 需打回修改 / 已完成自检，未完成正式独立验收
**Blocking issues 清单**：
- [位置]：[问题]
```

每条 blocking issue 必须标注具体位置（章节标题或子功能名称），不允许泛化描述（如"功能模块不完整"而不说哪个模块缺什么）。

## 质量检查

- [ ] 已读取当前工作区的 GDD 写作标准；若是游戏设计案/功能设计文档，没有跳过 GDD 标准
- [ ] 若本次是正式 GDD 交付审核，已确认审核者为非生产者；否则未输出“正式通过”
- [ ] 只使用写作标准判据及已声明的专项判据，未自定义评审维度
- [ ] 每条 blocking issue 标注了具体位置（章节/子功能名称）
- [ ] GDD Self-Review 判据逐条给出结论（通过 / 不适用 / blocking issue）
- [ ] 已检查手段框架是否承接需求目的，且主体章节没有绕过手段框架。
- [ ] 专项判据一：文档含 ≥ 2 个功能模块时已检查模块分类合理性
- [ ] 专项判据二：文档含委托描述时已检查委托目标 + 传入意图/数据类别 + 期望返回结果类型 + 异常降级/兜底（功能级契约，非技术字段）
- [ ] 适用系统策划、数值、立项等补充标准时，补充结论放在 GDD 判据之后，未替代 GDD 结论
- [ ] 最终结论明确（可通过 / 需打回修改）
- [ ] 任意适用判据有 blocking issue 时，结论必须为"需打回修改"
