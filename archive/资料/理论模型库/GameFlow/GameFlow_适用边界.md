# GameFlow 适用边界

## 1. GameFlow 能回答什么

GameFlow 主要回答一个问题：

> 玩家在实际游玩过程中，是否容易产生持续、愉悦、投入的体验？

它适合检查过程体验质量，包括：

- 玩家能否专注。
- 挑战是否匹配技能。
- 玩家是否知道目标。
- 操作和决策是否有控制感。
- 反馈是否及时、清楚、可用于调整行为。
- 游戏是否形成沉浸。
- 社交互动是否支持享受感。

## 2. GameFlow 不能直接回答什么

GameFlow 不直接回答以下问题：

| 问题 | 不适合直接用 GameFlow 判断的原因 |
|---|---|
| 用户底层需求是什么 | GameFlow 评估过程体验，不解释长期心理需求来源 |
| 这个题材是否适合买量 | 题材获量涉及市场供需、素材竞争、平台红利和转化成本 |
| 这个产品 ROI 是否成立 | ROI 需要商业化、留存、付费深度、买量成本和规模假设 |
| 这个游戏该如何做研发管理拆解 | GameFlow 不是产品模块管理框架 |
| 一个玩法是否天然适合某个人群簇 | 人群簇需要需求、任务、玩法承接和题材共同判断 |

## 3. 与 SDT/PENS 的边界

SDT/PENS 关注用户需求满足，例如胜任感、自主性和关系感。它回答的是“玩家为什么需要这种体验”。

GameFlow 关注过程体验条件。它回答的是“这个游戏在实际游玩时，是否让玩家持续享受”。

两者可以配合使用：

- SDT/PENS 用来解释需求根基。
- GameFlow 用来检查体验是否把需求顺畅地承接出来。

例子：

- 一个动作游戏可能满足胜任感需求，但如果操作反馈弱、挑战曲线不稳、失败原因不清，GameFlow 会指出它的过程体验承接失败。
- 一个社交游戏可能满足关系感需求，但如果匹配质量差、合作没有真实分工，GameFlow 会指出社交互动没有形成享受感。

## 4. 与 MDA 的边界

MDA 关注从 Mechanics 到 Dynamics 到 Aesthetics 的因果链。它回答的是“设计机制如何生成玩家体验”。

GameFlow 关注体验结果是否具备心流条件。它回答的是“玩家体验结果是否顺畅、投入、愉悦”。

两者可以这样分工：

- MDA 用来追踪问题来源：哪个机制导致了哪种动态，最后影响了哪种体验。
- GameFlow 用来定义体验问题：玩家是失去专注、挑战不匹配、目标不清，还是反馈不足。

## 5. 与六张牌的边界

六张牌是商业游戏研发管理视角，用于拆解和评审商业游戏的关键内容模块、研发判断和落地风险。

GameFlow 不是六张牌的替代品。它可以作为六张牌评审中的“过程体验检查层”，但不应被强行改造成六张牌。

可接入的位置：

- 当六张牌讨论核心玩法是否成立时，用 GameFlow 检查专注、挑战、技能、控制、目标和反馈。
- 当六张牌讨论内容体验是否成立时，用 GameFlow 检查沉浸和反馈。
- 当六张牌讨论社交结构是否成立时，用 GameFlow 检查社交互动是否真的产生享受感。

不可替代的位置：

- 六张牌中的商业化、内容供给、研发成本、版本节奏、市场定位，不能由 GameFlow 直接判断。

## 6. 与 `N/T/A/F/THM` 的边界

`N/T/A/F/THM` 关注用户需求、任务态、玩法承接、反馈结构和题材母题之间的映射关系。它用于回答“一个玩法或题材可能落在哪些用户需求和人群簇上”。

GameFlow 不负责做人群映射。它负责检查映射后的实际体验是否成立。

更合理的组合方式是：

1. 用 `N/T/A/F/THM` 判断用户需求、玩法承接和题材方向。
2. 用 GameFlow 检查核心玩法段落是否具备享受感条件。
3. 用市场数据、素材测试和商业化模型判断获量与 ROI。

## 7. 适用强弱

| 游戏类型 | 适用方式 |
|---|---|
| 动作 / 竞技 / 挑战型 | 重点看 Challenge、Player Skills、Feedback、Control |
| 解谜 / 策略 / 构筑型 | 重点看 Challenge、Player Skills、Clear Goals、Feedback |
| 剧情 / 探索 / 沉浸型 | 重点看 Immersion、Clear Goals、Feedback、Concentration |
| 模拟 / 经营 / 建造型 | 重点看 Clear Goals、Feedback、Control、Challenge |
| 社交 / MMO / 派对型 | 重点看 Social Interaction、Feedback、Clear Goals、Control |
| 放置 / 超休闲 / 低负荷型 | 部分元素需要降权，尤其是 Challenge 和 Player Skills |

## 8. 不应机械使用的情况

不要把 GameFlow 用成“8 项全高分才是好游戏”的 checklist。不同游戏可以有不同的体验目标。

- 低负荷游戏可能刻意降低 Challenge。
- 叙事游戏可能弱化 Player Skills，但强化 Immersion、Clear Goals 和 Feedback。
- 单机游戏可能没有 Social Interaction，这不代表体验失败。
- 高自由度游戏可能弱化显性目标，但仍需要局部目标和反馈支持。

评审时应先说明游戏的体验目标，再判断哪些 GameFlow 元素是主评项、辅评项或不适用项。

## 9. 静态验证样例

### 样例 A：动作 / 挑战型游戏

适用主评项：

- Challenge：敌人、关卡和 Boss 是否形成逐步升级的挑战。
- Player Skills：玩家是否能通过练习提升操作、闪避、连招、资源管理或战斗理解。
- Feedback：命中、受击、破防、奖励和失败原因是否清楚。
- Control：操作、镜头、判定和技能释放是否稳定可预期。

可验证的问题：

- 玩家失败后是否能说出下一次要改什么？
- 玩家提升技能后，游戏是否用更高阶挑战承认这种提升？
- 失败主要来自玩家判断与操作，还是来自看不懂的判定和信息缺失？

### 样例 B：剧情 / 沉浸型游戏

适用主评项：

- Immersion：叙事、场景、角色、音画和交互是否共同形成连续情境。
- Clear Goals：玩家是否知道当前剧情目标、行动目标和推进方向。
- Feedback：探索、对话、选择和剧情推进是否给出清晰反馈。
- Concentration：UI、任务和系统是否避免破坏叙事注意力。

可验证的问题：

- 玩家是否自然理解自己为什么要继续推进？
- 交互是否支撑叙事情绪，而不是把玩家拉回任务清单？
- 剧情选择、探索发现或关键行动是否被游戏及时承认？

## 10. 当前结论

GameFlow 应先作为“过程体验评估资料库”保存。它可以补足当前评审框架对游玩过程质量的检查，但不能替代用户需求、题材获量、商业化 ROI 或研发管理框架。
