# 标准演进方法论

管"标准类资产本身怎么演进和维护"的方法论，比业务方法论高一层。适用对象：部门标准、评分卡、判据集、写作/审核标准——任何会跨会话长期迭代的规则性文档。

业务方法论（立项/分析/题材）教你"怎么做事"；本文教你"怎么养一份会长期改的标准，让它不膨胀到失控"。

---

## 一、证据基础：两个独立案例，同一形状

**GDD 写作标准**（2026-05-26 ~ 06-03，八天 18 版）：

```
体积  v1      v4      v7      v11(峰值)   v14(推翻重写)  v18
     4.3KB → 10KB → 17KB →  24KB    →   5.3KB     →  8.8KB
            ╰── 单调膨胀 8 版 ──╯   ╰断崖瘦身 77%╯  ╰稳定贴判据╯
```

**数值评审评分卡**（同期，均在 2026-06-12 当天）：v5 臃肿版 **738 行**（commit `392ca18f`，上午）→ 当天下午重写为轻量评分卡 **90 行**（commit `0443d2f7`），砍掉 88%；之后 v6→v7 回补到现行 110 行。

两份性质不同的标准，被独立维护，都走出"**越堆越重 → 撑不住推倒重建 → 在新框架上贴补丁**"的三段式。这不是偶然，是标准类资产的默认命运。

---

## 二、四条规律

### 规律 1：适用范围决定体积，范围漂移是膨胀的根因

GDD v1–v11 想覆盖"所有系统/玩法/战斗设计文档"，为了通用不断加特例（程序生成模式、发奖离线处理…），单调涨到 24KB。v14 把适用范围锁死成单一品类"需求 GDD"，立刻瘦回 5.3KB。

**规则**：标准开篇必须锁死"服务于哪一类产出物"。范围外的特例扔进扩展文件，不进主标准。一份标准想服务的品类越多，它一定越胖。

### 规律 2："膨胀→推翻"是默认命运，要主动设瘦身触发线，别等到崩

GDD 涨到 24KB、数值评审涨到 738 行，两次都是"胖到没法维护"才被迫一次性重写，代价是整篇推倒。被动等待让重写来得最晚、最贵。

**规则**：给标准设瘦身触发线——行数上限，或"为范围外特例新增的规则条数"。到线就主动审视是否该重写，不要等它自己崩。

### 规律 3：每条规则必须由一份真实产出物的审核反向触发，禁止凭空设计

GDD 每条判据都能对应一份被审出问题的真实文档：v8 空动词（"负责处理 X"）、v10 退出路径缺失、v15 枚举子类型只有分类表没流程、v18 技术实现混进 GDD。没有一条是"我觉得应该加"。

**规则**：新增判据时必须能指出"它修的是哪份文档的哪个具体问题"，并配一条可证伪的反例。说不出真实触发案例的条目不许进标准。这与 quality-gates.md 里的"评质量不评存在性"同源——都是拒绝拿"应该有"当依据。

### 规律 4：健康形态 = 固定的核心框架 + 可增删的判据清单

前期（v1–v11）靠堆框架层增长——加流程图层、加规则层、加节点字段表——这是病态膨胀。后期（v14–v18）核心四节一字未动，新增全落在"禁止行为 + Self-Review 判据"两处，每条配反例。

**规则**：新需求优先进判据清单，不动核心框架。一旦发现"又要改核心框架了"，这本身就是该考虑推翻重写的信号，而不是继续往框架里塞。

---

## 三、补充：同一取舍会随品类切换被重新裁决

"规则集中 vs 规则内嵌"在 GDD v3–v11 要求抽出独立规则层，v14 直接反转成"内嵌在子功能里、不许抽出"。原因是目标品类从"复杂系统设计文档"变成了"需求 GDD"。

含义：标准不是在线性逼近唯一正确答案。当它换服务对象时，旧的"正确"会失效甚至反转。所以**"适用品类"是标准的第一性声明，一旦它变，整套判据都要重审**——别把上一个品类的结论当真理继承。

---

## 四、怎么用：维护任何标准时过一遍

新建或修改标准类资产前，逐条自检：

1. **范围**：这份标准服务的产出物品类锁死了吗？我这次改动是不是在为范围外的特例加规则？（是 → 移到扩展文件）
2. **触发**：我新增的每条规则，能指出它修的是哪份真实文档的哪个问题吗？（说不出 → 不许加）
3. **层次**：我是在加判据，还是在动核心框架？（动框架 → 警惕，可能该重写而非堆叠）
4. **体积**：到瘦身触发线了吗？（到了 → 先评估重写，再决定要不要继续加）
5. **品类**：服务对象变了吗？（变了 → 整套判据重审，不要继承旧品类的结论）

践行检验：这份方法论自己也是一份标准。它讲"标准要保持薄"，所以它自己被刻意压在 100 行内——一份讲克制膨胀的文档若自己先臃肿，就证伪了自己。
