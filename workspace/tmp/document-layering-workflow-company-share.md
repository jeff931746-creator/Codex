# AI 文档标准分层工作流说明

## 1. 核心结论

这套工作流的核心思想是：

> 用规则层定义通用文档标准，用项目层补充项目特有约束，再让 Skill 按两层标准执行文档生成、修改和校验。

它要解决的不是“让 AI 写得更多”，而是“让 AI 写得稳定、可复用、少返工”。  
规则层保证所有文档有统一质量底线；项目层保证不同项目不会被同一套模板粗暴套用；Skill 负责把标准真正执行出来，而不是临场发挥。

一句话概括：

> 标准要完整，入口要短；项目可扩展，但不能覆盖规则；Skill 只执行规则，不发明规则。

## 2. 这个工作流解决什么问题

很多团队用 AI 写文档时，容易遇到三类问题。

### 2.1 文档结构不稳定

同一个需求，今天写成 PRD，明天写成会议纪要，后天又变成半份设计说明。  
问题不是 AI 不会写，而是每次任务都在重新解释“这类文档应该长什么样”。

### 2.2 项目差异被模板抹平

通用模板可以保证基本完整，但每个项目的真实需求不同。  
例如游戏项目、SaaS 项目、运营工具、数据分析项目，对文档重点的要求完全不同。

如果只有通用规则，文档会显得完整但不贴业务；如果只有项目说明，文档又容易丢掉通用质量底线。

### 2.3 质量依赖个人提示词

如果文档质量主要靠某个人每次写一段很长的 prompt，那么标准没有沉淀下来。  
换一个人、换一个会话、换一个项目，输出质量就会波动。

## 3. 分层架构

整体结构分为四层。

```text
+----------------------+
| 规则层               |
| 通用文档结构与质量底线 |
+----------+-----------+
           |
           v
+----------------------+
| 项目层               |
| 项目语境、术语、额外约束 |
+----------+-----------+
           |
           v
+----------------------+
| Skill / Agent 工作流  |
| 读取、组合、生成、校验 |
+----------+-----------+
           |
           v
+----------------------+
| 具体文档              |
| PRD / GDD / 技术方案等 |
+----------------------+
```

### 3.1 规则层：通用文档契约

规则层定义“所有项目都必须满足的文档质量底线”。

它回答这些问题：

- 这类文档必须包含哪些章节？
- 每个章节的作用是什么？
- 哪些信息不能缺？
- 什么样的表达算合格？
- 什么情况必须进入检查清单？
- 哪些错误属于阻断问题？

规则层不应该写项目背景，也不应该写某个项目的业务细节。

规则层的典型内容包括：

- 文档类型索引
- PRD 写作标准
- 技术方案写作标准
- 玩法 / 系统设计文档标准
- 审核 checklist
- 示例和反例

### 3.2 项目层：项目专属标准

项目层定义“这个项目在通用标准之外，还需要额外满足什么”。

它回答这些问题：

- 这个项目的核心目标是什么？
- 项目内术语如何定义？
- 哪些模块边界必须写清楚？
- 哪些章节是本项目特有的？
- 哪些规则比通用标准更严格？
- 哪些场景必须特别覆盖？

项目层的关键边界是：

> 项目层只能补充或收紧规则层，不能随意替换规则层。

例如，规则层规定需求文档必须包含“目标、范围、用户流程、功能说明、验收标准、风险”。  
某个游戏项目的项目层可以额外要求：

- 必须写核心战斗循环
- 必须写关卡结构
- 必须写数值配置边界
- 必须写离线异常处理
- 必须定义和战斗系统的接口边界

但项目层不能说“这个项目不需要验收标准”。  
因为验收标准属于规则层质量底线。

### 3.3 Skill：执行工作流

Skill 不是标准本身，而是执行标准的工作流。

它负责：

1. 判断当前任务属于哪类文档
2. 读取规则层入口
3. 按文档类型加载对应标准模块
4. 读取项目层标准和必要背景
5. 根据当前任务生成或修改文档
6. 按 checklist 自检
7. 输出结果和未决问题

Skill 不应该做三件事：

- 不应该临场发明文档标准
- 不应该跳过规则层直接写项目内容
- 不应该把所有规则一次性全量读入

### 3.4 具体文档：最终产物

具体文档是执行结果，不是规则来源。

它可以沉淀项目决策，但不应该反过来变成隐形规则。  
如果某个项目文档里的写法被证明值得复用，应该经过整理后进入项目标准、方法论或规则层，而不是让后续 AI 自己从历史文档里猜。

## 4. 标准完整，但入口要短

一个常见误区是：为了降低默认读取负担，把标准写得很短。

这会直接降低质量。  
因为“结构清晰、逻辑完整、表达准确”这类短句，只是愿望，不是可执行标准。

更合理的做法是：

> 标准本体可以完整，默认入口必须短。

也就是说，团队不应该删除详细标准，而应该把标准拆成可索引、可按需读取的模块。

推荐结构：

```text
document-standard-index.md
standards/
  prd-standard.md
  technical-design-standard.md
  game-design-standard.md
  research-note-standard.md
checklists/
  prd-checklist.md
  design-review-checklist.md
examples/
  good-prd-example.md
  bad-prd-example.md
```

Skill 执行时只需要先读 `document-standard-index.md`，再根据任务读取相关模块。

例如：

```text
用户要写玩法设计文档
-> 读取 document-standard-index.md
-> 判断文档类型是 game-design
-> 读取 game-design-standard.md
-> 读取项目层 project-standard.md
-> 生成文档
-> 使用 design-review-checklist.md 校验
```

这样既保留了高质量标准，又避免每次全量加载所有资料。

## 5. 质量如何保证

高质量不是靠“提示 AI 写好一点”，而是靠四类约束叠加。

### 5.1 结构约束

规则层规定文档必须有哪些章节，以及章节之间的顺序关系。

例如需求文档至少需要：

- 背景
- 目标
- 范围
- 用户流程
- 功能说明
- 验收标准
- 风险与未决问题

### 5.2 内容约束

项目层规定当前项目必须补充哪些内容。

例如游戏项目可能要求：

- 核心循环
- 关卡结构
- 成长线
- 数值边界
- 异常处理
- 跨系统接口

### 5.3 检查清单

每类文档都应该有 checklist。  
checklist 的作用不是装饰，而是决定这篇文档能不能交付。

有效 checklist 应该能回答：

- 是否缺关键章节？
- 是否有未定义术语？
- 是否有流程断点？
- 是否有规则冲突？
- 是否有未覆盖异常场景？
- 是否有无法验收的描述？

### 5.4 示例与反例

示例解决“什么叫写得好”的问题。  
反例解决“什么叫不合格”的问题。

只给规则，没有示例，AI 容易理解偏。  
只给示例，没有规则，AI 容易模仿表面格式。

所以最佳组合是：

```text
规则说明
+ checklist
+ 好示例
+ 坏示例
```

## 6. 权责边界

这套工作流能否稳定，关键在于边界清楚。

| 层级 | 负责什么 | 不负责什么 |
|---|---|---|
| 规则层 | 通用结构、质量底线、评审标准 | 项目背景、项目特例 |
| 项目层 | 术语、模块边界、项目扩展、特殊约束 | 推翻规则层质量底线 |
| Skill | 读取、组合、生成、校验 | 自行创造标准 |
| 具体文档 | 承载当前决策和交付内容 | 作为长期规则来源 |

最重要的治理原则：

> 规则层定义最低标准，项目层增加项目专属要求，Skill 负责执行，文档只承载结果。

## 7. 推荐落地流程

可以按六步落地。

### Step 1：盘点现有文档类型

先列出团队最常写的文档：

- 需求文档
- 技术方案
- 系统设计
- 玩法设计
- 调研报告
- 复盘报告
- 会议纪要

不要一开始就试图覆盖所有文档。  
先选最高频、返工最多的一两类。

### Step 2：建立规则层索引

先写一个短入口，说明：

- 有哪些文档类型
- 每类文档应该读取哪个标准
- 每类文档最低验收条件是什么
- 什么时候需要读取示例或 checklist

这个入口越清晰，Skill 越不容易乱读。

### Step 3：为一个文档类型写完整标准

不要只写口号。  
完整标准至少应该包含：

- 适用场景
- 必须章节
- 每章写作要求
- 常见错误
- 交付 checklist
- 示例 / 反例

### Step 4：建立项目层标准模板

每个项目应该有一份项目标准，内容可以包括：

- 项目背景
- 术语表
- 模块边界
- 项目特有章节
- 比规则层更严格的约束
- 当前项目的未决问题记录方式

项目标准的第一原则应该写清楚：

> 本文件只在规则层基础上增加约束或扩展章节，不替换规则层定义。

### Step 5：改造 Skill 调用逻辑

Skill 的执行顺序应固定：

```text
识别任务
-> 读取规则层索引
-> 选择文档类型标准
-> 读取项目层标准
-> 读取当前任务上下文
-> 生成或修改文档
-> checklist 校验
-> 输出结果
```

这样 Skill 就不再是“万能 prompt”，而是一个稳定的执行流程。

### Step 6：试点并沉淀

先在一个项目、一类文档上试点。  
观察三个指标：

- 文档返工次数是否下降
- 缺项和结构错误是否减少
- AI 每次读取的上下文是否可控

试点稳定后，再扩展到更多文档类型。

## 8. 常见风险

### 8.1 把规则层写得太短

风险：文档质量下降。  
修正：短的是入口，不是标准本体。

### 8.2 项目层覆盖规则层

风险：每个项目长出一套独立标准，统一质量底线失效。  
修正：项目层只能补充或收紧，不能删除规则层要求。

### 8.3 Skill 变成规则仓库

风险：Skill 越写越长，维护困难，且默认上下文膨胀。  
修正：Skill 写执行步骤，详细规则放标准文档，按需加载。

### 8.4 每次全量加载资料

风险：执行过程被无关资料稀释，输出偏离当前任务。  
修正：使用索引、摘要和按需读取，只加载当前任务必要材料。

### 8.5 示例变成隐形规则

风险：AI 模仿示例表面格式，而不是遵守标准。  
修正：示例必须服务于标准，不能替代标准。

## 9. 对团队协作的价值

这套工作流的价值不只在 AI 写文档。

它能让团队形成一套更清晰的协作机制：

- 新人知道文档怎么写
- 老人不用反复解释格式
- 项目差异有地方承载
- 评审有明确标准
- AI 输出更稳定
- 历史经验能逐步沉淀为标准

最终目标是把“靠人记住的隐性要求”，变成“系统能执行的显性流程”。

## 10. 推荐对外表述

如果要在公司分享中用一页讲清楚，可以这样说：

> 我们把 AI 文档工作流拆成三层：规则层、项目层和执行层。规则层定义所有文档的通用结构和质量底线；项目层补充项目特有的术语、模块边界和更严格约束；Skill 作为执行层，按规则层和项目层组合生成文档，并用 checklist 做交付校验。这样既不会因为标准太短导致质量下降，也不会因为资料加载过多导致执行失焦。它的关键原则是：标准完整、入口简短、按需加载、项目扩展、清单验收。

## 11. 最小可行版本

如果团队想快速试起来，不需要一次建完整体系。  
最小版本只需要四个文件：

```text
document-standard-index.md
standards/prd-standard.md
checklists/prd-checklist.md
projects/{project-name}/project-standard.md
```

再配一个 Skill 执行顺序：

```text
读索引 -> 读 PRD 标准 -> 读项目标准 -> 写文档 -> checklist 校验
```

这就是最小闭环。  
等它在一个项目里跑顺，再扩展技术方案、设计文档、复盘报告等其他类型。

## 12. 结束语

这套工作流的本质，是把文档生产从“单次 prompt 表演”变成“可持续的标准化协作”。

它不追求让 AI 一次性记住所有东西，而是让 AI 每次都知道：

- 该读什么
- 不该读什么
- 该遵守什么
- 该如何检查
- 什么时候需要回到人来决策

这样，文档质量不再依赖某次提示词写得巧不巧，而是依赖一套可维护、可升级、可审查的工作流。
