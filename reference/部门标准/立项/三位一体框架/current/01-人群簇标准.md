# 人群簇标准 v1.2

> 配套讨论:玩法承接 SDT 升级讨论(2026-05-14 至 2026-05-15)

---

## 这是什么

人群簇 v1.2 是 v1.1 的**理论框架升级稿**:

> **概念三分:产品 / 簇 / 样本**(2026-05-15 新增,来源:主对话决策)
>
> 在使用本标准之前,先理清三个概念,避免互相混用:
>
> | 概念 | 含义 | 数量级 | 例子 |
> |---|---|---|---|
> | **簇** | 用户聚类,本库定义的 12 个稳定落点 | 12(+1 候选) | C04 变强确认人群 / C09 协作分工人群 |
> | **产品** | 真实在市场上跑的游戏,可能**横跨多个簇** | 数千 | 原神 Steam 版主走 N-Comp+T2(C04 附近);原神微信社区版主走 N-Rel+T3(C03 附近);**同一产品在两个簇里** |
> | **样本** | 单个玩家的体验数据点(1455 样本即 1455 个数据点) | 海量 | 1455 SDT 验证样本中每个游戏 = 1 个样本 |
>
> 立项时要分清:
> - 谈"我们要做的是哪个簇"——用簇编号
> - 谈"对标产品是谁"——产品名,且要注明走的是哪个簇
> - 谈"市场分布证据"——样本聚合的统计结论
> 横跨多簇的产品需要拆开论证,不能用一个产品名当成一个簇的全部代表。


```
v1.1:人群簇 = 心理任务 T × 承接偏好 P → 推 12 簇(矩阵推演)
v1.2:人群簇 = N × T × 玩法承接 × 题材触发 的市场稳定落点(组合映射)
```

**核心变化**:
- 人群簇从"独立第一性维度"降级为"**三库交汇的索引层**"
- 引入 SDT(自我决定理论)作为底层心理需求锚点
- 不再自定义承接维度,引用玩法承接库;不再自定义题材,引用题材母题库
- 12 簇内容暂保留,但每个簇按新四层结构重写定义

## 四层架构(v1.2 核心)

```
N(SDT 三需求)    ← 地基,长期不变,普适
  ↓
T(任务态)       ← 用户当下处理的心理任务
  ↓
玩法承接(A/F)   ← 玩法用什么提供反馈
  ↓
题材触发(THM)   ← 题材用什么唤起情绪
  ↓
人群簇 = 四层在市场中稳定重合后的索引
```

每层有清晰职责,不互相替代:
- N 防概念漂移
- T 主区分轴
- 承接给机制
- THM 给激活

---

## 第一层:N 底层需求(SDT)

理论根基:Self-Determination Theory(Deci & Ryan 1985, 2000)+ Player Experience of Need Satisfaction(Ryan, Rigby & Przybylski 2006)

| N | 学术名 | 通俗解释 |
|---|---|---|
| N-Comp | 胜任感(Competence)| 我能做到 / 我变强 / 我懂了 / 我掌控了 |
| N-Auto | 自主性(Autonomy)| 我能自己选 / 我按自己的方式玩 |
| N-Rel | 关系感(Relatedness)| 我和谁有连接 / 我在关系里有位置 |

**N 的功能定位**:
- 是**底层心理需求锚点**,防止概念漂移
- 不是主要的簇区分轴(那是 T 的职责)
- N-Comp 占比高是游戏媒介事实(游戏天然以能力验证为主),不是 bug

**N-Rel 的范围**:
- 包括"温和归属"(乙女、宠物、公会)
- 也包括"权力关系"(SLG 大盟主对组织的支配)
- 通过 secondary_N + secondary_reason 区分不同表现
- **细分对象类型**:N-Rel 同时必填 `rel_object` 副字段,枚举 `virtual / real / mixed`,与玩法承接 v1.1 标准的同名字段保持一致(来源:P0-4 字段补齐)

---

## 第二层:T 任务态

T 不是底层需求,而是**用户在某段时间具体处理的心理任务**。一个 T 可由多个 N 承接,一个 N 可服务多个 T。

| T | 任务态 | 主要由哪些 N 承接 |
|---|---|---|
| T1 | 状态调节 | N-Auto(无目标转移)/ N-Comp(快速胜任爽感)/ N-Rel(治愈陪伴) |
| T2 | 价值/能力确认 | N-Comp |
| T3 | 对象亲密 | N-Rel(rel_object=virtual) |
| T4 | 群体位置 | N-Rel(rel_object=real / mixed) |
| T5 | 规则理解 | N-Comp |
| T6 | 秩序掌控 | N-Comp + N-Auto |

**注意**:
- T1 不是 N-Auto 的别名。割草泄压本质是 N-Comp(瞬间胜任反馈),只是任务态是 T1
- T2/T5/T6 共享 N-Comp 但任务态不同,不能粗暴合并
- T 列表暂沿用 v1.1 的命名,后续可微调

**T_main + T_secondary 结构**(2026-05-15 修订,来源:P0-1):

人群簇 v1.2 用 `T_main`(必填,1 个)+ `T_secondary`(0-1 个,可选)表达"用户当下处理的主任务态 + 一个并存的次任务态"。

- `T_main`:该簇用户长期留下来在处理的主任务,**必填,只能 1 个**
- `T_secondary`:并存的副任务态,**0-1 个**;少数情况下用户同一段时间承接两种任务态(如咸鱼之王同时承接 T2 变强 + T1 泄压),才填
- 与玩法承接库的区分:玩法承接 `t_main + t_secondary` 允许 0-2 个副(因为玩法可同时承接多个任务态);人群簇 `T_secondary` 收紧到 0-1 个(因为簇是用户聚类,任务态过多即说明聚类不稳)

## 第三层:玩法承接(引用玩法承接库)

**人群簇库不自定义承接维度**,直接引用玩法承接库的 A/F/P。

依赖方向:**玩法承接库定义 → 人群簇库引用**(下游使用上游,不重新发明)。

引用方式:
```yaml
AF_ref:
  A: [A2, A3]        # 反复行为(玩法库定义)
  F: [F1, F2]        # 成功反馈(玩法库定义)
P_hint:              # 关键 P 标签(可选,辅助理解簇)
  cost: [P-Time, P-Rxn]
  pressure: [Pr-Lose]
```

**用户侧承接摘要**(展示字段,不参与分类):

| 摘要 | 对应玩法 F |
|---|---|
| 强刺激反馈 | F1 击杀反馈 / F2 数值膨胀 |
| 系统模拟 | F3 系统涌现 / F4 闭环达成 |
| 情感共鸣 | F5 情感见证 |
| 社交认可 | F6 社交认可 |
| 低负荷转移 | F4 闭环达成的低强度版本 |
| 自由表达 | (玩法库 F 当前缺口,需评估是否新增 F7) |

注意:如人群簇出现承接需求超出现有 F 范围,**反向推动玩法承接库补 F**,不在人群簇里自造。

## 第四层:题材触发(引用题材母题库)

**人群簇库不自定义题材**,引用题材母题库 THM 编号。

每个簇必标:
```yaml
THM_ref: [THM-逆袭, THM-战神]
theme_sensitivity: high | medium-high | medium | medium-low | low
theme_role: hard_trigger | soft_amplifier | replaceable_skin
theme_driver:
  - acquisition    # 影响获量
  - retention      # 影响留存
  - monetization   # 影响付费
  - identity       # 影响身份代入
  - virality       # 影响破圈传播
theme_note: "为什么这些题材对这个簇重要"
```

**theme_role 定义**:
- `hard_trigger`:题材是核心激活器,换题材会明显改变人群(如 C04 战神/逆袭强绑死)
- `soft_amplifier`:题材影响获量和表达,但玩法承接可迁移(如 C09 三国/末世可换)
- `replaceable_skin`:题材主要是包装,核心用户更看系统(如 C11 经营题材弱敏感)

**theme_role 反事实测试判据**(2026-05-15 新增,来源:P1-3):

判定一个题材属于哪档 role,问反事实问题"换题材后留存会掉多少":

| role | 反事实留存下降 | 数据来源建议 |
|---|---|---|
| `hard_trigger` | 换题材后留存掉 >30% | 实际换皮投放对比 / 同核心循环不同题材的竞品留存对比 |
| `soft_amplifier` | 换题材后留存掉 10-30% | 同题材库 IP 联动产品对比 / 阶段性换季活动留存 |
| `replaceable_skin` | 换题材后留存掉 <10% | 经营/解谜/沙盒类同核心循环跨题材竞品对比 |

立项时若没有真实数据,先按市场观察给 hypothesis,再用首批投放数据反推校正。

**theme_sensitivity 5 档锚定例**(2026-05-15 新增,来源:P1-4):

| sensitivity | 锚定簇 | 示例题材 | 说明 |
|---|---|---|---|
| high | C04 | 战神 / 逆袭 / 修仙渡劫 | 下沉用户对叙事敏感,题材直接决定能否激活 |
| medium-high | C09 | 三国 / 末日 / 战争 | 强化阵营身份和文化代入,可在同体系内迁移 |
| medium | C08 | 武侠 IP / 仙侠陪伴 | 题材影响代入但核心承接相对稳定 |
| medium-low | C10 | 解谜母题 / 推理叙事 | 题材决定入口体验,核心是机制理解 |
| low | C11 | Factorio / 城市天际线 | 题材是包装,核心用户更看系统深度 |

**theme_driver 约束**(2026-05-15 修订,来源:P0+ 反测试补丁,取代原 P1-9 的"最多 2 个"统一规则):

`theme_driver` 数量上限按 `monetization_models[0]` 调整:

- `buyout / sub / iap_single`:最多 2 个驱动(单次/订阅类天然收敛)
- `gacha / mixed-gacha-iap`:最多 3 个驱动(gacha 类天然有 4 驱动,强压到 2 个会丢信息;允许 3 个但 virality 不进主驱动)
- `iaa`:最多 2 个驱动(通常收敛到 acquisition + retention)
- `iap`(非纯 single):最多 2 个驱动

实际想标超过上限 → 簇定义本身不收敛,回头审视 primary_N 和 T_main 是否需要拆分。完整规则见"v1.2 簇定义字段结构 → 字段说明补充 → theme_driver 数量上限"。

**THM theme_role 与目标簇 sensitivity 兼容性约束**(2026-05-15 新增,来源:P-1 硬约束 4):

立项时,题材角色必须与目标簇的 sensitivity 兼容:

| 目标簇 sensitivity | 必须的 theme_role | 错配后果 |
|---|---|---|
| high(C04 类) | 必须 `hard_trigger` | 用 replaceable_skin 题材 → 失去激活力,目标用户进不来 |
| medium-high / medium | `hard_trigger` 或 `soft_amplifier` 都可,需匹配 driver | — |
| low(C11 类) | 必须 `replaceable_skin` | 用 hard_trigger 题材 → 核心系统玩家被叙事压力赶跑,叙事玩家又留不住 |

错配会**同时赶跑两类用户**,这是立项最常见的隐性失败。

## v1.2 簇定义字段结构

v1.2 yaml 拆成两个 section(2026-05-15 修订,来源:P0-3):
- `# === 簇定义 ===`:必填且影响匹配的字段(primary_N / T_main / AF_ref / THM_ref / boundary_rules 等)
- `# === 簇治理 ===`:生命周期管理字段(cluster_status / evidence_grade / evolution_note / evolution_trigger / representative_cases 等)

```yaml
# === 身份 ===
cluster_id: C04
cluster_name: 变强确认人群

# === 簇定义(必填,影响匹配)===

# 第一层 N
primary_N: N-Comp          # 必填,单选,主簇判据
secondary_N: [N-Auto]      # 0-2 个,可选
secondary_reason:          # 标 2 个时必填
  N-Auto: "升级路径玩家可选,提供轻自主性"
rel_object: null           # primary_N=N-Rel 或 secondary_N 含 N-Rel 时必填(virtual/real/mixed),否则 null;与玩法承接库同名字段对齐

# 第二层 T
T_main: T2                 # 必填,1 个主任务态
T_secondary: []            # 0-1 个并存副任务态(收紧到 0-1,玩法承接库的 t_secondary 允许 0-2)
cover_T_promise: null      # 卖相/素材承诺的任务态(选填,2026-05-15 新增,来源:P0+ 反测试补丁)
                           # 与 T_main 不一致时必填,触发立项硬约束 H3 告警
                           # 取值同 T_main(T1-T6),仅描述"素材+题材+宣发想让用户期待什么任务态"
                           # 一致时建议留 null,避免冗余

# 第三层 玩法承接(引用)
AF_ref:
  A: [A2, A3]              # 数组按重要性排序,最多 3 个;超出 3 个反推这是复合产品(横跨多簇)
  F: [F1, F2]              # 数组按重要性排序,最多 3 个
complex_cluster_flag: false  # 是否复合簇,默认 false(2026-05-15 新增,来源:P0+ 反测试补丁)
                             # AF_ref 任一维度达到 3 时,需明确填 true/false
                             # true 时必须在 evolution_note 说明横跨哪些子簇
P_hint:
  cost: [P-Time, P-Rxn]
  pressure: [Pr-Lose]

# 第四层 题材(引用)
THM_ref: [THM-逆袭, THM-战神, THM-修仙渡劫]
theme_sensitivity: high
theme_role: hard_trigger
theme_role_basis: hypothesis  # theme_role 判定依据(2026-05-15 新增,来源:P0+ 反测试补丁)
                              # 枚举:swap_test / analogy / hypothesis
                              # hypothesis 时 evidence_grade 不得高于 C
theme_driver:              # 数量上限按 monetization_models[0] 调整(详见字段说明)
  - acquisition
  - identity
theme_note: "战神/逆袭/修仙渡劫强绑死,下沉用户对'变强叙事'敏感"

# 边界
boundary_rules:
  - "与 C05 区别:对手是 PVE 内容 → C04;对手是真人 → C05"
  - "与 C10 区别:卡关想'练手感' → C04;卡关想'机制看不明白' → C10"

# 平台与商业化(2026-05-15 新增,P1-2;2026-05-15 修订为数组,来源:P0+ 反测试补丁)
platforms: [mobile_iap]              # 数组,首项为主平台,最多 3 项
                                     # 枚举:mobile_iaa / mobile_iap / steam / console / wechat_mini
monetization_models: [gacha, iap]    # 数组,首项为主商业化,最多 2 项
                                     # 枚举:buyout / gacha / iaa / iap / sub / iap_single

# === 簇治理(生命周期管理)===

cluster_status: stable | hypothesis | boundary | deprecated
evidence_grade: S | A | B | C | D

evolution_note: "C04 当前覆盖操作型/数值型/刷宝型三类承接,通过 A/F 区分,簇内不再细分"
evolution_trigger:
  - "若操作型/数值型样本在用户偏好上呈分化 → 触发拆分"

# === 反例累积(2026-05-15 新增,来源:成功复盘 SOP)===
counterexample_log:           # 复盘时发现的"违反框架但成功"案例,数组,可空
  - product: 原神
    violates: AF_ref.A 长度超 3
    why_succeeded: "米哈游研发能力 + IP + 渠道,弥补了组合复杂度"
    framework_lesson: "复合产品超 3 个 A 是可行的,但需要团队+IP双重支撑"
    logged_date: 2026-05-15
  # 累积 ≥ 3 个针对同一硬约束的反例时,触发该约束的修订评估

# 应用注释
media_fit:
  game_primary: high
  content_primary: high
representative_cases: [战神短剧, 斗罗大陆, 黑神话:悟空, 咸鱼之王]
```

**字段说明补充**:

- `AF_ref.A` / `AF_ref.F`(2026-05-15 修订,来源:P1-1):数组按重要性排序,**最多 3 个**。如果某簇需要列出超过 3 个 A 或 F,说明它实质上横跨多簇(典型如原神 Steam 偏 N-Comp、原神微信偏 N-Rel),应拆分论证而非堆叠
- `complex_cluster_flag`(2026-05-15 新增,来源:P0+ 反测试补丁):AF_ref 上限触发的强制告警字段。

  ```
  AF_ref 上限检查规则:
    IF length(AF_ref.A) == 3 OR length(AF_ref.F) == 3:
      必须填 complex_cluster_flag(true/false)
      IF true:
        evolution_note 必须说明横跨哪些子簇
        建议拆分为多个 cluster_id 独立论证(典型:原神 Steam vs 微信版)
      IF false:
        在 boundary_rules 说明为何保留 3 个的合理性

  禁止行为:
    - 不能继续往 A/F 数组堆第 4-5 个值
    - 不能在其他字段(如 evolution_note / theme_note)塞剩余 A/F
  ```

- `cover_T_promise`(2026-05-15 新增,来源:P0+ 反测试补丁):卖相/素材承诺的任务态。与 T_main 不一致时必填,触发立项硬约束 H3 自动告警(详见"立项 5 大硬约束 → H3")。一致时建议留 null。
- `rel_object`(2026-05-15 新增,来源:P0-4):当 primary_N=N-Rel 或 secondary_N 含 N-Rel 时必填,与玩法承接库的同名字段保持同义
- `platforms`(2026-05-15 修订为数组,来源:P0+ 反测试补丁):数组,首项为主平台,**最多 3 项**。枚举 `mobile_iaa / mobile_iap / steam / console / wechat_mini`。

  ```
  platforms 数组规则:
    - 单平台产品:1 项
    - 跨平台产品:2-3 项,首项为主平台
    - 拆分判据:
      IF 不同 platforms 上的 primary_N 不同 → 必须拆分为多个 cluster_id
      IF primary_N 相同但 P_hint 差异显著(如手游 P-$ 高、PC 端 P-Time 高):
         留单簇,但 boundary_rules 必须加注平台差异
  ```

- `monetization_models`(2026-05-15 修订为数组,来源:P0+ 反测试补丁):数组,首项为主商业化,**最多 2 项**。枚举 `buyout / gacha / iaa / iap / sub / iap_single`。

  ```
  monetization_models 数组长度限制:
    - 1 个:纯单一商业化(买断、纯订阅、纯 gacha)
    - 2 个:混合商业化
      典型:iaa + iap(无尽防线类小游戏)
           gacha + iap(二次元 + 月卡)
           buyout + DLC iap
    - 超过 2 个:商业化定位不清,需重新立项
  ```

- `theme_role_basis`(2026-05-15 新增,来源:P0+ 反测试补丁):theme_role 的判定依据,枚举 `swap_test / analogy / hypothesis`。

  ```
  theme_role_basis 约束:
    IF theme_role_basis == "hypothesis":
      evidence_grade 不能高于 C(防止虚标 role 推高证据等级)

    作用:防止 theme_role 被"虚标"
    Thronefall 等案例中,theme_role 写 soft_amplifier 但实际投放当 hard_trigger 用,
    通过强制 theme_role_basis 让判定依据透明化。
  ```

- `theme_driver` 数量上限(2026-05-15 修订,来源:P0+ 反测试补丁):上限按 monetization_models[0] 调整,取代原"最多 2 个"的统一规则。

  ```
  theme_driver 数量上限按商业化模型调整:

    monetization_models[0] in [buyout, sub, iap_single]:
      最多 2 个驱动
      (单次/订阅类商业化,驱动天然收敛)

    monetization_models[0] in [gacha, mixed-gacha-iap]:
      最多 3 个驱动
      (gacha 类天然有 4 驱动:acquisition + identity + monetization + retention,
       强压到 2 个会丢关键信息;允许 3 个但 virality 不进主驱动)

    monetization_models[0] == iaa:
      最多 2 个驱动
      (iaa 模式通常收敛到 acquisition + retention)

    monetization_models[0] == iap(非纯 single):
      最多 2 个驱动

  字段约束失败处理:
    IF 实际想标 > 上限:
      → 簇定义本身不收敛,应回头审视 primary_N 和 T_main 是否需要拆分
  ```

| 原则 | 内容 |
|---|---|

## 立项 5 大硬约束

> 2026-05-15 新增,来源:**用户提出**。本章节为立项时必须逐条核对的硬约束,优先级高于一般原则。

### 硬约束 1:N 一致是陷阱(四层一致才算一致)

**事实**:1455 样本验证中,N-Comp 占 74.8%,**N 维度区分力天然弱**。仅看 N 一致就误判"同簇"是立项最常见的陷阱。

**正确做法**:真正的区分力在 **T × A × F** 三层。立项决策必须四层(N、T、AF_ref、THM_ref)都对齐,不能只看 N。

**反面例子**(三个都是 N-Comp+T2,但承接形态完全不同):

| 产品 | N | T_main | A_main | F_main | THM_role |
|---|---|---|---|---|---|
| 黑神话:悟空 | N-Comp | T2 | A2 克服 PVE | F1 击杀反馈 | hard_trigger(神话叙事) |
| 咸鱼之王 | N-Comp | T2 | A3 投入累积 | F2 数值膨胀 | hard_trigger(小人物逆袭) |
| 王者荣耀 | N-Comp | T2 | A1 对抗真人 | F1 击杀 + F6 社交认可 | replaceable_skin |

三款的 N+T 完全一致,但因为 A、F、THM 全不同,**实际是三个完全不同的人群簇**。把它们放在同一立项框里讨论"我们做 N-Comp+T2 的产品"是无效讨论。

**四层一致性检查清单**(立项必跑):

1. [ ] primary_N 一致
2. [ ] T_main 一致
3. [ ] AF_ref.A 中前 2 个一致(允许 0 或 1 个不一致,但需说明原因)
4. [ ] AF_ref.F 中 F_main 一致
5. [ ] THM_ref 的 theme_role 一致(都是 hard_trigger 或都是 replaceable_skin,不能混)

5 条全过 → 同簇;过 3-4 条 → 边界样本,需复核;过 ≤2 条 → 不同簇。

### 硬约束 2:A 真伪判据

**事实**:很多产品在素材里展示某些 A(如塔防关 + 内置射击),但玩家进入后这个 A 不再被反复执行。这种 A 是"伪 A",仅为获量素材差异化服务,不进 a_main / a_others。

**判据**:

| 类型 | 标志 | 处理 |
|---|---|---|
| **真 A** | 对留存 / 付费有直接贡献,玩家进入后**反复执行**这个动作 | 进 a_main 或 a_others |
| **伪 A** | 仅为获量素材差异化,玩家进入后**不再或极少**执行这个动作 | 不进 a_main / a_others,可在 `acquisition_hooks`(选填)注明 |

**SOP**:立项时**Step 1 必须先做真伪判据**,再决定 a_main / a_others。判断方法:

- 看 7 日 / 30 日留存用户的核心行为日志,出现频次低于 20% 留存样本 → 伪 A
- 没有数据时,反问"删掉这个动作,玩家会停玩吗?",不会停玩 → 伪 A

**典型反面例**:某买量产品素材展示射击玩法,但玩家进入后核心是塔防摆放(A4)+ 战力养成(A3),射击仅在素材里出现,实际承接为 0 → 伪 A,不进字段。

### 硬约束 3:卖相 T 与实际承接 T 必须一致(Thronefall 案例)

**事实**:题材 / 卖相可以承诺任意 T(素材里包装"建造一个王国 / 经营一个农场"),但玩家实际的 A、F 决定他真正承接的 T。两个 T 不一致 → 必然产生宣发落差,首日留存暴跌。

**反面例**:Thronefall 卖相主打"建造王国"(承诺 T6 秩序掌控),但核心循环是"放置防御 + 实时对抗 + 通关"(实际承接 T2 价值确认 + T5 规则理解)。买量进来的"建造党"留存极差,留下来的全是动作 / 防御玩家。

#### H3 卖相 vs 实际承接检查(机器化判据)

> 2026-05-15 修订,来源:P0+ 反测试补丁。原"立项时跑两轮 v1.2 校验"改为基于 `cover_T_promise` 字段的自动检查规则。

立项时填 v1.2 yaml 时,如果素材/题材/宣发承诺的任务态与产品实际承接不同:
  必须在 `cover_T_promise` 字段标注卖相承诺的 T

自动检查规则:

```
IF cover_T_promise != null AND cover_T_promise != T_main:
  → 触发立项错位警告
  → 立项决策必须选择以下三种修正之一:
     A. 改素材:让卖相回归 T_main(投放重做)
     B. 改产品:让 A/F 真正承接 cover_T_promise(玩法调整)
     C. 接受错位:标 cluster_status: boundary,evolution_note 记录预期流失率
ELSE IF cover_T_promise == null:
  默认与 T_main 一致(常态)
```

典型反例:Thronefall — `T_main=T2`,`cover_T_promise=T6`。卖相承诺"建国土秩序掌控"(T6),实际承接是战斗确认(T2),未在立项前选择 A/B/C → 上市后用户流失率显著高于同 T_main 竞品。

立项里"我们可以两个都做到"是错误答案,实际不可能两个都做。

### 硬约束 4:THM theme_role 与目标簇 sensitivity 兼容性

**事实**:已在第四层"THM theme_role 与目标簇 sensitivity 兼容性约束"中正式定义。本条作为立项硬约束再强调一次:

| 目标簇 sensitivity | 必须的 theme_role | 错配后果 |
|---|---|---|
| high | 必须 `hard_trigger` | 用 replaceable_skin → 失去激活,核心用户进不来 |
| low | 必须 `replaceable_skin` | 用 hard_trigger → 题材压力赶跑系统玩家,叙事玩家又留不住 |

**错配 = 同时赶跑两类用户**。这是题材 / 玩法不匹配最隐性的失败模式。

立项时强制核对:目标簇的 sensitivity 等级 → 检查 theme_role 是否兼容。不兼容时必须改其中一个,不能并存。

### 硬约束 5:P 压力对 N 的排除规则

**事实**:P 压力组合会反向排除某些 N 选项。立项时先定 N,再选 Pr;Pr 选错会反向证伪 N。

**排除规则**:

| 主导压力 | 排除的 N | 原因 |
|---|---|---|
| Pr-Lose 主导 | 排除 N-Auto | 失败惩罚强 → 玩家无法自定节奏 |
| Pr-Cmp 主导 | 排除 N-Auto | 与真人比较 → 节奏被他人牵着走 |
| Pr-Rnd 主导 | 排除 N-Auto | 运气主导 → 玩家无法把控 |
| Pr-Sct 主导 | 排除 N-Auto | 资源稀缺压力 → 被迫追赶 |
| Pr-Spd 主导 | 排除 N-Auto | 限时压迫 → 节奏被版本逼迫 |
| Pr-Low 主导 | 排除 N-Comp | 无目标无压力 → 没有"做到"可以验证,无法承接胜任感 |

**SOP**:立项时**先定 N → 再选 Pr**。若 Pr 选完后发现违反上表 → 反向证伪 N 选择,需回头重选。

具体的 P-N 兼容性约束在玩法承接 v1.1 标准的 P 压力章节也已纳入。

### 反例累积机制(2026-05-15 新增,来源:成功复盘 SOP)

**触发条件**:

- 成功复盘 SOP([07b-成功复盘SOP.md](07b-成功复盘SOP.md))中发现产品违反某硬约束但仍成功
- 必须在簇定义的 `counterexample_log` 字段记录(yaml 模板已纳入)
- 累积 ≥ 3 个针对同一硬约束的反例 → 触发该约束的修订评估

**修订流程**:

- 触发评估**不等于**立刻改框架
- 主对话讨论:这些反例是"特例"还是"框架漏洞"
- 如确认是漏洞 → 进入正式 v1.2 → v1.3 修订
- 如是特例 → 在对应硬约束章节加注"已知特例清单",框架版本不变

**字段说明**:

| 字段 | 含义 |
|---|---|
| `product` | 反例产品名 |
| `violates` | 违反的硬约束(如 H1 N 一致陷阱 / H3 卖相错位 / AF_ref 上限) |
| `why_succeeded` | 为什么仍能成功(IP / 团队 / 时机 / 渠道 / 隐性优势) |
| `framework_lesson` | 这个案例对框架的启示(是否暴露容忍区间) |
| `logged_date` | 记录日期 |

**与硬约束的关系**:

- 硬约束是**失败避免条件**,不是"成功必要条件"
- 违反硬约束但成功的产品**不否定硬约束**,但需在 `counterexample_log` 留痕
- 复盘 SOP 主动产出反例,立项 SOP 不消费反例(立项分析自身仍按硬约束 check)

## 证据等级 evidence_grade

| 等级 | 证据要求 | 可支持的结论 |
|---|---|---|
| **S** | 自有投放/留存/付费/用户重合数据 | 稳定簇,可作核心立项依据 |
| **A** | 多产品真实商业成功 + 榜单/收入/素材长期存在 | 高可信稳定簇 |
| **B** | 多样本 LLM 归类 + 明确竞品案例 + 逻辑自洽 | 假设簇,可立项但需补证 |
| **C** | 少量样本或单一品类推断 | 待验证组合 |
| **D** | 理论推演,无市场样本 | 不入正式簇 |

## 簇状态 cluster_status

| 状态 | 含义 |
|---|---|
| `stable` | 已有市场稳定证据,可作核心立项依据 |
| `hypothesis` | 逻辑成立但证据不足,可立项但需复核 |
| `boundary` | 边界样本/待复核,不可单独立项 |
| `deprecated` | 已废弃(但保留记录) |

每个簇 status 与 evidence_grade 配合使用:
- evidence_grade ≥ A → status 可标 stable
- evidence_grade B → status 通常为 hypothesis
- evidence_grade C-D → status 应为 boundary 或 deprecated

## 分类流程(v1.2)

```
分析一个产品时,不要直接问"它属于哪个 C"。按以下流程:

Step 1: 判 T 任务态
  问:用户长期留下来是在处理什么任务?
  确定 T_main(必填,1 个);若并存第二任务态,补 T_secondary(0-1 个)

Step 2: 判 N 底层需求
  问:这个任务底层满足哪个 SDT 需求?
  确定 primary_N 和可能的 secondary_N

Step 3: 判玩法承接
  问:玩法系统靠什么 A/F 提供反馈?
  从玩法承接库引用 AF_ref

Step 4: 判题材触发
  问:题材靠什么母题 THM 触发用户?
  确定 theme_sensitivity / theme_role / theme_driver

Step 5: 匹配已有 C 簇
  在 12 簇中寻找与 (primary_N, T_main, AF_ref, THM_ref) 最匹配的

Step 6: 如果匹配不上
  不新增簇,先标为 boundary 样本/待验证组合
  累积达到一定数量后,启动新簇评估
```
