## 章节 1:状态说明

### 1.1 这是什么

玩法承接 v1.1 是 v1 标准的**整体重写稿**,已升格为正式执行标准。

- v1 的公分母:`品类大类 + 核心循环组合 + 独立性五问`,以"品类骨架"为骨架
- v1.1 的公分母:`玩家行为契约 = A × P × F × N`,以"玩家在做什么、付出什么、得到什么、底层满足什么需求"为骨架

v1 把玩法看作**品类的具体形态**(塔防、卡牌、SLG…);v1.1 把玩法看作**玩家与系统之间的稳定行为契约**,品类只是这套契约在市场上的常见外壳之一。

### 1.2 与 v1 的关系(历史追溯)

v1 已归档至 [`history/03-玩法承接标准/v1.0_2026-05-12.md`](../history/03-玩法承接标准/v1.0_2026-05-12.md),仅作追溯查阅,不进入执行流。

## 章节 2:公分母定义

玩法承接 = 玩家行为契约 = **A × P × F × N**

```
A (Action)    ─ 玩家每天/每局/每节点反复做什么
P (Pressure)  ─ 玩家付出什么(成本)+ 承受什么(压力)
F (Feedback)  ─ 成功瞬间玩家得到什么反馈
N (Need)      ─ 这个反馈满足什么基本心理需求(SDT 三需求)
```

四个维度互相支撑,缺一不可:
- A 缺失 → 玩法没有可重复的核心动作
- P 缺失 → 玩家没有投入,无承诺,无心流
- F 缺失 → 玩家不知道自己赢了,无强化
- N 缺失 → 无法判断玩家"为什么留下来",无法判断玩家簇

### 命名约定

- 字段命名一律小写下划线(`a_main`, `n_others`, `p_pressure` 等)
- 维度代号区分大小写:`A1`/`A2` 行为编号、`F1`/`F2` 反馈编号、`P-Rxn`/`Pr-Lose` 压力编号、`N-Comp`/`N-Auto`/`N-Rel` 需求编号、`T1`-`T6` 任务态编号
- yaml 字段值用枚举代号,不用中文别名

## 章节 3:N 基本心理需求(SDT 三需求)

### 3.1 理论根基

- Deci, E. L. & Ryan, R. M. (1985, 2000). Self-Determination Theory.
- Ryan, R. M., Rigby, C. S. & Przybylski, A. (2006). The motivational pull of video games: A self-determination theory approach.

SDT 主张人有三种基本心理需求,长期不变、跨文化普适。N 维度即把 SDT 三需求作为玩法承接的底层锚点。

### 3.2 三需求完整定义

#### N-Comp 胜任感(Competence)

**定义**:玩家通过游戏验证"我能做到 / 我能掌握"。

**覆盖范围**:
- 操作能力被验证(打击、连招、走位、反应)
- 认知能力被验证(解谜、构筑、推演)
- 系统掌控(自动化、流程优化、规则掌握)
- 数值膨胀(养成数字稳定上涨、战力提升)
- 通关达成(关卡过、副本过、谜题解)
- PVP 上分(排位、比拼、击败对手)

**关键特征**:有目标 + 有反馈 + 玩家能力被验证。

**典型游戏**:黑神话:悟空(操作胜任)、咸鱼之王(数值胜任)、杀戮尖塔(认知胜任)、Factorio(系统胜任)、王者荣耀(竞技胜任)。

**与 v1.2 人群簇的对接**:N-Comp 是 C04/C05/C10/C11 的 primary_N。

#### N-Auto 自主性(Autonomy)

**定义**:玩家获得"我自己决定"的自由感。

**覆盖范围**:
- 无目标体验(没有强制目标,玩什么自己定)
- 自由探索(开放世界探索,主动发现)
- 自定义建造(沙盒、装修、捏脸捏角色)
- 无压力消磨(放置、挂机、休闲消除)
- 低压派对(轻量社交,无强对抗压力)

**关键特征**:玩家自定节奏 + 自定目标 + 低强制压力(Pr-Low 主导)。

**典型游戏**:Minecraft 创造模式、模拟人生、动物森友会、蛋仔派对(派对模式)、消消乐(无强目标版)。

**与 v1.2 人群簇的对接**:N-Auto 是 C01(状态调节)、C06(自由表达,候选)的 primary_N。

#### N-Rel 关系感(Relatedness)

**定义**:玩家通过游戏获得"我和谁有连接"。

**覆盖范围**:
- 虚拟关系(与 NPC、宠物、可攻略角色、剧情角色的情感纽带)
- 真人关系(队友、公会、熟人局、PVP 对手关系本身)
- 组织归属(SLG 联盟、MMO 公会、固定开黑队)
- 权力关系(SLG 大盟主对组织的支配,非温和归属)

**关键特征**:与对象的关系是主驱动,不是工具。

**反例提醒**:王者荣耀里队友是"赢比赛的工具" → N-Comp;MMO 公会里队友是"归属对象" → N-Rel。同样是"和真人玩",N 不同。

**典型游戏**:乙女游戏(虚拟亲密)、原神角色向玩家(虚拟亲密)、SLG 联盟战(真人组织)、MMO 公会(真人组织)、宠物游戏(虚拟陪伴)。

**与 v1.2 人群簇的对接**:N-Rel 是 C03/C08/C09/C12 的 primary_N(C12 为权力型 N-Rel,与温和型区分)。

### 3.3 rel_object 副字段(N-Rel 关系对象类型)

当 `n_main = N-Rel` 时,必须标 `rel_object`:

| 取值 | 含义 |
|---|---|
| `virtual` | 关系对象是虚拟角色 / NPC / 宠物 |
| `real` | 关系对象是真人 |
| `mixed` | 虚拟与真人两者并存 |

当 `n_main ≠ N-Rel` 时,`rel_object` 留空(`null`)。

### 3.4 主副规则

每个玩法承接条目必须标:
- `n_main`:N-Comp / N-Auto / N-Rel 之一(必填,1 个主 N)
- `n_secondary`:0-2 个副 N(选填,允许跨需求)。**字段命名 2026-05-15 修订(P0-2),原 `n_others` 改为 `n_secondary`**

判定原则:**按"长期留存与付费最核心的驱动力"决定主 N**,不是按"出现频率最高"决定。

## 章节 4:A 反复行为(7 个)

A 描述玩家每天/每局/每节点绕不开的核心动作。允许多选,但必须标 1 个主 A。

| 编号 | A 类型 | 描述 | 典型动作 | 典型游戏 |
|---|---|---|---|---|
| A1 | 对抗真人 | 与真人 PVP 胜负、比拼、博弈 | 排位赛、对线、抢分 | 王者荣耀、CS、皇室战争 |
| A2 | 克服 PVE 内容 | 打 BOSS、推关卡、刷怪 | 推图、副本、boss 战 | 黑神话:悟空、原神大世界、消消乐 |
| A3 | 投入累积 | 登录、领奖、看战力涨、刷资源 | 每日任务、看数值面板、肝资源 | 咸鱼之王、放置奇兵、SLG 资源运营 |
| A4 | 调整系统 | 设计布局、排序、优化流程、调参 | 拉传送带、改阵容、调流水线 | Factorio、动森装修、SLG 城建 |
| A5 | 探索/试错 | 抽卡组、走未知路线、试规则、解谜 | 试构筑、走迷宫、解谜 | 杀戮尖塔、纪念碑谷、塞尔达 |
| A6 | 见证内容 | 看剧情、看角色、看演出 | 走主线 CG、看演出、互动小说 | 乙女游戏、视觉小说、剧情向手游 |
| A7 | 协同执行 | 和真人协调任务、分工执行(非对抗) | 公会副本、SLG 联盟战、固定队 raid | MMO 公会副本、SLG 联盟战、Among Us 协作 |

### 4.1 A 维度填写规则

- `a_main`:A1-A7 中选 1 个,必填
- `a_secondary`:其他次要 A,数组,选填(0-3 个)。**字段命名 2026-05-15 修订(P0-2),原 `a_others` 改为 `a_secondary`,语义不变**

### 4.2 A 真伪判据(2026-05-15 新增,来源:P-1 硬约束 2)

很多产品在素材里展示某些 A(如塔防关 + 内置射击),但玩家进入后这个 A 不再被反复执行。这种 A 是"伪 A",仅为获量素材差异化,**不进 a_main / a_secondary**。

| 类型 | 标志 | 处理 |
|---|---|---|
| **真 A** | 对**留存 / 付费有直接贡献**,玩家进入后**反复执行**这个动作 | 进 a_main 或 a_secondary |
| **伪 A** | 仅为获量素材差异化,玩家进入后**不再或极少**执行这个动作 | 不进 a_main / a_secondary,可在 `acquisition_hooks`(选填)注明 |

**判定方法**:

- 数据法:看 7 日 / 30 日留存用户的核心行为日志,出现频次低于 20% 留存样本 → 伪 A
- 反问法:删掉这个动作,玩家会停玩吗?不会停玩 → 伪 A

立项时**Step 1 必须先做真伪判据**,再决定 a_main / a_secondary。

### 4.3 A 软兼容声明(2026-05-15 新增,来源:P1-7)

A 维度允许任意组合,通过 `a_main` 单选 + `a_secondary` 多选区分主副,**无硬互斥**。1455 样本验证显示所有 A 组合都有大量共现(A2+A5=338,所有 A 对共现 >7),A 之间没有冲突需要排除。

## 章节 5:P 成本与压力

P 描述玩家必须**付出**什么(成本)+ **承受**什么(压力)。两个子维度独立编码。

### 5.1 P-成本(5 个)

玩家必须投入什么资源才能进入核心体验:

| 编号 | 类型 | 描述 |
|---|---|---|
| P-Rxn | 反应力 | 操作手感、即时判断 |
| P-Time | 时间 | 单局时长 / 长期在线 |
| P-Cog | 认知 | 钻研规则、查攻略、推演 |
| P-Soc | 社交 | 必须有真人队友 / 对手 / 熟人局 |
| P-$ | 金钱 | 高 ARPU 才能解锁完整体验 |

### 5.2 P-压力(6 个)

玩家承受什么压力:

| 编号 | 类型 | 描述 |
|---|---|---|
| Pr-Lose | 失败压力 | 失败惩罚强 |
| Pr-Cmp | 比较压力 | 与真人/排名比较 |
| Pr-Rnd | 随机压力 | 不可控运气因素 |
| Pr-Sct | 稀缺压力 | 资源/时间/角色不够 |
| Pr-Spd | 时间限制压力 | 版本压迫、活动限时 |
| Pr-Low | 低压力 | 基本无压力,自我节奏 |

### 5.3 互斥约束

- **Pr-Low 与其他压力互斥**:Pr-Low 表示"没有压力主轴",不能与 Pr-Lose/Cmp/Rnd/Sct/Spd 并存
- 其他压力之间可叠加(如 SLG 同时承受 Pr-Cmp + Pr-Sct + Pr-Spd)
- 成本字段(P-Rxn 等)与压力字段(Pr-Lose 等)在不同子数组,无互斥关系

### 5.4 P 维度填写规则

- `p_cost`:数组,P-Rxn / P-Time / P-Cog / P-Soc / P-$ 中至少 1 个
- `p_pressure`:数组,Pr-Lose / Pr-Cmp / Pr-Rnd / Pr-Sct / Pr-Spd / Pr-Low 中至少 1 个;选 Pr-Low 时其他压力必须为空

### 5.5 P-N 兼容性约束(2026-05-15 新增,来源:P-1 硬约束 5)

P 压力组合会反向排除某些 N 选项。**立项时先定 N → 再选 Pr;Pr 选错反向证伪 N 选择**。

| 主导压力 | 排除的 N | 原因 |
|---|---|---|
| Pr-Lose 主导 | 排除 N-Auto | 失败惩罚强 → 玩家无法自定节奏 |
| Pr-Cmp 主导 | 排除 N-Auto | 与真人比较 → 节奏被他人牵着走 |
| Pr-Rnd 主导 | 排除 N-Auto | 运气主导 → 玩家无法把控 |
| Pr-Sct 主导 | 排除 N-Auto | 资源稀缺压力 → 被迫追赶 |
| Pr-Spd 主导 | 排除 N-Auto | 限时压迫 → 节奏被版本逼迫 |
| Pr-Low 主导 | 排除 N-Comp | 无目标无压力 → 没有"做到"可以验证,无法承接胜任感 |

填字段时:若 `p_pressure` 主导项与 `n_main` 在上表中冲突,要么改 n_main,要么改 p_pressure,**不能并存**。

## 章节 6:F 成功反馈(6 个)

F 描述玩家在"成功瞬间"得到的反馈类型。允许多选,但必须标 1 个主 F。

| 编号 | F 类型 | 反馈本质 | 时间尺度 | 典型游戏 |
|---|---|---|---|---|
| F1 | 击杀反馈 | 即时打击、爆装、命中 | 秒级 | 黑神话:悟空(打击感)、CS(爆头)、咸鱼之王(秒杀爽感) |
| F2 | 数值膨胀 | 数字慢慢涨,看见就有满足 | 分钟-天 | 放置奇兵、咸鱼之王战力涨、刀塔传奇 |
| F3 | 系统涌现 | 多元素跑出意外好结果 | 局内/单次 | Factorio 流水线跑通、杀戮尖塔卡组爆炸、城建 SLG 经济链路 |
| F4 | 闭环达成 | 关卡通过、谜题解开、套装齐 | 单局-单关 | 消消乐过关、纪念碑谷解谜、消除拼图 |
| F5 | 情感见证 | 剧情进展、角色亲密 | 章节-长期 | 乙女游戏、原神角色剧情、视觉小说 |
| F6 | 社交认可 | 排名提升、被点赞、被认同 | 周-赛季 | 王者荣耀排位、SLG 排行榜、抖音点赞 |

### 6.1 F 维度填写规则

- `f_main`:F1-F6 中选 1 个,必填
- `f_secondary`:其他次要 F,数组,选填(0-3 个)。**字段命名 2026-05-15 修订(P0-2),原 `f_others` 改为 `f_secondary`**

### 6.2 F7 不加声明(2026-05-15 新增,来源:P1-8)

F1-F6 已覆盖所有沙盒/创造/建造类游戏的反馈类型(主要走 F3 系统涌现 + F4 闭环达成),**不需要 F7 自由表达**。

数据依据:1455 样本中沙盒/创造类样本 85 个,其中 F3=42% / F4=35%,无 F7 缺口。原"自由表达"承接主要由 N-Auto + F3/F4 组合承担,不需要新增 F 编号。

如未来出现真实样本走 F7 缺口(即 N-Auto + 不是 F3/F4 的反馈类型),再启动 F7 评估。当前不入。

## 章节 7:T 任务态(只引用)

T 任务态描述**用户当下处理的心理任务**,跨人群簇库与玩法承接库共享。

在玩法承接条目里,T 以"**主 T + 副 T 承接列表**"形式出现:

```yaml
t_main: T2                  # 必填,1 个主任务态
t_secondary: [T1]           # 选填,0-2 个副任务态(玩法可同时承接多个任务态)
```

**字段命名 2026-05-15 修订(P0-2)**:原 `t_can_carry` 数组拆为 `t_main` + `t_secondary`,语义上 `t_can_carry[0]` 即 `t_main`,后续元素即 `t_secondary`。

**人群簇 vs 玩法承接库的 T 字段区别**:

| 库 | 字段 | 副 T 数量 | 原因 |
|---|---|---|---|
| 人群簇库 v1.2 | `T_main` + `T_secondary` | 0-1 个 | 簇是用户聚类,任务态过多即说明聚类不稳 |
| 玩法承接库 v1.1 | `t_main` + `t_secondary` | 0-2 个 | 玩法可同时承接多个任务态(如动作 RPG 同时承接 T2/T1/T5) |

**T 的完整定义不在本文档**,见 [06-基础维度定义.md](06-基础维度定义.md)。

简要提示:
- T 与 N 解耦,一个 N 可服务多个 T,一个 T 可由多个 N 承接
- 玩法承接的 `t_main + t_secondary` 表达"这个玩法可以服务于哪些用户任务态"
- 人群簇通过 `T_main` 字段表达"该簇用户当下主要处理什么任务态"
- 玩法选型时,人群簇的 T_main 应在玩法承接的 `t_main` 或 `t_secondary` 中

## 章节 8:玩法分析方法(SOP)

本章节是"用 v1.1 框架分析一个具体游戏 / 一个玩法想法"的标准操作步骤。

**输入**:一个游戏(或一个玩法构想)
**输出**:它的 `a_main / a_others / p_cost / p_pressure / f_main / f_others / n_main / n_others / rel_object / t_can_carry / confidence`

### Step 1:找出反复行为 A

**主问题清单**(挨个问):
- 玩家每天打开游戏先做什么?
- 玩家每局/每节点绕不开的核心动作是什么?
- 删掉哪个动作,玩家就不玩了?

按答案落到 A1-A7。**剩下的次要动作进 `a_others`**。

### Step 2:找出成本与压力 P

**P-成本判断问题**:
- 操作手感重要吗 → P-Rxn
- 需要长时间投入吗 → P-Time
- 需要思考钻研吗 → P-Cog
- 必须有真人队友/对手吗 → P-Soc
- 高付费才能进核心体验吗 → P-$

**P-压力判断问题**:
- 失败惩罚强吗 → Pr-Lose
- 跟别人比较吗 → Pr-Cmp
- 运气主导吗 → Pr-Rnd
- 资源/时间稀缺吗 → Pr-Sct
- 限时压迫吗 → Pr-Spd
- 基本无压力吗 → Pr-Low(选这个就不能选其他压力)

### Step 3:找出成功反馈 F

问:**玩家成功的那一刻,看到/听到/感觉到什么?**

按答案落到 F1-F6。注意区分:
- 屏幕特效、击杀提示 → F1
- 数值面板上涨、战力涨 → F2
- 系统跑出意外好结果 → F3
- 关卡 / 谜题 / 套装的"完成"提示 → F4
- 剧情推进、角色互动 → F5
- 排名、点赞、社交可见的认可 → F6

### Step 4:推出基本心理需求 N(SDT 三需求)

**三需求判断核心问题**:
- 这游戏有强目标 + 失败/比较压力,玩家投入是为了证明"我能行/我变强" → N-Comp
- 这游戏 Pr-Low 主导 + 没有强目标,玩家自定节奏 → N-Auto
- 这游戏的主驱动是和某个对象(虚拟角色/真人)的关系 → N-Rel

**退出感受判据**(B-A 同款,放这里复述):
- 玩家退出时本能反应是"下次能更强 / 能解锁更多" → N-Comp
- 玩家退出时本能反应是"玩爽了 / 可以收工" → N-Auto
- 玩家退出时本能反应是"想念那个人/那个组织/那段关系" → N-Rel

### Step 5:推出可承接 T 列表

问 2 个问题:
1. **用户长期留下来在处理什么任务?** → 主 T(进 `t_can_carry[0]`)
2. **这个玩法还能承接哪些其他任务态?** → 次要 T(进 `t_can_carry[1..]`,0-2 个)

举例:
- 动作 RPG:主 T2(确认变强),也承接 T1(打怪释放压力) → `t_can_carry: [T2, T1]`
- SLG:主 T4(在联盟有位置),也承接 T6(经营自己的城市) → `t_can_carry: [T4, T6]`

### Step 6:输出置信度

| 置信度 | 标准 |
|---|---|
| `high` | A/P/F/N 一致,核心反复行为清晰,N 与 F/P 强相关 |
| `medium` | A 清晰但 N 在两个候选间略有摇摆 |
| `low` | A 不清晰,或 N 在多个候选间摇摆 |

### Step 7:卡关时的处理

如果某一步纠结,使用"本能反应判据"兜底:

- A 纠结:**删掉一个候选 A,玩家会不会停玩?会停玩的那个 → 主 A**
- N 纠结:**问玩家"为什么留下来"。回答以"我变强/我能行"为主 → N-Comp;以"我想干嘛干嘛"为主 → N-Auto;以"和谁谁谁"为主 → N-Rel**
- T 纠结:**问"长期留存的用户在解决什么问题"**

仍然摇摆时,标 `confidence: low / medium` + `boundary_excluded` 字段写明排除的最相邻候选及理由。

## 章节 9:易混判据(boundary)

### 9.1 N 维度易混

| 易混对 | 关键判据 | 典型反例 |
|---|---|---|
| B-A:N-Comp vs N-Auto | 有目标 + 压力 → N-Comp;无强目标 + Pr-Low → N-Auto | 消消乐有目标版 → N-Comp;消消乐随便玩版 → N-Auto |
| B-B:N-Comp vs N-Rel | F1/F2/F3/F4 主反馈 → N-Comp;F5/F6 主反馈 → N-Rel | 王者荣耀(F1+F6 但驱动是上分)→ N-Comp;MMO 公会(F6 但驱动是归属)→ N-Rel |
| B-C:N-Auto vs N-Rel | 无压力但独自玩 → N-Auto;无压力但和别人玩 → N-Rel(rel_object 必填) | 动森独自装修 → N-Auto;动森串门访问 → N-Rel |
| B-D:N-Auto vs N-Rel(叙事 NPC 场景) | 开放叙事 + Pr-Low,玩家是**观察 / 选择者**,NPC 是世界元素 → N-Auto;**固定 NPC 同伴 + 回访关系**(有特定对象认知)→ N-Rel | Disco Elysium 的"自我对话/世界观察"→ N-Auto;尼尔:自动人形的 9S 同伴 → N-Rel(rel_object=virtual)|

**B-B 副条:F4+F5 共存时的剥离测试**(2026-05-15 新增,来源:P0-8)

当 `f_main=F4 闭环达成` 与 `f_secondary 含 F5 情感见证` 共存时(典型 RPG / 剧情向通关游戏),N 归属容易在 N-Comp 与 N-Rel 之间摇摆。1455 样本里 F4+F5 共存对摇摆 98 次,是 N 维度最高频的歧义场景。

**剥离测试**:问"剥离哪一个,玩家仍坚持玩"?

| 剥离对象 | 玩家行为 | N 归属 |
|---|---|---|
| 弃叙事(只剩 F4 通关) | 仍坚持玩 | N-Comp 主(F4 是主驱动,F5 是包装) |
| 弃通关 / 数值(只剩 F5 见证) | 仍坚持玩 | N-Rel 主(F5 是主驱动,F4 是节奏) |
| 两者剥离都玩不下去 | 走 N-Comp 主 + n_secondary 含 N-Rel,在 `boundary_excluded` 注明剥离测试不收敛 | 复合承接 |

数据方法:看"纯通关向"和"纯剧情向"两类用户在 7 日 / 30 日留存的占比和付费;占比高的那一边是主驱动。

**B-D 副条:N-Auto vs N-Rel 在叙事场景的判据**(2026-05-15 新增,来源:P1-1)

开放叙事 + Pr-Low 是 N-Auto / N-Rel 的高频摇摆区(1455 样本里 37 个 medium 置信样本落此区)。区分判据:

- **玩家是观察者 / 选择者,NPC 是世界元素的一部分** → N-Auto(玩家的"自由选择"是主驱动)
- **存在固定 NPC 同伴 + 回访关系机制**(用户对特定对象有持续认知和情感投射) → N-Rel
- **自我对话 / 世界观看类**(Disco Elysium 的内心对话、Pathologic 的世界观察)算 **N-Auto**,因为"对象"是玩家自己的认知与世界本身,不是某个特定 NPC

## 章节 11:与人群簇库的接口

### 11.1 引用方向

```
玩法承接库(本库,上游)
   ↓ 提供 A / F / N 定义
人群簇库(下游)通过 AF_ref 单向引用
```

**禁止反向**:人群簇库不得自造 A/F/N,如有缺口反向推动本库增补。

### 11.2 人群簇引用本库的字段

人群簇 v1.2 的 `AF_ref` 字段示例:

```yaml
AF_ref:
  A: [A2, A3]        # 来自本库 A 枚举
  F: [F1, F2]        # 来自本库 F 枚举
P_hint:
  cost: [P-Time]     # 来自本库 P-成本枚举(可选,辅助理解)
  pressure: [Pr-Lose] # 来自本库 P-压力枚举
```

人群簇的 `primary_N` / `secondary_N` 也直接引用本库 N 枚举。

### 11.3 玩法承接条目不再持有 audience_ids

v1 中,玩法承接条目持有 `audience_ids` 反查人群簇。v1.1 取消该字段,原因:

- 玩法承接是上游枚举,**不应感知下游引用**,否则改一个玩法要回写所有人群簇
- 人群簇通过 `AF_ref` 单向声明引用关系即可
- 题材关联也由人群簇层承担(`THM_ref`),不再由玩法持有

如需"哪些人群簇引用了 PLY-XXX-001",做反向索引脚本生成,不写进玩法条目字段。

## 章节 12:与 v1 标准的迁移指南

### 12.1 v1 的"独立性五问"在 v1.1 的位置

| v1 问题 | v1.1 中的承接位置 |
|---|---|
| 1. 成功案例验证(能否独立做成功) | 仍然有效,作为**新增玩法承接条目的必检项**,体现在 `evidence_grade` ≥ B + `representative_games` ≥ 3 |
| 2. 操作冲突检验 | 现在通过 **A 互斥**判断(如 A1 真人对抗与 A4 系统调整在同时长强度下互斥)。具体互斥关系在 `boundary_excluded` 或外部组合规则文档中维护 |
| 3. 时间分离检验 | 现在通过 **LT 时间结构**承担(玩法的 `representative_games` 字段中样本案例自然体现,以及 `core_systems` 字段拆解局内/局外节奏) |
| 4. 成果体现检验 | 现在通过 **F 维度**承担(成功反馈的形式即"成果如何体现") |
| 5. 深度检验 | 现在通过 **evidence_grade** + 长线代表游戏数量承担 |

### 12.2 v1 大类代码(TD/RPG/SLG/...)在 v1.1 的位置

v1.1 不再使用品类大类作为玩法承接的骨架,但允许在 `playstyle_id` 命名中保留品类前缀作为人类可读的索引(如 `PLY-TD-001`),不参与机器分类。

实质分类靠 `(a_main, f_main, n_main)` 三元组,品类前缀仅作命名习惯保留。

### 12.3 v1 → v1.1 迁移操作步骤

对每个 v1 已有条目:

1. 保留 `id`、`name`、`representative_games`、`evidence_grade`(原 `evidence_level`)
2. 按章节 8 的 SOP,补出 `a_main / a_others / p_cost / p_pressure / f_main / f_others / n_main / n_others / rel_object / t_can_carry / confidence`
3. 删除 `category`、`core_loop`、`independence_check`、`audience_ids`、`theme_motif_ids`(或保留为注释字段供历史追溯)
4. `boundary_excluded` 字段填写最相邻的 N/A/F 排除理由
5. 标 `status: draft` 直到至少 3 个真实样本验证一致

迁移完成且本库整体校验通过后,v1 文档归档,v1.1 升格为执行标准。
