# 机制拆解质量标准

定位：机制库拆解的日常验收标准。  
原则：主标准只判断“能不能过”，案例、反例和解释放到案例库或复盘文档。  
适用：游戏机制拆解三阶段输出，包括系统全景、结构循环、模块拆解和结论提炼。

---

## 核心原则

一篇合格拆解必须同时满足两件事：

1. 没玩过这个游戏的人，能凭文档重现机制的行为。
2. 做另一个游戏的设计者，能从文档中提取可操作约束。

---

## 阶段一：系统穷举

目标：确认“有什么”，不提前判断重要性。

验收判据：

- 六维度全覆盖：核心玩法、成长养成、经济系统、社交多人、赛季活动、商业化。
- 每个维度必须写明：有系统、确认无系统、或未确认。
- “确认无”和“未确认”必须分开；没查到不能写成无。
- 每个事实必须标注来源：第一手、具体二手来源、或推断。
- 推断项必须写出推断依据。

不通过条件：

- 任一维度空白。
- 来源写成“攻略/玩家反馈/官方介绍”等模糊标签。
- 把机制库未收录当成游戏不存在该系统。

---

## 阶段二：结构与循环

目标：确认“系统之间如何连起来”。

验收判据：

- 阶段一列出的系统必须全部映射到结构图或结构表。
- 每条行为循环必须闭合：行为输入、过程、产出、消耗或反馈都要有去向。
- 每条资源循环必须闭合：来源、存量、消耗、回收或清理都要写明。
- 系统接口必须写清传递内容：资源、状态、行为触发、权限、数值或目标。
- 结构关系必须标注置信度：confirmed、inferred、unknown。

不通过条件：

- 只画核心玩法，成长、经济、社交或商业化系统从结构中消失。
- 只写“有关联”，不写传递了什么。
- 出现只有产出没有消耗、只有消耗没有来源的悬空资源。

---

## 阶段三：目的与设计思路

目标：确认“为什么这样设计，以及换一个项目时能学到什么”。

验收判据：

- 关键机制必须可重现：触发条件、执行过程、结果反馈写清楚。
- 模块必须有边界：负责什么、不负责什么，与相邻模块怎么区分。
- 分类必须有识别标准：拿一个具体元素时能判断它属于哪一类。
- 关键机制必须回答“为什么存在”：删掉后系统哪里会坏。
- 关键机制必须区分三层：上层设计目的、中层机制手段、下层实现项。
- 不得把机制手段或实现项直接写成设计目的，例如赛季、体力、商店、排行榜、重置。
- 关键设计必须写失效条件：过强、过弱、缺失时分别坏在哪里。
- 产出必须写资源职责：来源、消耗、服务对象、解决的设计问题。
- 玩家分层必须写参与入口、门槛、收益上限和被排除风险。
- 验证指标必须对应设计目的，不能只列总活跃、总参与等泛指标。
- 可迁移结论必须写适用前提和判断标准，不强制写成 If-Then。

不通过条件：

- 只写机制做什么，不写为什么存在。
- 只列奖励，不解释资源职责。
- 只按战力分层，不写时间、操作、资源、组织、认知等门槛。
- 把赛季、商店、体力、排行榜等机制名本身当成目的。
- 结论只对当前游戏成立，或宽到适用于所有游戏。

---

## 交付表达要求：内部分析脚手架不得外露

目标：交付给人的机制拆解文档必须呈现核心结论和逻辑，不把 AI 或作者内部使用的分析维度直接暴露成标题、标签或列表项。

验收判据：

- 可以在分析过程中使用拆解维度，但最终交付必须改写成自然结论段落。
- 标题、独占粗体、冒号标签、无序列表标签、编号列表标签不得直接使用内部分析脚手架。
- 同义换词后的短标签也不得外露，例如把“断点风险”换成“承接风险”仍属于脚手架外露。
- 正常编号章节可以保留，例如“九、当前风险”；但章节下的内容必须是结论和逻辑，而不是维度填空。

不通过条件：

- 直接出现“设计目的 / 机制手段 / 资源状态 / 社交状态 / 与前后日接口 / 断点风险 / 修正方向”等标签式结构。
- 把换词后的短维度标签作为标题或列表项，例如“承接关系 / 风险点 / 问题定位 / 改进方向”。
- 文档看起来像把内部检查表展开，而不是给出可读的判断链。

修正方式：

- 把标签删掉，改成一句核心判断。
- 后续内容按因果链展开：为什么成立、影响什么、如果缺失会断在哪里。
- 保留必要的结构，但结构名应服务读者理解，而不是暴露分析表字段。

## 跨阶段验收

- 标记为深拆的系统，必须有对应模块文件。
- 标记为不深拆的系统，至少要在结构图中有位置和不深拆理由。
- 总档必须包含三部分：系统全景、系统总览、总判断。
- 所有 inferred 结论必须能追溯到事实依据。
- 资料未覆盖的内容必须标注，不得补成确定规则。

## 快速自检

阶段一：

- [ ] 六维度都有结论？
- [ ] 无、未确认、推断分清？
- [ ] 每个事实有来源？

阶段二：

- [ ] 阶段一系统全部进入结构？
- [ ] 行为循环和资源循环闭合？
- [ ] 接口写清传递内容？
- [ ] 推断关系有置信度？

阶段三：

- [ ] 机制可重现？
- [ ] 模块边界清楚？
- [ ] 目的、手段、实现项分层？
- [ ] 产出写清资源职责？
- [ ] 玩家分层写清门槛和收益？
- [ ] 失效条件明确？
- [ ] 验证指标对应设计目的？
- [ ] 结论有适用前提和判断标准？
