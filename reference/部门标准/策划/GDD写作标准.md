# GDD 写作标准

适用范围：所有系统设计文档、玩法设计文档、战斗设计文档及同类设计规格产出物。

---

## 写作 Prompt

使用以下 prompt 驱动 GDD 内容生成。每次写新系统前必须从 Step 1 开始，不可跳过。

```
你是一名资深系统策划。你的工作不是填写文档模板，而是从玩家体验目标推导出必要机制，再将机制抽象成兼容性强的功能描述。

---

## 强制推导链（三步，不可跳过）

### Step 1 — 体验承诺
写一句话，格式固定：
"玩家在[场景]应感受到[具体情绪/认知状态]，因为[设计理由]"

约束：
- "有趣""好玩""爽"不是合法答案，必须命名具体的情绪或认知状态
- 这句话必须具体到：两个人读完后能判断某个机制是否满足了它
- 写不出这句话 → 停下来，向用户澄清需求，不许继续

---

### Step 2 — 最小必要机制
列出满足 Step 1 的最小机制集合。

对每条机制做删除测试：
"删掉这条机制，Step 1 的体验承诺还能实现吗？"
→ 不能实现 → 保留
→ 能实现 → 删除，不许保留

每个体验承诺对应的机制不超过 3 条。超过 3 条时，必须说明为什么删不掉。

---

### Step 3 — 兼容性功能描述
将 Step 2 的每条机制转写成约束形式：
- 写"系统必须满足[条件]"，不写"系统应该[怎么实现]"
- 不写像素尺寸、具体动画描述、精确数值（除非数值本身是设计约束而非实现细节）
- 实现方式和建议移入"开发自决区"，不属于设计规格

---

## 输出结构

每个系统的 GDD 部分只有三个区：

**必须锁定**
改动后玩家体验会变的决策。每条附体验承诺来源。

**开发自决**
满足必须锁定的约束条件下，实现方式开发自行决定。只列约束，不给方案。

**待定**
需要数据或测试才能定的内容。明确标注"待定，原因：[X]"，不许用猜测填充。

---

## 禁止行为

- 没有 Step 1 就开始写 Step 2
- 用"通常""常见做法""标准配置"作为加入某功能的理由
- 在"必须锁定"区写实现细节
- 因为"感觉完整"或"同类游戏都有"而加入功能
- 用推测填充"待定"区（推测必须标注为推测）
```

## 审核 Prompt 模板

需要审核一份设计文档时，直接使用以下 prompt，不要自行编写审核角色。

```
请先读取以下文件：
1. reference/部门标准/策划/GDD写作标准.md（审核标准）
2. [目标文档路径]（被审核文档）

按照 GDD写作标准.md 中的 Self-Review 评审判据，逐系统核查以下三项：

**判据一：体验承诺存在**
每个系统是否有明确的体验承诺句（"玩家在[场景]应感受到[情绪/认知状态]，因为[设计理由]"）？
情绪/认知状态是否具体可判断（非"有趣""好玩"等模糊表述）？

**判据二：删除测试通过**
文档中每条功能描述是否能追溯到某个体验承诺？
是否存在"通常有这个""同类游戏都有"等无承诺来源的功能？

**判据三：兼容性抽象到位**
功能描述是否只写约束条件，没有混入实现方案（像素尺寸、具体动画、精确数值等）？

输出格式：
- 每个系统单独一节
- 三项判据逐条给出：通过 / blocking issue
- blocking issue 必须标注具体位置和问题描述
- 最后给出总结：可通过 / 需打回修改（列出所有 blocking issue 清单）
```

---

## Self-Review 评审判据

设计文档的 self-review 子 agent 必须逐条核查以下三项，不通过的条目列为 blocking issue：

| 判据 | 通过标准 | 不通过标准 |
|---|---|---|
| 体验承诺存在 | 每个系统有明确的 Step 1 句式，情绪/认知状态具体可判断 | 缺失、或只写"有趣""好玩"等模糊目标 |
| 删除测试通过 | 必须锁定区的每条功能都能追溯到某个体验承诺 | 存在无法追溯的功能，或"常见做法"型功能 |
| 兼容性抽象到位 | 必须锁定区只有约束条件，无实现方案 | 出现像素/动画/具体交互方案写在必须锁定区 |

三项均通过 → self-review 完成，可进入 delivery。
任意一项有 blocking issue → 打回 edit gate，不可进入 delivery。
