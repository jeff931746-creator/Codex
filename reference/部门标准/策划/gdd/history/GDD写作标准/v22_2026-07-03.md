# GDD 写作标准

适用范围：需求 GDD、功能需求规格文档及同类策划产出。

## 一、标准定位

GDD 是设计层文档，只回答三件事：

1. 为什么做：解决什么问题，想改变什么玩家行为、系统状态或上下游关系。
2. 做什么：玩家做什么，系统判断什么，结果如何结算，状态如何变化，玩家看到什么。
3. 不做什么：不写工程实现方案。

GDD 正文必须从需求和场景出发，按设计对象描述功能。规则、边界、异常和配置跟随对应设计对象，不单独漂成规则清单。

## 二、设计层边界

**GDD 写：**

- 功能行为与必要交互。
- 玩家可见的系统响应，包含异常、离线、失败、未满足条件时看到什么。
- 功能描述中的规则约束、状态变化和结算结果。
- 与其他系统的功能级契约：委托给谁、传入什么意图或数据类别、期望什么结果、异常时功能上如何兜底。

**GDD 不写：**

- 事务、锁、并发、幂等、防重复。
- 重试次数、补发队列、补偿流程。
- 日志、监控、埋点。
- 接口字段、数据结构、协议、存储、缓存。

判断口径：回答“玩家 / 系统在功能上发生什么”就写进 GDD；回答“工程上怎么保证它发生”就移出 GDD。

## 三、必备结构

每份需求 GDD 必须包含：

1. **需求目的**：只写目标状态，不写实现手段。每条目标必须能判断是否达成。
2. **需求概述**：用 1-3 句话说明功能是什么、范围是什么、主要限制是什么。
3. **脑图 / 流程图**：展示主要设计对象、关系、流转和关键分支。只有文字列表不通过。
4. **主体设计描述**：按设计对象写功能、规则、状态、反馈和边界。
5. **交互流程**：交互型内容必须写玩家操作和系统响应，有分支时逐一说明。

按需补充：

- **配置项**：仅列策划可配置参数，必须写生效范围。
- **UE 交互**：当界面入口、按钮、弹窗、页面流转与功能逻辑强绑定时补充。
- **内容配置区**：只能在功能描述完成后追加，不能承载系统规则。
- **待定区**：只放需要数据或测试才能确定的内容，格式为“待定，原因：[X]”。

## 四、设计对象写法

正文先判定设计对象，再决定章节。不要先套章节，再把内容塞进去。

常见设计对象包括：完整系统、玩法、玩法内功能、积分 / 资源规则、角色分层、反馈页面、技能 / 单位 / 道具方案。

一个内容能独立成章，必须有明确功能职责，并能说明以下关键项中的主要部分：

- 玩家入口或触发场景。
- 系统判断。
- 状态变化或结算结果。
- 玩家可见反馈。
- 与前置或后续玩法的关系。

以下内容不能单独伪装成模块，只能挂到所属规则或功能描述中：

- 计分维度。
- 成员类型。
- 状态枚举。
- 展示字段。
- 待确认项。
- 零散规则条目。

每个一级章节先写“本章解决什么问题”，再写：

1. 包含哪些对象、途径或状态。
2. 每个对象的定位。
3. 系统如何判断。
4. 结果如何结算或状态如何变化。
5. 玩家看到什么反馈。
6. 边界和异常是什么。

## 五、正文规则

功能描述用自然文字写清：这个设计对象是什么、在什么场景下发生、系统产生什么结果、对玩家或上下游功能造成什么影响。

规则正文优先写：

- 玩家做什么。
- 系统判断什么。
- 结果怎么结算。
- 状态怎么变化。
- 玩家看到什么。

规则约束必须写清触发条件和系统行为。不要只写“胜利后结算”“满足条件后发奖”，而不定义胜利、条件和发奖结果。

分类信息必须挂靠到所属规则：

- 成员分层 -> 挂到参与差异或积分获取。
- 积分来源 -> 挂到积分获取。
- 展示字段 -> 挂到排行与反馈。
- 待确认项 -> 挂到对应段落或待定区。
- 规则条目 -> 挂到对应功能描述。

解释性内容不能替代正文。设计推导、正反例、审核解释、AI 思考过程只用于协作沟通，不进入 GDD 主体。

## 六、配置项

有可配置参数时使用下表；不可配置内容不列入配置项。

| 配置项 | 生效范围 | 默认值 | 可配置范围 | 说明 |
|---|---|---|---|---|
| [配置项名称] | 全局 / 实例 / 其他 | [默认值] | [范围] | [说明] |

生效范围口径：

- `全局`：整个游戏共用一个值。
- `实例`：每个关卡、商店、事件等可独立设置。
- `其他`：难度档、玩家组、阶段等，需在说明列写清。

## 七、协作与纠偏

结构有争议时，先输出结构草案和判断，不直接改文档：

```md
建议结构：
一、...
二、...

结构判断：
- XXX 能成章，因为...
- XXX 不能成章，只能并入...
- XXX 是分类，不是模块...
```

发现质量问题时先归因，再修改：

- 设计对象判定错。
- 模块被分类信息替代。
- 正文写成解释文。
- 流程产物混进正文。
- 章节层级错。
- 技术实现写进设计文档。

## 八、Self-Review

评审纪律遵守 `.agents/rules/quality-gates.md`：评质量，不只评存在；先看单项是否成立，再看整体结构是否协调。

| 判据 | 通过标准 | 打回标准 |
|---|---|---|
| 需求目的 | 目标清晰、可验证，只写目标状态 | 只说做功能；目标含糊；把实现手段写成目的 |
| 结构图 | 覆盖主要设计对象、关系、流转和分支 | 缺失；只有文字列表；看不出对象关系 |
| 章节职责 | 每个一级章节有功能职责，分类信息挂靠到所属规则 | 计分维度、成员类型、状态枚举、字段或待确认项被拆成独立模块 |
| 功能正文 | 写清场景、系统判断、结算结果、状态变化、玩家反馈和上下游影响 | 只有标题、字段、配置表或解释文字，无法支持开发和验收 |
| 交互流程 | 交互型内容有完整操作和系统响应，分支条件明确 | 缺流程；状态变化自引用；条件和结果不清 |
| 配置项 | 只列可配置参数，并声明生效范围 | 配置项替代功能描述；未写生效范围 |
| 设计层边界 | 只写功能行为、玩家可见响应和功能级契约 | 写入事务、锁、重试、日志、接口字段、存储等技术实现 |

需求目的、结构图、章节职责、功能正文、设计层边界必须通过；涉及交互、配置、内容配置时，对应判据也必须通过。任一适用判据出现打回标准，不可交付。
