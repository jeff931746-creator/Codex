# GDD 写作标准

适用范围：需求 GDD、功能需求规格文档及同类策划产出。

## 1. 核心原则

GDD 只写设计层：玩家做什么、系统判断什么、结果如何结算、状态如何变化、玩家看到什么反馈。

不写技术实现、接口字段、数据结构、日志、埋点、补偿队列、并发锁、数据存储。

涉及其他系统时，只写功能级契约：委托给谁、传入什么意图或数据类别、期望什么结果、异常时功能上如何兜底。

规则必须跟着功能场景走，不单独堆成“规则清单”。

解释、推导、正反例、AI 思考过程只能用于协作沟通，不能替代 GDD 正文。

## 2. 写作前判断设计对象

写正文前先判断当前对象是：

- 完整系统
- 单个玩法
- 玩法内功能
- 积分 / 资源规则
- 角色分层
- 反馈页面
- 技能 / 单位 / 道具方案

未判断对象类型前，不给章节结构。

结构有争议时，先给“建议结构 + 结构判断”，确认后再改文档。

## 3. 章节成立标准

一级章节必须承担功能职责。

能成章的内容，至少要说明：

- 玩家入口或触发场景
- 系统判断
- 状态变化或结算结果
- 玩家可见反馈
- 与前后玩法的关系

不能成章的内容：

- 计分维度
- 成员类型
- 状态枚举
- 展示字段
- 待确认项
- 配置项
- 规则条目

这些内容必须挂靠到所属功能或规则下。

## 4. 正文写作顺序

每章按以下顺序写：

1. 本章解决什么问题
2. 包含哪些对象 / 途径 / 状态
3. 每个对象的定位
4. 系统如何判断
5. 结果如何结算或状态如何变化
6. 玩家看到什么反馈
7. 边界和异常是什么

不要一上来解释概念，也不要把设计推导写成正文。

## 5. 规则表达要求

规则必须写清：

- 触发条件
- 系统判断
- 结算结果
- 状态变化
- 玩家反馈
- 无效或异常情况

交互型内容必须写玩家操作和系统响应；有分支时逐一说明。

状态变化不能自引用。不要只写“胜利后结算”，必须定义胜利条件和结算结果。

## 6. 交付检查

每份 GDD 必须包含：

- 需求目的：只写目标状态，不写实现手段；每条目标必须可验证。
- 需求概述：用 1-3 句话说明功能是什么、范围是什么、主要限制是什么。
- 脑图 / 流程图：展示主要设计对象、关系、流转和关键分支；只有文字列表不通过。
- 主体设计：按设计对象写功能、规则、状态、反馈和边界。

按需补充：

- 交互流程：有连续操作、页面跳转、按钮反馈时必须写。
- 配置项：只列策划可配置参数，必须写生效范围。
- UE 交互：界面入口、按钮、弹窗、页面流转与功能逻辑强绑定时写。
- 内容配置区：只能在功能描述完成后追加，不能承载系统规则。
- 待定区：只放需要数据或测试才能确定的内容，写明“待定，原因：[X]”。

禁止行为：

- 没有需求目的就写功能。
- 没有判断设计对象就套模板。
- 把分类、字段、枚举、待确认项拆成一级章节。
- 只有配置表，没有功能描述。
- 用解释、推导、正反例替代 GDD 正文。
- 写入技术实现、接口字段、日志、埋点、补偿、并发等开发内容。
- 使用自创抽象词替代玩家可见行为。
- 配置项不写生效范围。
- 内容配置表出现在功能描述之前。

交付前只检查 7 件事：

1. 需求目的是否可验证。
2. 设计对象是否已判定。
3. 一级章节是否都有功能职责。
4. 分类、字段、枚举、配置项是否挂靠到所属规则。
5. 规则是否写清触发、判断、结算、状态、反馈和异常。
6. 交互型内容是否写清操作、响应和分支。
7. 是否混入技术实现或解释性正文。

任一项不通过，打回修改，不交付。
