# GDD 写作标准

适用范围：需求 GDD、功能需求规格文档及同类策划产出。

## 1. 核心原则

GDD 只写设计层：玩家做什么、系统判断什么、结果如何结算、状态如何变化、玩家看到什么反馈。

不写技术实现、接口字段、数据结构、日志、埋点、补偿队列、并发锁、数据存储。

涉及其他系统时，只写功能级契约：委托给谁、传入什么意图或数据类别、期望什么结果、异常时功能上如何兜底。

规则必须跟着功能场景走，不单独堆成“规则清单”。

解释、推导、正反例、AI 思考过程只能用于协作沟通，不能替代 GDD 正文。

## 2. 写作前分层与转译

写正文前必须先把材料分成四层：

- 玩法目的层：功能要在游戏里形成的关系、状态或结果，例如竞争关系、成长目标、协作关系、资源价值、身份变化、长期承接。
- 设计对象层：本文真正设计的功能对象、玩法对象、系统对象或规则对象。
- 交付对象层：设计对象内部需要落地的对象、规则、统计、展示、结算、配置、状态、奖励或调用关系。
- 正文结构层：正文实际组织给开发、UE、数值、测试阅读和实现的结构。

玩法目的层决定需求目的。交付对象和正文结构不能反推需求目的。

设计推演层材料可以用于判断方向，但不能直接生成 GDD 正文目录。正文目录必须先经过结构依据判定和交付结构转译。

写作前必须先按以下顺序确认：

```text
玩法目的 -> 设计对象 -> 交付对象 -> 正文结构
```

禁止跳过玩法目的，直接从页面、统计、计分、配置、展示、归属、互斥、结算等交付对象倒推需求目的。

### 2.1 玩法目的

玩法目的回答“为什么需要这个功能”，只写功能要在游戏里形成什么关系、状态或结果。

玩法目的可以包括：

- 玩家、队伍、军团、组织或系统之间形成的关系。
- 排名、胜负、成长、协作、交易、争夺、身份、资源价值等目标状态。
- 成员行为、资源流转、关系变化与上级玩法之间建立的结果关联。
- 当前周期结果对后续玩法、长期系统或生态目标的承接。

玩法目的不能写成交付手段。以下内容不能直接作为需求目的：

- 建立统计对象、接入事件、来源归属、互斥口径。
- 积分计算、字段、配置、展示页、排行页、奖励表、结算口径。
- 页面入口、按钮、任务池、状态枚举、打点指标。
- “让玩家点击 / 查看 / 进入 / 完成”等过程行为。

需求目的只能来自玩法目的层。需求概述和主体设计再说明功能是什么、如何交付。

### 2.2 设计对象与边界

- 边界是什么：从哪里开始，到哪里结束。
- 服务哪个上级目标、玩法或系统。
- 自身是否承担完整设计职责。
- 下属信息是功能、规则、分类、字段还是配置。
- 应独立成章，还是挂靠到上级功能或规则。

同时必须判断本次 GDD 最终在定义什么对象、变化或结果：

- 该对象是否能承载玩法目的、贯穿主要规则并产生玩家可感知结果。
- 哪些材料只是设计推演词、体验判断或策略取舍，不能直接成为正文标题。
- 哪些材料只是交付对象，不能反推为需求目的或最高设计对象。

### 2.3 交付对象判定

设计对象确认后，必须拆出交付对象。交付对象是正文需要落地的对象、规则、统计、展示、结算、配置、状态或调用关系。

交付对象可以进入主体设计，但不能直接写进需求目的。常见交付对象包括：

- 统计对象、积分账户、贡献记录、排行对象。
- 来源、归属、互斥、结算、领取、状态、资格。
- 页面、反馈、提示、配置项、奖励表、内容项、调用场景。

交付对象必须说明它服务哪个设计对象，以及在正文中承担实现、配置、展示、结算或验证职责。

### 2.4 结构依据判定

写正文前必须判断本文档应该按什么结构依据组织。结构依据不是固定模板，而是这篇 GDD 最适合被交付阅读的组织方式。

常见结构依据包括但不限于：

- 赛程、阶段、玩法节点。
- 对象构成、生成、变化、消耗、调用。
- 资源流转、积分汇总、排名结算、奖励领取。
- 状态变化、资格变化、关系变化。
- 操作流程、页面流程、功能调用场景。

结构依据必须来自交付对象如何生成、变化、配置、展示、结算或验收，不能来自设计意图、体验强度、卖点归纳或策略标签。

### 2.5 交付结构转译

完成结构依据判定后，必须把设计推演材料转译到交付结构中：

- 设计意图只解释为什么这样设计，不决定一级目录。
- 体验判断只作为对应规则、表现或验收关注点，不独立成章。
- 玩法目的只进入需求目的或必要的概述说明，不直接拆成主体章节。
- 页面、配置、奖励表、状态枚举、打点指标或局部规则，只能归位到其实际生效的交付结构节点。
- 转译后的主体章节必须让开发、UE、数值或测试知道要实现、配置、展示、结算或验证什么。

未完成对象判定前，不给章节结构。

未完成玩法目的、设计对象、交付对象、结构依据判定和交付结构转译前，不生成正文目录。

结构有争议时，先给“建议结构 + 结构判断”，确认后再改文档。

## 3. 章节成立标准

一级章节必须来自已确认的交付结构，不是资料分类，也不是设计推演词的展开。

能独立成章，必须能说明它在交付结构中承担什么职责：实现什么对象、规则、状态、计算、结算、展示或调用关系。

一级章节标题不能只写抽象结构、设计目的、体验特征、风险强度、收益感知或策略卖点，必须落到可交付内容。可交付内容包括但不限于：

- 入口与参与规则。
- 目标、任务、进度、资格、状态或关系规则。
- 生成、随机、计算、结算或分配规则。
- 排名、展示、反馈、领取或异常处理。
- 功能级调用关系。

配置项生效范围、内容配置、字段、参数和表格只能作为上述设计对象内的交付内容，不能单独作为一级主体章节。

章节内应根据内容需要写清：

- 入口：玩家从哪里进入，或由什么场景触发。
- 判断：系统根据什么条件判定。
- 变化：结果如何结算，状态如何变化。
- 反馈：玩家看到什么。
- 关系：它承接什么前置内容，又影响什么后续内容。

对于对象构成、生成规则、数值计算、套装/词条、调用场景等非连续流程内容，可以用“适用对象、生成/计算规则、结果影响、展示或调用关系”替代入口/操作链路。

不能说明其关键职责、结果影响和上下游关系的内容，不单独成章。

只表达“为什么要这样做”的章节，不是主体设计章节；必须先转译到本文档的交付结构，再写成玩家、系统或配置层实际发生的内容。

附属信息只能挂靠到所属功能或规则下，包括：

- 计分维度、成员类型、状态枚举。
- 展示字段、配置项、内容项。
- 待确认项、边界条目、零散规则。
- UE 页面、奖励表、公式参数、打点指标和局部算法。

## 4. 正文写作顺序

每章应覆盖以下信息，但不要求作为固定小标题，也不要求严格按此顺序呈现：

1. 本章解决什么问题
2. 包含哪些对象 / 途径 / 状态
3. 每个对象的定位
4. 系统如何判断
5. 结果如何结算或状态如何变化
6. 玩家看到什么反馈
7. 边界和异常是什么

不要一上来解释概念，也不要把设计推导写成正文。

正文标题和段落形态应贴合设计对象本身。不要把写作前检查项原样写成固定小标题，例如“本节作用、适用对象、规则说明、判断方式、结果变化、玩家表现”。这些只用于写作校验，不作为公共 GDD 正文模板。

## 5. 规则表达要求

规则必须写清：

- 触发条件
- 系统判断
- 结算结果
- 状态变化
- 玩家反馈
- 无效或异常情况

交互型内容必须写玩家操作和系统响应；有分支时逐一说明。

状态变化不能自引用。不要只写“胜利后结算”，必须定义胜利条件和结算结果。

## 6. 交付检查

每份 GDD 必须包含：

- 需求目的：只写玩法目的层的目标状态，不写实现手段、交付对象或正文结构；每条目标必须可验证。
- 需求概述：用 1-3 句话说明功能是什么、范围是什么、主要限制是什么。
- 脑图 / 结构图：展示本文档的结构依据、主要对象、关系、流转和关键分支；只有文字列表不通过。
- 主体设计：按交付结构写功能、规则、状态、反馈和边界。

按需补充：

- 交互流程：有连续操作、页面跳转、按钮反馈时必须写。
- 配置项：只列策划可配置参数，必须写生效范围。
- UE 交互：界面入口、按钮、弹窗、页面流转与功能逻辑强绑定时写。
- 内容配置区：只能在功能描述完成后追加，不能承载系统规则。
- 待定区：只放需要数据或测试才能确定的内容，写明“待定，原因：[X]”。

禁止行为：

- 没有需求目的就写功能。
- 没有确认玩法目的就写需求目的或拆正文。
- 从交付对象、系统口径、页面、计分、统计、配置、展示、结算反推需求目的。
- 没有判断设计对象和交付对象就套模板。
- 没有完成设计推演层和交付结构层分层就拆正文。
- 没有判断结构依据就生成正文目录。
- 把设计意图、体验强度、收益感知、风险高低、协作氛围或策略卖点直接写成主体章节。
- 没有把设计推演材料转译到交付结构。
- 把附属信息拆成一级章节。
- 只有配置表，没有功能描述。
- 用解释、推导、正反例替代 GDD 正文。
- 写入技术实现、接口字段、日志、埋点、补偿、并发等开发内容。
- 使用自创抽象词替代玩家可见行为。
- 配置项不写生效范围。
- 内容配置表出现在功能描述之前。
- 把内部写作检查项机械写成每章固定标题。

不可交付条件：

1. 需求目的不可验证。
2. 需求目的来自交付对象、系统口径或正文结构，而不是玩法目的层。
3. 未完成玩法目的判定。
4. 未完成设计对象判定。
5. 未完成交付对象判定。
6. 未完成设计推演层和交付结构层分层。
7. 未完成结构依据判定。
8. 设计推演材料没有转译到交付结构。
9. 一级章节不能说明其在交付结构中的实现、配置、展示、结算或验证职责。
10. 附属信息独立成章。
11. 规则未写清触发、判断、结算、状态、反馈和异常。
12. 交互型内容缺少操作、响应或分支。
13. 混入技术实现或解释性正文。
14. 机械套用内部写作检查项，导致正文不像实际 GDD。

命中任一项，打回修改，不交付。
