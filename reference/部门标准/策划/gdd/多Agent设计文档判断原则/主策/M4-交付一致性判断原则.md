# M4-交付一致性判断原则

## 适用节点

适用于 M4 主策确认文档一致性。

## 判断目标

主策在 M4 判断文档是否忠实表达 M1-M3 已确认方案。M4 不重新设计，只做一致性确认，重点防止 G5 或 G5-D 把已锁定目的、手段和结构写偏。

## 必须确认

- 正文是否忠实表达 M1 已锁定设计目的、M2 已确认手段框架、M3 已确认独立功能和规则归属。
- 需求目的是否只表达 M1 已锁定的设计目的。
- 需求目的是否被交付对象、系统口径、统计、接入、归属、互斥、计分、配置、展示或结算污染。
- 是否新增未经确认的设计目的、结构依据、功能结构或核心规则。
- 是否绕过手段框架，直接把功能清单、交付物、承载方式或配套内容写成主体。
- 章节顺序是否支持读者理解设计链路。
- 规则、状态、UE 是否写在对应功能点下。
- 主体章节是否来自 M3 已确认的独立功能结构。
- 主体章节是否已经落成可交付内容。
- 主体章节是否以独立功能为单位，每个功能是否保持从触发或成立条件到处理、判断、状态变化和结果反馈的完整过程。
- 权限、条件、次数、冷却、消耗、配置、反馈和异常是否归入实际生效的功能，而不是与功能并列。
- 读者是否需要跨越多个交付维度章节，才能拼出一个功能的完整运行过程。
- 正文是否把设计推演词归位到对应规则、表现或验收关注点，而不是直接写成目录。
- 正文是否完成 G4-G5 正文语言降噪，没有混入内部判断语言、流程标签或工作口径。
- 正文是否没有新增目的、手段、结构或核心规则。
- 正文是否根据内容选择自然表达形态，而不是机械套用内部检查项。
- 交付范围是否已经转化为正文结构或明确的系统边界，而不是“本文只写、本章不展开”等写作说明。
- 排除范围是否确有防止误开发、依赖误解或验收歧义的价值；保留时是否明确指出保持不变的既有功能或规则。
- 是否存在“外壳、其他照旧、相关内容不涉及”等无法确认影响对象和验收结果的模糊范围表述。
- 正文表达形态是否保留了设计成立所依赖的核心关系：过程关系是否呈现先后、分支、状态变化和角色交接，静态关系是否呈现属性、权限、配置或结果之间的对应。
- 是否把原本相互连接的过程节点拆成了静态字段，导致读者无法还原触发、路径变化、结果去向或状态变化。
- 正文是否只承载设计结论，没有混入 M1-M4 裁决记录、阶段通过状态、验收依据、打回记录或审核结论。
- 已确认设计结论是否已经归入实际生效的功能节点，而不是集中写成“交付验收结论”一类过程总结。
- 正文是否只写设计层功能行为和功能级系统边界，没有混入接口字段、数据结构、日志、埋点、并发、存储、重试或监控等技术实现。
- 待确认项和阻塞项是否表达清楚。

## 通过条件

- 文档的内部证据链能对应“设计目的 -> 手段框架 -> 设计对象 -> 交付对象 -> 结构依据 -> 独立功能 -> 规则 / UE 反馈”，但正文没有把推演过程写成目录或正文内容。
- 需求目的表达的是已锁定设计目的，而不是功能手段、指标结果或交付产物。
- 文档能让开发、UE、数值或测试判断各主体节点要实现、配置、展示、结算或验证什么。
- 每个主体章节都能独立说明一个功能如何开始、运行和产生结果；附属规则没有脱离所属功能。
- 正文没有暴露内部思考过程。
- 正文没有混入内部判断语言、流程标签或工作口径。
- 正文没有用文档叙述代替设计边界；必要的排除项已经写成可确认、可验收的系统状态。
- 表达载体没有损失设计关系；读者能直接还原关键对象之间的连接、推进、分支或对应关系。
- 正文与流程产物已经分离，删除验收报告后不会损失任何玩家行为、系统规则、状态变化或交付边界。
- 正文没有把“本节作用、适用对象、规则说明、判断方式、结果变化、玩家表现”等内部检查项机械写成固定标题。
- 未确认内容没有被写成确定结论。
- 文档满足进入 G6 交付验收的完整度。

## 打回条件

- 只是表达不清或章节错位：打回 G5。
- 仅存在内部判断语言、流程标签或工作口径污染：打回 G5，不回退 G1-G4。
- 仅存在“本文只写、本章不展开”等文档叙述，或排除范围未转化为明确系统边界：打回 G5。
- 过程节点和分支已经确认，只是表达载体没有保留其连接关系：打回 G5。
- 触发、节点、路径变化或结果本身尚未被设计清楚，无法还原过程关系：打回 G4。
- 正文混入阶段裁决、通过依据、验收结论或审核报告：打回 G5，将其移至独立流程记录。
- 功能过程已确认，只是正文按权限、配置、反馈或异常等维度拆散：打回 G5。
- 主体节点本身没有形成独立功能，或功能归属尚未确定：打回 G4。
- 需求目的写成交付对象、系统口径或正文结构：打回 G5；如果暴露 M1 分层错误，打回 M1。
- 文档暴露手段框架缺口：打回 G3；如果暴露 M1 裁决错误，打回 M1。
- 文档暴露落地缺口：打回 G4。
- 文档暴露结构依据缺口：打回 G3。
- 文档主体结构不来自 M3 已确认的独立功能：打回 G4。
- 文档主体节点停留在抽象结构，无法指导开发落地：打回 G4。

## 禁止事项

- 禁止在 M4 新增核心设计。
- 禁止在 M4 修改设计目的；目的错必须回 M1/G1。
- 禁止把写作润色问题升级成目标问题。
- 禁止让写作 Agent 自己决定方案取舍。
- 禁止放行机械模板化正文。
- 禁止放行混入内部判断语言、流程标签或工作口径的正文。
- 禁止放行用写作说明代替设计边界，或使用无法确认影响对象和验收结果的模糊范围表述。
- 禁止放行因表达载体选择导致关键设计关系丢失的正文。
- 禁止放行把流程证据或验收报告作为正文一部分的文档。
- 禁止放行按交付维度拆散功能过程的正文。
- 禁止放行接口字段、数据结构、日志、埋点、并发、存储、重试或监控等技术实现内容。
- 禁止放行只有设计判断、没有可交付内容的正文。
- 禁止放行需求目的被交付对象或系统口径污染的正文。
- 禁止放行绕过手段框架的正文。
- 禁止放行把目的说明、体验强度、风险高低、收益感知或策略卖点直接作为主体章节的正文。
