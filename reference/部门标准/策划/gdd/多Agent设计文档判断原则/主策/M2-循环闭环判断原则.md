# M2-结构依据判断原则

## 适用节点

适用于 M2 主策确认设计推演质量和交付结构依据。

## 判断目标

主策在 M2 不审正文目录，也不直接拆功能。M2 只判断 G3 的设计推演是否服务 M1 已确认玩法目的、设计对象和交付对象边界，以及提出的结构依据是否适合本文档的交付阅读。

结构依据应能说明本文档后续应该按什么组织：赛程/阶段、对象构成、资源流转、积分排名、状态关系、操作流程、调用场景，或其他更贴合该功能交付的方式。

M2 的核心不是选择一个固定模板，而是防止设计推演词、体验卖点、风险收益判断直接变成正文结构，也防止交付对象倒推需求目的。

## 必须确认

- 设计推演是否服务 M1 已确认玩法目的、设计对象、交付对象边界和范围边界。
- G3 是否区分了设计推演层和交付结构层。
- 结构依据是否来自交付对象如何被生成、实现、配置、展示、结算或验收。
- 结构依据是否能承接对象如何成立、变化、结算、生成、生效或被调用。
- 交付对象是否只进入结构依据和主体设计，没有被反推为玩法目的。
- 关键结果变化是否可感知或可被下游系统调用。
- 涉及社交、军团、协作或竞争时，关系变化是否明确。
- 结构依据断点是否可接受或可作为方向验证保留项。

## 通过条件

- 设计推演能解释设计对象的成立逻辑。
- 已确认一个适合交付阅读的结构依据。
- 结构依据能承接 M1 的交付对象边界。
- 关键判断、计算、状态变化、结算或调用关系闭合。
- 关键反馈能被玩家感知，或关键结果能被下游系统调用。
- 收益、属性、资源、资格、关系或状态变化足以支撑目标。
- 设计推演词没有被直接当作正文目录。
- 交付对象没有被反推为需求目的或最高设计对象。
- 外部依赖没有阻断结构依据。

## 打回条件

- 结构依据不成立：打回 G3。
- 反馈不可感知、结果不可调用或变化无意义：打回 G3。
- 设计推演显示 M1 玩法目的、设计对象或交付对象边界错误：回到 M1。

## 禁止事项

- 禁止在 M2 审 UI 细节。
- 禁止用“功能很多”代替结构依据成立。
- 禁止把设计意图、体验强度、风险高低、收益感知或策略卖点当作结构依据。
- 禁止用统计、接入、归属、互斥、计分、展示、配置、结算等交付对象反推玩法目的。
- 禁止修改 M1 目标但不回到 M1。
