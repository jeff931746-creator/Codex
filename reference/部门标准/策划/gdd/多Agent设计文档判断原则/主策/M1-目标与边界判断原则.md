# M1-目标与边界判断原则

## 适用节点

适用于 M1 主策确认目标与边界。

## 判断目标

主策在 M1 必须把 G1/G2 的候选材料转化为明确的玩法目的、设计对象、交付对象边界、设计意图和范围边界。M1 是选择点，不是继续发散点。

M1 必须按顺序确认：

```text
玩法目的 -> 设计对象 -> 交付对象 -> 范围边界
```

禁止先确认交付对象，再从交付对象反推玩法目的。

## 必须确认

- 本次设计要解决的核心问题。
- 本次玩法目的：功能要在游戏里形成的关系、状态或结果。
- 本次设计目标。
- 本次设计意图。
- 本次设计对象。
- 本次交付对象边界：哪些统计、规则、展示、结算、配置、状态或调用关系进入正文落地。
- 本次范围边界。
- 哪些材料只是交付对象，后续不得写入需求目的。
- 哪些材料属于设计推演层，后续不得直接作为正文目录。
- 哪些问题可作为方向验证保留项。
- 哪些问题是正式 GDD 阻塞项。

## 通过条件

- 玩法目的不是功能手段、交付对象或系统口径，而是可判断的游戏关系、状态或结果。
- 目标能回到已确认玩法目的。
- 设计目标从属于玩法目的，不能替代玩法目的。
- 设计意图能说明该目标服务的整体游戏体验、系统结构或对象规则。
- 设计对象能承载玩法目的和设计目标，贯穿主要规则，并产生核心结果。
- 设计对象没有被页面、配置、奖励表、指标、局部规则或设计推演词替代。
- 交付对象被明确归位，没有替代玩法目的或设计对象。
- 边界足够收敛，后续设计推演和结构依据判断不会无限扩散。
- 必须裁决的问题已经裁决，或被明确降级为方向验证保留项。
- 正式 GDD 阻塞项没有被伪装成普通待确认项。

## 打回条件

- 资料不足导致目标无法判断：打回 G1。
- 前置问题没有问清：打回 G2。
- 候选玩法目的仍停留在统计、接入、归属、互斥、计分、展示、配置或结算等交付对象：打回 G1。
- 候选目标仍停留在功能载体或奖励包装：打回 G1。
- 候选设计对象仍停留在页面、配置、奖励、指标、局部规则或设计推演词：打回 G1。
- 候选设计对象实际只是交付对象，无法承载玩法目的：打回 G1。

## 禁止事项

- 禁止让子 Agent 替主策选择目标。
- 禁止把多个方向并列保留到后续阶段。
- 禁止用“先做着看”代替边界裁决。
- 禁止未确认玩法目的就确认设计对象。
- 禁止未确认设计对象和边界就进入 G3。
- 禁止把交付对象、系统口径或正文结构写成玩法目的。
