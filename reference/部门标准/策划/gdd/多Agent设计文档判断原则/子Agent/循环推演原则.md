# 设计推演与结构依据候选原则

## 适用阶段

适用于 G3 设计推演与结构依据候选。

## 判断目标

本阶段要从已确认玩法目的、手段框架、设计对象、交付对象边界和范围边界出发，产出设计推演材料，复核手段框架，并提出本文档可采用的交付结构依据候选。

G3 不能直接生成正文目录。G3 的产物是推演和结构依据候选，供 M2 判断；正式正文结构要到 G4 才能在已确认结构依据下转译形成。

设计推演可以包括玩法目的如何由手段框架和设计对象承载、交付对象如何生成或变化、系统如何判断或计算、结果如何生效、玩家或其他系统如何感知和调用。

结构依据候选要说明本文档更适合按什么方式交付阅读，例如赛程/阶段、对象构成、资源流转、积分排名、状态关系、操作流程或调用场景。它不是固定类型库，也不是案例套用。

## 必须回答的问题

- 本次玩法目的是什么，设计对象如何承接该玩法目的？
- 本次手段框架是什么，是否能写成“通过什么规则，把什么输入转成什么结果”？
- 手段框架中的输入、规则类型和输出结果分别是什么？
- 哪些节点承担转化关系，哪些内容只是配套职责？
- 本次交付对象有哪些，它们分别服务设计对象的哪个部分？
- 哪些内容属于设计推演层：目标意图、体验判断、策略取舍、玩家行为假设、风险/收益/协作/竞争等。
- 本文档可能采用什么交付结构依据：流程推进、对象构成、生成规则、资源流转、状态变化、关系变化、结算分配或调用关系？
- 为什么这个结构依据适合本文档的交付阅读，而不是只适合设计讨论？
- 为什么这个结构依据能承接手段框架，而不是从功能清单、承载方式或阶段表现倒推？
- 为什么该结构依据来自交付对象链路，而不是从玩法目的词、体验卖点或交付对象倒推需求目的？
- 关键输入是什么：玩家行为、系统事件、配置、掉落、消耗、状态、关系或外部调用？
- 系统如何判断、计算或推进？
- 结果如何变化，并影响玩家、队伍、军团、资源、状态、属性、排名或其他系统？
- 玩家或下游系统如何感知这个结果？
- 设计推演材料中哪些不能直接成为正文目录，后续必须归位到交付结构？
- 哪些交付对象不能进入需求目的，只能进入需求概述或主体设计？
- 哪些不承担转化关系的内容不能独立成章，必须挂靠到手段框架对应节点？
- 结构依据候选中是否存在断点、外部依赖或正式 GDD 阻塞项？

## 结构依据候选

根据本文档交付阅读方式提出结构依据候选，不得强制套一种结构：

- 玩法 / 活动 / 赛制：进入、参与、推进、判断、结算、反馈、再进入。
- 养成 / 装备 / 属性：对象定义、构成、生成、随机、计算、生效、展示、调用。
- 资源 / 货币 / 积分：来源、持有、消耗、转化、回收、展示、结算。
- 状态 / 资格 / 身份：进入、持续、切换、退出、反馈。
- 社交 / 军团 / 协作：关系建立、行为互动、关系或组织状态变化、反馈、后续承接。
- 管理 / 配置工具：管理对象、权限、操作、结果、异常。

## 断点显性化

推演中发现以下情况必须标为断点：

- 设计对象只能解释局部规则，不能承载目标。
- 手段框架缺失，只有目的和功能清单。
- 手段框架只写交付物、承载方式或阶段表现，无法说明规则转化关系。
- 手段框架不能解释哪些节点承担转化关系，哪些内容只是配套职责。
- 交付对象被误判为设计对象，导致玩法目的无法成立。
- 结构依据成立，但玩法目的只能从交付对象反推。
- 有行为、生成或计算，但没有结果变化。
- 有结果变化，但玩家或下游系统无法感知。
- 有收益、属性、资格或状态，但无法说明生效或调用关系。
- 需要他人回应但没有回应机制。
- 目标依赖外部系统但边界未确认。
- 结构依据只来自设计意图或体验卖点，不能支撑交付阅读。

## 禁止事项

- 禁止把设计推演词直接写成正文目录。
- 禁止用功能列表代替结构依据。
- 禁止用功能列表代替手段框架。
- 禁止用奖励列表代替收益状态变化。
- 禁止把玩家行为驱动对象写成纯系统流程。
- 禁止把对象规则驱动内容强行写成玩家循环。
- 禁止修改 M1 已确认目标。
- 禁止修改 M1 已确认玩法目的、手段框架、设计对象和交付对象边界。
- 禁止从交付对象、系统口径或正文结构反推玩法目的。
- 禁止把不承担转化关系的配套内容当成手段框架本体。
- 禁止把 UE 入口当成结构依据成立的证据。
