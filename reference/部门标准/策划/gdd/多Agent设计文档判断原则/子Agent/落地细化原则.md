# 落地细化原则

## 适用阶段

适用于 G4 落地细化。

## 判断目标

落地细化要把已确认循环拆成可执行、可验证、可写入 GDD 的功能点、规则、状态、入口、反馈和 UE 要求。

## 拆解顺序

1. 从循环节点拆功能点。
2. 从功能点拆玩家操作和系统响应。
3. 从系统响应拆规则、状态和边界条件。
4. 从反馈需求拆 UE、提示、列表、弹窗或动效要求。
5. 标明方向验证保留项和正式 GDD 阻塞项。

## 功能点判断

每个功能点都必须能回答：

- 承接循环中的哪个节点？
- 玩家在这里做什么？
- 系统在这里判断什么？
- 结果如何反馈给玩家？
- 会改变什么状态？
- 异常或边界是什么？

不能回答上述问题的功能点，应删除、合并或退回循环阶段。

## 规则可执行性校验

落地细化 Agent 在思考层必须能把核心规则转成最小 `若 X，则 Y` 骨架，用来确认功能是否可执行。

方向验证稿不强制把这套规则骨架完整写进正文；正文可以用更自然的设计表达。

正式 GDD 才需要把关键规则明确写成可执行条件。

思考层最小校验包括：

- 若玩家触发入口，则系统如何生成或展示对象。
- 若玩家执行核心操作，则状态如何变化。
- 若操作完成，则系统给谁什么反馈。
- 若对象已被占用、过期或失败，则系统如何处理。

## 状态要求

涉及任务、奖励、协作、排行、贡献、报名、领取、结算、展示的功能，必须列清关键状态。

每个状态至少说明：

- 进入条件
- 可执行操作
- 退出条件
- 玩家可见反馈

## 禁止事项

- 禁止重新定义核心循环。
- 禁止用 UI 包装代替规则。
- 禁止在思考层只校验正常流程，不校验异常和边界。
- 禁止把配置项当成功能说明。
- 禁止把正式 GDD 阻塞项降级成普通待确认项。
