# 落地细化原则

## 适用阶段

适用于 G4 落地细化。

## 判断目标

落地细化要把已确认手段框架、交付对象边界、结构依据和设计推演材料，转译成可执行、可验证、可写入 GDD 的交付结构、功能点、规则、状态、入口、反馈和 UE 要求。

落地细化的核心是转译，不是继续发散设计点。主体节点只能来自已确认交付结构，不能来自设计意图、体验强度、收益感知、风险高低、协作氛围、页面、配置、奖励表、状态枚举、打点指标或局部规则。

转译后的节点必须是开发、UE、数值或测试可以直接拆任务、做配置、做界面或写用例的交付内容。

## 拆解顺序

1. 确认 M1 已确认的玩法目的、手段框架、设计对象、交付对象边界和范围边界。
2. 确认 M2 已确认的手段框架复核结论和结构依据。
3. 把 G3 的设计推演材料拆成：M1 已确认、可进入需求目的的玩法目的内容，可进入正文的交付内容，只能作为设计说明的推演内容，必须归位的附属内容。
4. 按手段框架、结构依据和交付对象边界生成主体节点。
5. 将主体节点落成可交付内容，例如入口与参与规则、目标与进度、贡献或生成规则、排名或结算规则、展示反馈、功能级调用场景。
6. 从交付内容拆玩家操作、系统事件、对象规则和系统响应。
7. 从系统响应或对象规则拆规则、状态和边界条件。
8. 从反馈需求拆 UE、提示、列表、弹窗或动效要求。
9. 把配置、状态枚举、奖励表、公式参数、打点指标和局部算法归位到实际生效的主体节点。
10. 标明方向验证保留项和正式 GDD 阻塞项。

## 功能点判断

每个功能点都必须能回答：

- 承接 M2 已确认结构依据中的哪个节点？
- 承接 M1/M2 已确认手段框架中的哪个输入、规则类型或输出结果？
- 承接 M1 已确认的哪个交付对象？
- 它是交付结构节点，还是设计推演材料的归位结果？
- 开发、UE、数值或测试要在这里交付什么？
- 玩家在这里做什么，或系统在这里处理什么事件、生成、计算、结算或调用？
- 系统在这里判断、计算、生成或调用什么？
- 结果如何反馈给玩家，或如何被下游系统感知/调用？
- 会改变什么状态？
- 异常或边界是什么？

不能回答上述问题的功能点，应删除、合并或退回 G3/M2 重新判断结构依据。

不直接承担手段框架转化关系的功能点，必须挂靠到对应规则节点并说明配套职责；不能把它写成玩法本体。

## 规则可执行性校验

落地细化 Agent 在思考层必须能把核心规则转成最小 `若 X，则 Y` 骨架，用来确认功能是否可执行。

方向验证稿不强制把这套规则骨架完整写进正文；正文可以用更自然的设计表达。

正式 GDD 才需要把关键规则明确写成可执行条件。

思考层最小校验包括：

- 若玩家触发入口，则系统如何生成或展示对象。
- 若玩家执行核心操作，则状态如何变化。
- 若操作完成，则系统给谁什么反馈。
- 若对象已被占用、过期或失败，则系统如何处理。

## 状态要求

涉及任务、奖励、协作、排行、贡献、报名、领取、结算、展示的功能，必须列清关键状态。

每个状态至少说明：

- 进入条件
- 可执行操作
- 退出条件
- 玩家可见反馈

## 禁止事项

- 禁止重新定义 M2 已确认的结构依据。
- 禁止重新定义 M1/M2 已确认的手段框架。
- 禁止绕过结构依据，把设计推演词直接写成主体节点。
- 禁止绕过手段框架，把功能清单直接写成主体节点。
- 禁止把 M1 已确认的玩法目的拆成主体节点。
- 禁止把交付对象反推为需求目的。
- 禁止用 UI 包装代替规则。
- 禁止在思考层只校验正常流程，不校验异常和边界。
- 禁止把配置项当成功能说明。
- 禁止把页面、配置、奖励表、状态枚举、打点指标或局部规则拆成主体节点。
- 禁止只给抽象结构，不转译成可交付内容。
- 禁止把正式 GDD 阻塞项降级成普通待确认项。
