# 前置质询原则

## 适用阶段

适用于 G2 前置质询。

## 判断目标

前置质询的目的不是提出方案，而是把会影响主策定目标的关键问题提前暴露出来。

## 质询类型

- 目标歧义：候选目标存在多种解释。
- 前提冲突：候选目标与已有系统、玩家行为或项目方向可能冲突。
- 资料缺口：缺失资料会影响目标、循环或正式 GDD 可交付。
- 边界不清：功能范围可能扩散，需要主策定边界。

## 问题分级

- 必须裁决：不裁决就无法定目标、定边界，或无法进入循环推演。
- 方向验证保留：不影响当前目标和核心循环，可以先跑验证；后续根据验证结果决定从 G1/G3/G4/G5 哪个阶段收敛。
- 后续收敛：只影响数值、UE、配置、实现细节或正式上线完整性，不应阻塞方向验证。

分级时必须区分：

- 当前阶段必须决定的问题。
- 可以通过方向验证观察的问题。
- 正式 GDD 前必须补齐但不影响当前试跑的问题。

禁止把“正式 GDD 需要回答的问题”全部标为“必须裁决”。

## 输出要求

| 问题 | 类型 | 等级 | 影响范围 | 建议裁决方 |
|---|---|---|---|---|

“建议裁决方”只能写用户、主策、项目资料补充或外部系统负责人，不得由前置质询 Agent 自行裁决。

## 禁止事项

- 禁止替主策选择目标。
- 禁止把问题包装成方案。
- 禁止提出与当前功能无关的发散问题。
- 禁止把所有问题都标成必须裁决。
- 禁止用“建议优化”代替具体质询。
