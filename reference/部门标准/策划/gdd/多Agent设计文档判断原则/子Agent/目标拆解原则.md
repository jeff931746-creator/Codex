# 目标拆解原则

## 适用阶段

适用于 G1 资料收集与目标拆解。

## 判断目标

目标拆解的目的不是替主策做决定，而是把资料拆成可判断的层级材料：玩法目的、设计对象、交付对象、设计推演材料和待裁决问题。

## 必须产出的材料

- 已确认资料：来自用户输入、项目文档、部门标准或已确认事实。
- 未覆盖资料：当前无法确认但会影响目标判断的信息。
- 候选设计问题：功能可能要解决的问题。
- 候选玩法目的：功能要在游戏里形成的关系、状态或结果。
- 候选设计目标：功能可能要达成的玩家行为、系统状态或关系变化；必须回到候选玩法目的。
- 候选设计意图：为什么要这样设计，它服务于什么体验、生态或运营目标。
- 候选设计对象：本次 GDD 可能真正定义的对象、变化或结果。
- 候选交付对象：设计对象内部可能需要落地的统计、规则、展示、结算、配置、状态、奖励或调用关系。
- 设计推演材料：资料中出现的体验判断、策略取舍、玩家行为假设、风险/收益/协作/竞争等内容；只作为后续推演材料，不得直接当作正文目录。
- 冲突与依赖：候选项之间的冲突、前提依赖和需要主策裁决的问题。

## 拆解原则

候选玩法目的必须回答“为什么需要这个功能”，不能写成功能手段或交付产物。

错误形式：

- 建立统计对象。
- 接入上游事件。
- 明确归属互斥。
- 展示排行榜。

正确形式：

- 形成玩家、队伍、军团或系统之间的竞争、协作、成长、交易或身份关系。
- 让某类结果能够代表综合实力、阶段胜负、长期价值或关系变化。
- 让成员行为、资源流转或对象变化与上级玩法结果建立明确关联。

候选目标必须能回到一个设计问题和一个玩法目的。

错误形式：

- 做一个排行榜。
- 增加一个入口。
- 加一套奖励。

正确形式：

- 让玩家能感知自己在军团内的贡献位置。
- 让短期协作行为形成可见反馈。
- 让低门槛社交行为能被军团承接。

候选设计意图必须说明目标服务的整体设计方向。如果只能说明“用户会点击”“系统会展示”，说明还停留在功能手段层。

候选设计对象必须说明它为什么能承载玩法目的和设计目标，并标明它不是页面、配置、奖励表、指标或局部规则。

判断口径：

- 设计对象应能贯穿主要规则并产生核心结果。
- 设计对象应能被玩家体验、系统状态、关系变化、资源流转或结算结果感知。
- 局部规则、配置字段、UE 页面、奖励表、状态枚举和打点指标不能作为设计对象，只能作为后续归位材料。
- 体验强度、风险高低、收益感知、协作氛围和策略卖点不能作为设计对象，只能作为设计推演材料。
- 交付对象可以进入后续正文结构，但不能反推为玩法目的。
- 交付对象不能替代最高设计对象；如果候选对象只是统计、积分、配置、展示或结算口径，应标为候选交付对象。

## 候选不等于结论

目标拆解 Agent 可以列出多个候选目标，但不得推荐唯一方案，不得写“建议采用 A”。选择权属于主策 Agent。

## 来源标记

每条候选材料都要标记来源：

- confirmed：已有事实。
- inferred：基于资料推断。
- unknown：缺资料但影响判断。

不得把 inferred 写成 confirmed。

## 输出要求

| 项目 | 内容 |
|---|---|
| 已确认资料 | 明确资料来源 |
| 未覆盖资料 | 说明影响什么判断 |
| 候选设计问题 | 不少于 1 条，可多条 |
| 候选玩法目的 | 功能要形成的游戏关系、状态或结果 |
| 候选设计目标 | 每条对应至少一个问题 |
| 候选设计意图 | 每条说明服务的整体方向 |
| 候选设计对象 | 说明承载目标的对象、变化或结果 |
| 候选交付对象 | 标明它服务哪个设计对象，不能进入需求目的 |
| 设计推演材料 | 标明哪些材料属于意图、体验判断或策略取舍 |
| 主策待裁决点 | 需要 M1 决定的问题 |

## 禁止事项

- 禁止替主策定目标。
- 禁止直接写功能点。
- 禁止用奖励包装代替设计目标。
- 禁止把统计、接入、归属、互斥、计分、展示、配置、结算包装成玩法目的。
- 禁止把页面、配置、奖励、指标或局部规则包装成设计对象。
- 禁止把交付对象包装成最高设计对象。
- 禁止把设计推演材料包装成正文结构。
- 禁止把用户原话简单改写成目标。
- 禁止在资料不足时编造项目背景。
