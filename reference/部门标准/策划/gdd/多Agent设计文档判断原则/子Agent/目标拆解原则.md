# 目标拆解原则

## 适用阶段

适用于 G1 资料收集与目标拆解。

## 判断目标

目标拆解的目的不是替主策做决定，而是把“可能要解决什么问题、可能要达成什么变化、可能要承担什么设计意图”拆成可判断材料。

## 必须产出的材料

- 已确认资料：来自用户输入、项目文档、部门标准或已确认事实。
- 未覆盖资料：当前无法确认但会影响目标判断的信息。
- 候选设计问题：功能可能要解决的问题。
- 候选设计目标：功能可能要达成的玩家行为、系统状态或关系变化。
- 候选设计意图：为什么要这样设计，它服务于什么体验、生态或运营目标。
- 冲突与依赖：候选项之间的冲突、前提依赖和需要主策裁决的问题。

## 拆解原则

候选目标必须能回到一个设计问题。

错误形式：

- 做一个排行榜。
- 增加一个入口。
- 加一套奖励。

正确形式：

- 让玩家能感知自己在军团内的贡献位置。
- 让短期协作行为形成可见反馈。
- 让低门槛社交行为能被军团承接。

候选设计意图必须说明目标服务的整体设计方向。如果只能说明“用户会点击”“系统会展示”，说明还停留在功能手段层。

## 候选不等于结论

目标拆解 Agent 可以列出多个候选目标，但不得推荐唯一方案，不得写“建议采用 A”。选择权属于主策 Agent。

## 来源标记

每条候选材料都要标记来源：

- confirmed：已有事实。
- inferred：基于资料推断。
- unknown：缺资料但影响判断。

不得把 inferred 写成 confirmed。

## 输出要求

| 项目 | 内容 |
|---|---|
| 已确认资料 | 明确资料来源 |
| 未覆盖资料 | 说明影响什么判断 |
| 候选设计问题 | 不少于 1 条，可多条 |
| 候选设计目标 | 每条对应至少一个问题 |
| 候选设计意图 | 每条说明服务的整体方向 |
| 主策待裁决点 | 需要 M1 决定的问题 |

## 禁止事项

- 禁止替主策定目标。
- 禁止直接写功能点。
- 禁止用奖励包装代替设计目标。
- 禁止把用户原话简单改写成目标。
- 禁止在资料不足时编造项目背景。
