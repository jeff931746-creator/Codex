# 交付状态检查原则

## 适用阶段

适用于 G6 交付状态检查。G6 只报告客观状态、问题和风险，不决定方向稿或正式 GDD 是否交付。

## 检查目标

- U1-U4 用户确认记录是否完整，并与当前产物版本对应。
- 待检查文档是否与 U4 用户确认版本一致。
- 方向验证保留项和正式 GDD 阻塞项是否完整记录。
- G6 检查报告、审核报告和 GDD 正文是否分离。
- 是否存在未记录的 Agent 自行选择、返回、风险接受或版本覆盖。

## 检查报告的三种写法

G6 只允许输出：

- `检查完成，未发现交付状态问题`。
- `检查完成，存在交付状态问题`。
- `检查无法完成，证据不足`。

这些状态不等于“通过”“不通过”或“打回”。报告必须列出证据、影响、可选处理方式、推荐和“等待用户 U5 决定”。

## 方向验证稿检查项

- U1-U4 确认记录完整。
- 文档与 U4 用户确认版本一致。
- 方向验证保留项已记录，没有被包装成正式结论。
- 检查报告与正文分离。

## 正式 GDD 检查项

- U1-U4 确认记录完整。
- 文档与 U4 用户确认版本一致。
- 正式 GDD 阻塞项及其影响完整呈现。
- 检查报告与正文分离。
- 已准备进入独立 `gdd-review`；独立审核仍只报告问题，不决定交付。

## 问题处理

发现证据缺失、版本不一致、阻塞项未关闭、产物未分离或疑似上游问题时，G6 必须：

1. 记录问题与证据。
2. 说明影响。
3. 列出可选处理阶段。
4. 给出推荐理由。
5. 等待用户在 U5 指定处理方式。

## 禁止事项

- 禁止重写方案、修改目标文档或补设计。
- 禁止重新选择目的、手段、结构或功能。
- 禁止把个人偏好当作检查标准。
- 禁止自行放行阻塞项、打回阶段或接受风险。
- 禁止输出具有最终效力的“方向验证通过”“正式 GDD 通过”“打回”或“交付”。
- 禁止把检查记录或审核结论写回 GDD。
