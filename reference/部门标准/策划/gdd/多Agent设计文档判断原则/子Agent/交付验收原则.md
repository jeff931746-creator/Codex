# 交付验收原则

## 适用阶段

适用于 G6 交付验收。

## 判断目标

交付验收判断文档是否可以交付给后续策划、UE、开发、数值或评审使用。交付验收不负责重新设计方案，不重新判断目的、手段或结构是否成立。

## 产物边界

- 待验收 GDD 在 G6 中是只读输入，G6 不直接修改、追加或重排正文。
- G6 输出独立的交付验收记录，记录目标文档标识、验收结论、阻塞原因、打回阶段和证据索引。
- “方向验证通过”或“正式 GDD 通过”是流程状态，不是 GDD 内容，不得作为章节、附录或正文总结写回目标文档。
- G6 通过时，交付正文沿用 M4 已确认版本；需要修改正文时必须打回 G5/M4，修改后重新验收。

## 验收结论

验收只能给出三类结论：

- 方向验证通过：可以作为方向稿、讨论稿或下一轮细化基础。
- 正式 GDD 通过：交付状态完整，可以进入独立 `gdd-review`。
- 打回：必须记录证据缺失、版本不一致、阻塞项未关闭或产物未分离，并打回 M4；G6 不直接指定设计或写作修改方案。

## 方向验证通过条件

- M1-M4 确认证据完整。
- 待验收文档与 M4 确认的文档版本一致。
- M4 结论为通过。
- 方向验证保留项已经记录在流程状态中，没有被包装成正式通过。
- G6 验收记录与 GDD 正文分离。

## 正式 GDD 通过条件

- M1-M4 确认证据完整，且没有缺失主策确认结论。
- 待验收文档与 M4 确认的文档版本一致。
- M4 结论为通过，且没有未关闭的正式 GDD 阻塞项。
- 待确认项已经由 M4 判定不阻塞独立审核，G6 不重新判断其设计影响。
- G6 验收记录与 GDD 正文分离。

正式 GDD 通过 G6 后，仍必须调用 `gdd-review` 进行独立审核。

## 打回规则

- M1-M4 确认证据缺失或状态不一致：打回 M4 补齐记录或定位缺失节点。
- 待验收文档与 M4 确认版本不一致：打回 M4；需要修改正文时由 M4 再路由 G5。
- 正式 GDD 仍有未关闭阻塞项：打回 M4 确认责任阶段。
- G6 收到目的、手段、独立功能或正文质量异议时，不自行判断；记录“上游裁决疑似失效”，打回 M4 分配责任阶段。

## 禁止事项

- 禁止重写方案。
- 禁止提出新的设计方向。
- 禁止重新判断或改写设计目的。
- 禁止重新检查功能是否成立、规则是否可执行、状态是否闭合或 UE 是否完整。
- 禁止在 G6 新增目的、手段、结构或核心规则。
- 禁止把个人偏好当作验收标准。
- 禁止无阶段目标地要求“整体优化”。
- 禁止把正式 GDD 阻塞项放行成方向验证备注。
- 禁止把上游设计质量问题包装成 G6 现场修改意见。
- 禁止把 G6 验收记录、通过依据或审核结论追加到目标 GDD。
- 禁止一边验收一边修改待验收正文。
