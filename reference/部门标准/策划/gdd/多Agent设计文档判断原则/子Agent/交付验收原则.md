# 交付验收原则

## 适用阶段

适用于 G6 交付验收。

## 判断目标

交付验收判断文档是否可以交付给后续策划、UE、开发、数值或评审使用。交付验收不负责重新设计方案。

## 验收结论

验收只能给出三类结论：

- 方向验证通过：可以作为方向稿、讨论稿或下一轮细化基础。
- 正式 GDD 通过：可以进入 `gdd-review` 最终标准审核。
- 打回：必须指定目标阶段和阻塞原因。

## 方向验证通过条件

- 设计目标明确。
- 玩法目的明确，且需求目的来自玩法目的层。
- 设计意图明确。
- 设计对象和边界明确。
- 交付对象边界明确。
- 结构依据明确。
- 核心功能点能承接结构依据。
- 关键不确定项已标记为方向验证保留项。

## 正式 GDD 通过条件

- 目标、意图、边界已确认。
- 玩法目的已确认，需求目的未被交付对象或系统口径污染。
- 设计对象和结构依据已确认。
- 交付对象边界已确认。
- 设计推演材料已完成交付结构转译。
- 功能点完整覆盖交付结构。
- 主体章节来自已确认交付结构。
- 主体章节已落成开发、UE、数值或测试能接住的交付内容。
- 核心规则可执行。
- 关键状态闭合。
- UE 入口、反馈和异常提示可支持玩家理解。
- 待确认项不影响正式实现判断。
- 符合 `GDD写作标准.md` 和 `GDD输出模板.md`。
- 正文没有机械套用内部写作检查项。

正式 GDD 通过 G6 后，仍必须调用 `gdd-review` 进行最终标准审核。

## 打回规则

- 目标或边界问题：打回 G1 或 G2，后续自然重新进入 M1。
- 玩法目的被交付对象、系统口径或正文结构替代：打回 G1/G2/M1。
- 结构依据不成立：打回 G3，后续自然重新进入 M2。
- 功能点、规则、状态、UE 缺失：打回 G4，后续自然重新进入 M3。
- 主体章节停留在抽象结构，无法判断要实现什么：打回 G4，后续自然重新进入 M3。
- 主体章节来自设计推演词而不是交付结构：打回 G4，后续自然重新进入 M3。
- 表达、章节、正文忠实度问题：打回 G5，后续自然重新进入 M4。

## 禁止事项

- 禁止重写方案。
- 禁止提出新的设计方向。
- 禁止把个人偏好当作验收标准。
- 禁止无阶段目标地要求“整体优化”。
- 禁止把正式 GDD 阻塞项放行成方向验证备注。
- 禁止放行需求目的来自统计、接入、归属、互斥、计分、展示、配置、结算等交付对象的文档。
