# 写作原则

## 适用阶段

适用于 G5 文档写作。

## 判断目标

写作阶段只负责把已确认方案表达成可读、可执行、可审核的 GDD 文档，不重新设计。

## 输入边界

写作 Agent 只能使用：

- M1 已锁定的设计目的、循环依据、当前缺口和边界。
- M2 已确认的手段框架。
- M2 已确认的设计对象。
- M2 已确认的交付对象边界。
- M2 已确认的结构依据。
- M3 已确认的功能点、规则、状态和 UE 要求。
- `GDD输出模板.md`。

未经主策确认的材料，只能进入“待确认项”或“附录资料”，不得写成正文结论。

M1-M4 的确认记录只用于证明正文输入有效，不是正文素材。写作 Agent 只能提取其中已经确认的设计结论，不能复制阶段状态、裁决过程、通过依据或审核话术。

## 表达原则

- 写设计结论，不写推理过程。
- 不直接继承 G4 的原始措辞；写作前必须把 G4 的内部判断语言改写为策划正文语言。
- 需求目的只能表达 M1 已锁定的设计目的；不得从交付对象、系统口径或正文结构反推，也不得在 G5 重新拆出“设计目标、设计意图、玩法目的”等并列口径。
- 需求概述和主体设计必须能承接已确认手段框架，但不得把“手段框架裁决”机械写成正文标题。
- 需求概述说明功能是什么、范围是什么、主要限制是什么，可以写设计对象和必要交付对象。
- 交付范围是写作输入，不是必须原样落入正文的说明。纳入范围应通过章节和规则直接呈现，不写“本文只写、本章仅写”等文档叙述。
- 排除范围只有在可能造成误开发、依赖误解或验收歧义时才进入正文，并必须改写为明确的系统边界，说明哪些既有功能或规则保持不变；无法对应具体功能或规则的“旧系统外壳、其余不展开”等模糊表述应删除。
- 标题来自 M3 已确认的独立功能及其内部过程或规则，写设计动作、机制转化、生成、结算、状态或调用关系，不写抽象载体。
- 标题必须落到可交付内容，不能只写抽象目标、结构判断、目的说明或体验特征。
- 主体章节以 M3 已确认的独立功能为单位。每个功能先写清从触发或成立条件到处理、判断、状态变化和结果反馈的主过程，再补充作用于该过程的规则。
- 权限、条件、次数、冷却、消耗、配置、奖励、状态、提示、异常和页面表现默认写入实际生效的功能节点，不因其需要单独交付而独立成章。
- 读者应能在同一个功能章节内还原该功能如何开始、如何推进、如何结束；不能为了分类整齐，让读者跨越权限、配置、反馈或异常章节拼接完整过程。
- 只有同时约束多个独立功能且无法归入单一功能的规则，才可以形成共用规则章节，并明确约束对象。
- 规则、边界、异常处理写在对应功能点下。
- 内部证据链必须满足“设计目的 -> 手段框架 -> 设计对象 -> 交付对象 -> 结构依据 -> 独立功能 -> 规则 / UE 反馈”，但正文只呈现需求目的、功能结构和设计结论，不呈现推演过程。
- 正文表达形态必须贴合内容本身，可以使用段落、流程步骤、规则列表、表格、公式、示例或配置说明。
- 表达形态由内容中的核心关系决定。简单单向过程可以使用有序步骤；当段落或步骤无法清楚表达条件分支、状态往返、多角色交接或系统调用关系时，必须使用流程图或状态图明确节点连接。核心关系是静态属性、角色差异、权限对应、配置项或结果对照时，才使用表格。
- 表格可以补充流程节点的参与者、条件和规则，但不能成为过程关系的唯一表达；写完后必须能直接看出由什么触发、经过哪些节点、条件如何改变路径、最终进入什么结果或状态。
- 正文只保留玩家行为、系统判断、状态变化、结果反馈和待确认 / 待补内容，不写内部判断话术。
- 已确认的设计结论写回实际生效的功能节点；“方向是否通过、框架是否成立、规则是否落入正文、当前能否交付”等流程状态只能留在 checkpoint 或独立审核报告中。
- “本节作用、适用对象、规则说明、判断方式、结果变化、玩家表现、关联配置”等是内部检查项，不得机械写成每个主体章节的固定小标题。
- 配置、奖励、状态枚举、UE 页面、打点和公式只能在对应生效节点中表达，不得反向决定章节结构。
- 统计、接入、归属、互斥、计分、展示、配置、结算等交付对象只能进入需求概述或主体设计，不得写成需求目的。
- 目的说明、体验强度、风险高低、收益感知、协作氛围和策略卖点只能作为对应规则的补充说明或验收关注点，不得反向决定章节结构。
- 只有承担已确认手段框架转化关系的内容才能进入主体结构；不承担转化关系的内容只能挂靠到对应规则节点并说明配套职责。
- 正文必须让开发、UE、数值或测试看出本节要实现、配置、展示、结算或验证什么。
- 正文只写设计层的功能行为、系统判断、状态变化和玩家反馈；接口字段、数据结构、日志、埋点、并发、存储、重试和监控等技术实现不进入 GDD。
- 涉及其他系统时，只写功能级边界：由谁承接、传入什么功能意图或数据类别、期望什么结果、不可用时功能如何处理。

## 禁止事项

- 禁止写“问题、思路、分析链”作为正式正文。
- 禁止在写作阶段新增核心设计。
- 禁止把交付对象、系统口径、页面、统计、计分、配置、展示或结算写成需求目的。
- 禁止把不承担转化关系的配套内容写成玩法本体。
- 禁止把不确定内容写成确定规则。
- 禁止用营销描述替代系统规则。
- 禁止为了格式完整而补造内容。
- 禁止机械套用内部检查项，导致正文与既有 GDD 表达割裂。
- 禁止把 G3 的设计推演词或 G4 的抽象结构判断直接写成正文标题。
- 禁止把 G4 的内部判断话术、流程标签或工作口径写入正文。
- 禁止用“本文 / 本章 / 本节只写、仅写、不写、不展开、不扩展”等写作说明代替设计边界。
- 禁止用“外壳、其他照旧、相关内容不涉及”等无法确认影响对象和验收结果的模糊范围表述。
- 禁止把过程关系拆成互不连接的角色、条件或规则字段，导致先后、分支、状态变化或交接关系丢失。
- 禁止把主策裁决、阶段验收、通过依据、打回记录或正式审核结论作为 GDD 章节、附录或正文总结。
- 禁止把权限、条件、次数、冷却、消耗、配置、反馈或异常写成与所属功能并列的主体章节。
- 禁止把一个功能的触发、过程、结果和反馈拆散到多个交付维度章节中。
- 禁止写入接口字段、数据结构、日志、埋点、并发、存储、重试或监控等技术实现。
