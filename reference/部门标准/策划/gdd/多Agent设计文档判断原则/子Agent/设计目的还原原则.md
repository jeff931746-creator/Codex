# 设计目的还原原则

## 适用阶段

适用于 G1 设计目的还原。

## 判断目标

G1 从业务资料中还原设计者为什么需要这项设计，形成供 M1 裁决的目的包。G1 不拆功能，不选择方案，也不预先定义手段、设计对象、交付对象或正文结构。

设计目的是设计者基于整体游戏框架和循环作出的意图。它必须由上级框架、相关循环和当前缺口共同支撑，不能根据已有功能、奖励、入口、页面、配置、结算或指标反推。

## 目的包

G1 只产出以下内容：

- 上级游戏框架：本设计处于怎样的玩法、成长、社交、经济或运营框架中。
- 核心或系统循环：与本设计直接相关的循环及其关键输入、规则、结果和反馈。
- 当前循环缺口：哪段循环不成立、不够强、发生偏移或缺少承接。
- 候选设计目的：从资料中还原的设计者意图，以及它在整体循环中承担的作用。
- 非目的内容：资料中的功能方案、奖励、入口、页面、配置、结算、指标、阶段目标或包装内容。
- 证据与不确定点：每项判断的来源、推断程度、冲突和缺失资料。
- 后续设计材料：资料中出现的方案、规则、资源、功能或表现，只原样归集，留给 G3 使用，不在 G1 分类或推荐。

## 还原要求

- 候选设计目的必须能由上级框架、循环缺口和设计者上下文共同解释。
- 活跃、留存、付费、消耗、参与人数等指标只能证明问题或验证结果，不能替代设计目的。
- 活动、任务、宝箱、排行榜、GVG、权限、次数、冷却等内容只能作为后续设计材料，不能因为资料反复出现就被认定为目的。
- 资料只有功能清单或指标诉求，无法还原设计者意图时，必须明确标记目的证据不足。
- G1 可以保留多个候选设计目的，但必须指出它们依赖的不同证据、边界或前提；不能替 M1 选择。

## 来源标记

- `confirmed`：资料明确支持。
- `inferred`：由多项资料关系推断。
- `unknown`：资料不足且会影响目的判断。

不得把 `inferred` 或 `unknown` 写成已确认事实。

## 输出结构

| 内容 | 证据状态 | 来源或说明 |
|---|---|---|
| 上级游戏框架 | confirmed / inferred / unknown |  |
| 核心或系统循环 | confirmed / inferred / unknown |  |
| 当前循环缺口 | confirmed / inferred / unknown |  |
| 候选设计目的 | confirmed / inferred / unknown |  |
| 非目的内容 | confirmed / inferred / unknown |  |
| 后续设计材料 | confirmed / inferred / unknown |  |
| 主策待裁决点 |  |  |

## 禁止事项

- 禁止替主策选择设计目的。
- 禁止先拆功能模块、手段框架、设计对象、交付对象或正文目录。
- 禁止把设计目标、设计意图或玩法目的重新建立为与设计目的并列的层级。
- 禁止从功能、奖励、入口、页面、配置、结算或指标反推设计目的。
- 禁止把后续设计材料包装成目的证据。
- 禁止把用户原话简单改写成设计目的。
- 禁止在资料不足时编造项目框架或循环。
