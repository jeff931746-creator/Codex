# 独立审核原则

## 适用节点

适用于正式 `gdd-review`，也可用于 Self-Review 或过程自检。正式通过必须由未参与当前版本写作、文本优化或阻塞项修复的审核者作出。

## 判断目标

独立审核判断最终 GDD 是否忠实承接各协作节点已经确认的设计结论，正文是否围绕实际功能组织，以及是否达到可交付状态。

审核只给出通过或 blocking issue，不修改文档，不在审核阶段补设计。

## 读取依据

- `多Agent设计文档工作流.md`，用于确认阶段职责和证据链。
- M1、M2、M3、M4、G6 对应判断原则，按审核问题读取对应节点原则。
- `写作原则.md`，用于审核正文组织和表达。
- `GDD输出模板.md`，只用于确认正文占位完整，没有检查项污染。
- 目标项目已有补充原则；补充原则不能覆盖部门协作原则。

## 判断顺序

### 1. 协作证据

- M1 是否锁定设计目的、循环依据、当前缺口、非目的内容和边界。
- M2 是否确认服务该目的的手段框架。
- M3 是否确认独立功能及规则归属。
- M4 是否确认正文忠实表达已确认设计。
- G6 是否形成与正文分离的交付验收记录。

缺少 M1 目的锁定证据或关键主策确认时，正式 GDD 不得通过。

### 2. 目的与手段承接

- 需求目的是否忠实表达 M1 锁定目的，没有从功能、奖励、入口、页面、配置、结算或指标反推。
- 正文是否能看出已确认手段如何把输入、行为或状态转成结果。
- 正文是否新增未经确认的目的、手段、结构或核心规则。

### 3. 功能聚焦

- 主体章节是否对应 M3 已确认的独立功能。
- 每个主体功能是否具有独立触发或成立条件、处理或判断过程、结果或状态变化。
- 一个功能的触发、过程、分支、结果和反馈是否保持在同一功能章节内。
- 权限、条件、次数、冷却、消耗、配置、奖励、状态、提示、异常和页面表现是否归入实际生效的功能节点。
- 共用规则是否确实同时约束多个独立功能，并明确约束对象。

按交付维度拆散功能过程，或把附属规则误作独立功能，属于 blocking issue。

### 4. 关系与表达

- 过程关系是否保留先后、分支、状态变化和角色交接。
- 静态对应关系是否清楚表达属性、权限、配置或结果之间的映射。
- 表格是否只承载静态关系，没有替代功能流程或状态变化。
- 需要依靠图形才能清楚理解的关键过程、状态或结构，是否使用了对应图形表达。

### 5. 功能完整性

- 每个核心功能是否能从触发或成立条件读到处理、判断、状态变化、结果反馈和必要异常。
- 状态是否说明进入、可执行行为、退出和玩家可见反馈。
- 配置、奖励、结算、资格和领取规则是否归入实际生效的功能节点，并足以支持实现与测试。
- 涉及其他系统时，是否说明由谁承接、传入什么功能意图或数据类别、期望什么结果、不可用时功能如何处理。

### 6. 正文边界

- 正文是否只写设计层的功能行为、系统判断、状态变化和玩家反馈。
- 是否混入接口字段、数据结构、日志、埋点、并发、存储、重试、监控等技术实现。
- 是否混入主策裁决、阶段状态、验收依据、打回记录或审核结论。
- 是否使用写作说明代替明确的系统边界。

技术实现或流程产物进入正文，属于 blocking issue。

## 通过条件

- 协作证据完整，目的、手段、独立功能和正文之间能够对应。
- 正文围绕功能运行过程组织，附属规则全部归位。
- 关键关系表达正确，核心功能完整且可执行、可验证。
- 正文没有新增设计、技术实现或流程产物。

任一适用项存在 blocking issue 时，不得正式通过。

## 输出要求

审核报告独立于 GDD，至少包含：审核类型、结论、blocking issue 位置、问题所属阶段和打回目标。

Self-Review 或过程自检不能输出“正式通过”；缺少独立审核者时，只能标记“已完成自检，未完成正式独立验收”。

## 禁止事项

- 禁止在审核阶段修改正文或补写设计。
- 禁止用个人偏好替代节点判断原则。
- 禁止只检查“有没有”，不判断功能是否成立、关系是否完整。
- 禁止把审核报告写回 GDD 正文。
- 禁止由当前版本生产者作出唯一正式通过结论。
