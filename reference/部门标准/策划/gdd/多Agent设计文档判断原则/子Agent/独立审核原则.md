# 独立审核原则

## 适用节点

适用于正式 `gdd-review`、Self-Review 或过程检查。审核者只报告问题、证据、风险与建议，不拥有正式通过、打回、风险接受或交付决定权。

## 判断目标

独立审核检查最终 GDD 是否忠实承接 U1-U4 用户确认的设计结论，正文是否围绕实际功能组织，以及有哪些交付风险。审核不修改文档，不补设计。

## 读取依据

- `策划决策权规则.md`。
- `多Agent设计文档工作流.md`。
- U1-U4、G6 记录和对应节点原则。
- `写作原则.md`。
- `GDD输出模板.md`，只确认正文占位结构。

## 检查顺序

### 1. 用户确认与协作证据

- U1 是否由用户确认设计目的、循环依据、当前缺口和边界。
- U2 是否由用户选择手段框架、对象和结构依据。
- U3 是否由用户确认功能、规则、状态和 UE 方向。
- U4 是否由用户确认当前正文版本。
- G6 是否形成与正文分离的交付状态检查记录。

### 2. 目的与手段承接

- 需求目的是否忠实表达 U1 结论。
- 正文是否承接 U2 确认的手段与结构。
- 正文是否新增未经用户确认的目的、手段、结构或核心规则。

### 3. 功能聚焦与完整性

- 主体章节是否对应 U3 确认的独立功能。
- 每个功能是否具有触发或成立条件、处理过程、状态变化和结果反馈。
- 权限、条件、次数、冷却、消耗、配置、奖励、状态、提示、异常和页面表现是否归入实际生效功能。
- 一个功能的过程是否被交付维度拆散。

### 4. 关系与表达

- 过程关系是否保留先后、分支、状态变化和角色交接。
- 静态对应关系是否清楚。
- 表格是否没有替代流程或状态变化。
- 正文是否存在重复展开、内部判断语言、流程产物或模板污染。

### 5. 正文边界

- 是否只写设计层功能行为、系统判断、状态变化和玩家反馈。
- 是否混入接口字段、数据结构、日志、埋点、并发、存储、重试或监控。
- 是否混入用户确认记录、阶段状态、检查依据或审核结论。

## 输出要求

每个问题至少包含：位置、证据、违反原则、影响、建议处理阶段和可选动作。报告最后给出 Agent 推荐，但必须明确写“审核结论不具有交付决定效力，等待用户 U5 决定”。

未发现问题时写“未发现问题”，不能写“正式通过”。存在问题时写“存在问题”，不能自行写“打回”。

## 禁止事项

- 禁止修改正文或补写设计。
- 禁止用个人偏好替代节点原则。
- 禁止把审核报告写回 GDD。
- 禁止由任何 Agent 作出唯一或最终通过结论。
- 禁止自行选择返回阶段、接受风险、停止方向或批准交付。
