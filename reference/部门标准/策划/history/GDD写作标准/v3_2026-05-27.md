# GDD 写作标准

适用范围：系统设计文档、玩法设计文档、战斗设计文档及同类功能设计规格产出物。

---

## 核心写作视角

**策划工具集视角**，不是实现结果视角。

每一份系统设计文档的读者是策划。策划拿到文档后应该能回答四个问题：

1. **我有什么工具**：系统暴露了哪些可配置的功能模块
2. **工具的规则是什么**：各模块如何运作，约束如何生效，冲突如何处理
3. **怎么拼装**：这些模块如何组合，组合决策的依据是什么
4. **能实现什么体验**：不同的拼装方式对应什么玩家体验目标

文档描述的是"策划侧的操作界面 + 操作规则"，不是"系统的内部实现"。

**禁止用实现结果视角写文档**：
- ❌ "系统会生成 X 个房间，按 Y 逻辑排列"
- ✅ "策划通过配置 [房间池] 和 [约束规则] 决定地牢结构；当约束冲突时按优先级 A > B > C 处理"

---

## 写作框架（四层）

每个系统文档必须包含以下四层，顺序不可颠倒：

---

### 第一层：体验目标

**格式固定**：
> "玩家在 [场景] 应感受到 [具体情绪/认知状态]，因为 [设计理由]"

约束：
- "有趣""好玩""爽"不是合法答案，必须命名具体的情绪或认知状态
- 两个人读完后能判断某个工具配置是否满足了这句话
- 写不出这句话 → 停下来澄清需求，不许继续

每个系统可以有多个体验目标，但每个目标必须独立成句。

---

### 第二层：工具集定义

列出策划可操作的所有功能模块，每个模块说明：

| 字段 | 要求 |
|---|---|
| **模块名** | 策划能识别的名称 |
| **能配置什么** | 具体可调的参数或开关 |
| **影响什么体验** | 调整这个模块会改变哪个体验目标 |
| **硬约束** | 系统必须满足的边界条件，格式：必须 / 禁止 / 当...则... |
| **参考值（非约束）** | 推荐范围、建议值，不由系统强制，策划自行判断 |

**硬约束与参考值的区别**：
- 硬约束：违反时系统拒绝配置或自动纠正，无例外
- 参考值：可突破，突破时策划自行承担体验后果

**删除测试**：对每个模块问：
> "删掉这个模块，第一层的体验目标还能实现吗？"
- 不能实现 → 保留
- 能实现 → 删除，不许保留

每个体验目标对应的模块不超过 3 个。超过 3 个时，必须说明为什么删不掉。

---

### 第三层：规则层

对整个工具集定义系统的操作规则。第二层说"有哪些旋钮"，第三层说"旋钮转动后发生什么"。

规则层必须覆盖三类内容：

#### a) 操作规则

每条规则格式：
> "当 [触发条件] 时，系统必须/禁止 [行为]"

操作规则覆盖：
- 各模块的配置如何转化为系统输出（关键逻辑，不是算法步骤）
- 模块之间的联动关系（A 模块的配置如何影响 B 模块的行为）

#### b) 约束优先级

当多个硬约束同时触发时，按以下顺序处理（序号越小优先级越高）：

> 第 1 优先级 > 第 2 优先级 > ...

若各约束不存在冲突场景，明确声明"各约束独立生效，无优先级冲突"。

#### c) 边界行为

配置违反硬约束时，系统如何响应：

| 违反的约束 | 系统响应 | 兜底行为 |
|---|---|---|
| [约束名] | 报错 / 回退默认值 / 强制修正 | [具体处理方式] |

**规则层删除测试**：对每条规则问"删掉这条规则，系统行为是否还有明确定义？"——无法定义则保留。

---

### 第四层：拼装示例

给出至少 2 个体验目标的拼装配置，每个示例必须包含决策理由：

```
体验目标：[复制第一层的句子]
决策理由：[为什么选这套模块组合和配置值，而不选其他]
工具配置：
  · [模块A]：[配置值]
  · [模块B]：[配置值]
预期效果：[玩家会感受到什么，对应第一层]
```

拼装示例不是参考案例，是策划实际操作的决策模板。决策理由说明"为什么这样配"，是示例的核心价值，不可省略。

---

## 文档输出结构

每个系统文档分三个区：

**必须锁定**
- 体验目标句（第一层）
- 工具集定义（第二层，含删除测试结论）
- 规则层（第三层：操作规则、优先级、边界行为）
- 所有硬约束

**开发自决**
- 满足必须锁定约束条件下，内部实现方式开发自行决定
- 只列约束，不给方案
- 算法步骤、具体数据结构、渲染方案均属于开发自决区

**待定**
- 需要数据或测试才能定的内容
- 明确标注"待定，原因：[X]"，不许用猜测填充

---

## 禁止行为

- 没有体验目标就开始写工具集
- 用"通常""常见做法""同类游戏都有"作为保留某个模块的理由
- 在"必须锁定"区写实现细节（算法步骤、像素尺寸、具体动画）
- 在硬约束字段写"建议""推荐""通常"等非强制表述（建议值应进参考值字段）
- 缺少规则层，或规则层只重复工具集定义的约束而不说明系统行为
- 只写一个拼装示例（至少 2 个，否则看不出模块的组合弹性）
- 拼装示例缺少决策理由（只给配置值不说明为什么这样配）
- 用推测填充"待定"区

```
写作视角：策划拿到这份文档后，能知道"我有什么工具、工具的规则是什么、怎么拼装、能实现什么体验"。

## 强制推导链（四步，不可跳过）

### Step 1 — 体验目标
写出所有体验目标句，格式固定：
"玩家在[场景]应感受到[具体情绪/认知状态]，因为[设计理由]"

约束：
- "有趣""好玩""爽"不是合法答案
- 这句话必须具体到：两个人读完后能判断某个工具配置是否满足了它
- 写不出这句话 → 停下来，向用户澄清需求，不许继续

### Step 2 — 工具集定义
列出满足 Step 1 的最小工具集合。

对每个模块：
- 说明能配置什么 / 影响什么体验
- 硬约束字段只写"必须/禁止/当...则..."格式的强制条件
- 建议范围和推荐值写入参考值字段，不写入硬约束
- 做删除测试：删掉这个模块，体验目标还能实现吗？

### Step 3 — 规则层
对整个工具集定义三类规则：

a) 操作规则：当[条件]时，系统必须/禁止[行为]
   - 覆盖各模块配置如何转化为输出
   - 覆盖模块间联动关系

b) 约束优先级：当多个硬约束同时触发时的处理顺序
   - 列出：第1优先级 > 第2优先级 > ...
   - 若无冲突场景，明确声明

c) 边界行为：配置违反硬约束时系统如何响应
   - 格式：违反[约束名] → 系统响应 → 兜底行为

### Step 4 — 拼装示例
给出至少 2 个体验目标的拼装配置，格式：
体验目标：[Step 1 的句子]
决策理由：[为什么选这套配置而不选其他]
工具配置：· [模块]：[配置值]
预期效果：[对应 Step 1 的具体描述]
```

## 审核 Prompt 模板

```
请先读取以下文件：
1. reference/部门标准/策划/current/GDD写作标准.md（审核标准）
2. [目标文档路径]（被审核文档）

按照 GDD写作标准.md 中的 Self-Review 评审判据，逐系统核查以下四项：

**判据一：体验目标存在**
每个系统是否有明确的体验目标句（"玩家在[场景]应感受到[情绪/认知状态]，因为[设计理由]"）？
情绪/认知状态是否具体可判断（非"有趣""好玩"等模糊表述）？

**判据二：工具集完整且通过删除测试**
文档是否定义了策划可操作的功能模块？
每个模块是否说明了：能配置什么 / 影响什么体验 / 硬约束 / 参考值？
硬约束字段是否混入了"建议""推荐"等非强制表述？
每个模块是否通过了删除测试？

**判据三：规则层完整**
是否有操作规则说明各模块配置如何转化为系统行为？
是否有约束优先级（或声明无冲突）？
是否有边界行为定义（配置非法时系统如何响应）？

**判据四：拼装示例存在且可操作**
是否有至少 2 个体验目标的拼装配置？
每个示例是否包含决策理由？
"必须锁定"区是否混入了实现细节（算法步骤、像素尺寸、具体动画）？

输出格式：
- 每个系统单独一节
- 四项判据逐条给出：通过 / blocking issue
- blocking issue 必须标注具体位置和问题描述
- 最后给出总结：可通过 / 需打回修改（列出所有 blocking issue 清单）
```

## Self-Review 评审判据

| 判据 | 通过标准 | 不通过标准 |
|---|---|---|
| 体验目标存在 | 每个系统有明确的 Step 1 句式，情绪/认知状态具体可判断 | 缺失、或只写技术指标、或只写"有趣""好玩" |
| 工具集完整且通过删除测试 | 每个模块定义了可配置项 + 体验影响 + 硬约束 + 参考值，且通过删除测试；硬约束字段无"建议""推荐" | 只描述实现结果、缺少可操作配置、硬约束混入软建议、存在无体验来源的模块 |
| 规则层完整 | 有操作规则（当...时系统...）；有约束优先级或声明无冲突；有边界行为定义 | 缺少规则层；只重复约束而不说明系统行为；配置非法时无响应定义 |
| 拼装示例存在且可操作 | 至少 2 个体验目标的拼装配置，含决策理由，策划可直接操作 | 缺少示例、示例无决策理由、必须锁定区混入实现细节 |

四项均通过 → self-review 完成，可进入 delivery。
任意一项有 blocking issue → 打回 edit gate，不可进入 delivery。
