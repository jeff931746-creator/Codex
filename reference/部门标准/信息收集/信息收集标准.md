# 信息收集标准

适用范围：所有从外部来源（文章、报告、演讲、数据平台）摄入信息并结构化归档的库。

当前适用库：
- `archive/资料/战略库/` — 文章级，市场情报
- `archive/资料/竞品库/` — 产品级，新品监控

本标准定义两条线共用的通用部分。文章级和产品级的差异由各库 SCHEMA 定义。

---

## 一、通用必填字段

所有信息收集条目（不论文章级还是产品级）必须包含以下 YAML 字段。各库 SCHEMA 可增加领域字段，但不可删减通用字段。

```yaml
---
# === 身份 ===
entry_id: ""           # 格式由各库 SCHEMA 定义，全局唯一
title: ""              # 原文标题（文章级）或产品名称（产品级）
date: ""               # 发布日期，YYYY-MM-DD；无法确认写 "未知"
source_name: ""        # 信息来源（媒体名/平台名）
url: ""                # 原文 URL

# === 质量评估 ===
source_credibility: "" # 见枚举 §三
bias_note: ""          # 明显偏向时注明，无偏向留空

# === 用户反馈（入库后按需填写）===
user_rating: null      # 5=极有用 4=有用 3=一般 2=不值得收 1=误收
user_note: ""          # 批注

# === 元数据 ===
collected_date: ""     # 收集日期，YYYY-MM-DD
---
```

`content_type`、`core_thesis`、`actionable_insights`、`source_author` 等字段移至战略库 SCHEMA（文章级专属），不在通用层强制。产品级条目不需要这些字段。

## 二、内容类型枚举（content_type）

| 值 | 含义 | 判定线索 |
|---|---|---|
| 数据报告 | 以数据为主体的报告、白皮书 | 有原始数据表格、图表、统计口径 |
| 行业分析 | 基于数据或案例的行业趋势分析 | 有论点 + 论据，不只是数据罗列 |
| 演讲实录 | 会议、峰会的演讲内容整理 | 有明确演讲者、场合 |
| 方法论 | 提出可复用框架或方法 | 有明确的步骤、原则、适用条件 |
| 产品软文 | 以推广产品/服务为目的的内容 | 内容导向某个产品，信息选择性呈现 |
| 案例复盘 | 对具体项目/产品的复盘总结 | 有明确的项目、时间线、结果 |
| 政策公告 | 平台政策、行业法规变化 | 官方发布，有明确生效时间/范围 |
| 观点评论 | 以个人观点为主，论据较少 | 主观判断多，缺少系统性论证 |

各库 SCHEMA 可新增枚举值，但不可修改通用枚举的定义。

---

## 三、来源可信度（source_credibility）

评估的是**信息来源的可靠程度**，不是文章写得好不好。

| 值 | 含义 | 典型来源 |
|---|---|---|
| 高 | 一手数据或官方渠道 | 平台官方报告、开发者大会演讲、上市公司财报 |
| 中 | 可信行业媒体或有据分析 | GameLook、36kr、行业分析师报告，有数据支撑的分析 |
| 低 | 二手转述、无数据支撑、或明显商业推广 | 软文、无来源的"据了解"、纯观点无论据 |

### 与 llm-fact-checking 规则的关系

本标准的信息来源等级与 `.claude/rules/llm-fact-checking.md` 的标注规范对齐：

| 本标准 | llm-fact-checking 对应 |
|---|---|
| 高（一手/官方） | "搜索：{URL}" 或 "用户提供" |
| 中（行业媒体/有据分析） | "搜索：{URL}" |
| 低（二手/推广） | 需额外标注；事实性陈述不可仅依赖此类来源 |

**硬规则**：来源可信度为"低"的条目，其中的事实性陈述不可直接用于决策，必须通过其他来源交叉验证后才可引用。

## 四、通用质量判据

所有条目（不论哪条线）归档前必须通过以下检查。

| # | 判据 | 通过标准 | 不通过标准 |
|---|---|---|---|
| 1 | 通用必填字段完整 | entry_id / title / date / source_name / url / source_credibility / collected_date 全部有值 | 任何通用字段缺失 |
| 2 | 来源可信度有评估 | `source_credibility` 有值且判定理由可追溯 | 未评估 |
| 3 | 偏向性标注 | 有明显偏向时 `bias_note` 已标注 | 明显有偏向但未标注 |

各库 SCHEMA 在此基础上叠加专项判据（文章级的事实/观点区分、论点准确性等；产品级的字段完整性等）。

## 五、通用处理流水线

### 入口：分流

所有文章进入后，第一步是分流，决定走哪条处理路径。

```
文章进入（来源 + 标题 + 摘要）
  ↓
提到具体游戏产品？（产品名、上线、首发、榜单排名...）
  ├── 是 → 产品级路径：提取每个产品 → 竞品库（全入库）
  │         同时：文章本身有行业分析价值？
  │           ├── 有 → 也走文章级路径
  │           └── 没有 → 仅入竞品库
  │
  └── 否（纯行业/市场/买量分析）→ 文章级路径 → 战略库
```

### 文章级路径（战略库）

```
1. 读取全文
2. 提取元数据（标题、日期、来源、作者）
3. 判断内容类型（content_type）
4. value_score 快速评分（基于标题+摘要）
   → ≤2：不入库，记过滤日志
   → ≥3：继续
5. 提取核心论点和关键信息
6. 评估来源可信度和偏向性
7. 提取可行动洞察
8. 分类、打标签
9. 校验：通用判据 + 战略库专项判据
10. 写入条目 → 更新索引
```

### 产品级路径（竞品库）

```
1. 读取全文
2. 识别文中提到的所有产品/游戏
3. 对每个产品：
   a. 查竞品库是否已有该产品 → 有则更新，无则新建
   b. 提取产品信息（名称、平台、品类、玩法、数据...）
   c. 标注信息来源和可信度
4. 校验：通用判据 + 竞品库专项判据
5. 写入/更新产品条目
```

**产品级路径不做 value_score 筛选，所有新产品全入库。**

## 六、文章级筛选规则（仅战略库适用）

**本节只适用于文章级路径（战略库）。产品级路径（竞品库）不做 value_score 筛选，新产品全入库。**

### 价值评分（value_score）

文章级条目在读取全文前，基于标题+摘要快速评 1-5 分：

| 分数 | 含义 | 处理方式 |
|---|---|---|
| 5 | 重大：一手数据/重大政策/独家信息 | 入库，完整处理 |
| 4 | 高价值：有数据支撑的分析/可行动的趋势洞察 | 入库，完整处理 |
| 3 | 中等：有参考价值/已知信息的新角度 | 入库，简要处理 |
| 2 | 低价值：旧闻重复/无数据的观点 | **不入库**，记过滤日志 |
| 1 | 噪音：纯推广/无关内容 | **不入库** |

### 过滤日志

被过滤的文章记录到 `{库}/过滤日志.md`：
```
- [日期] [来源] 标题 | 过滤原因（重复/低分/不匹配关键词）
```

每周查看，发现误过滤时调整规则。

## 七、用户反馈与质量闭环

入库不是终点。用户使用条目时的反馈是改进系统的唯一真信号。

### 条目反馈字段

每条入库条目的 YAML 增加以下可选字段（用户按需标注）：

```yaml
# === 用户反馈（入库后按需填写）===
user_rating: null        # 用户评分：5=极有用 4=有用 3=一般 2=不值得收 1=误收
user_note: ""            # 用户批注：摘要哪里不准、遗漏了什么、实际用途
```

### 反馈驱动的迭代规则

| 反馈信号 | 系统响应 |
|---|---|
| 某来源连续 5 条 `user_rating ≤ 2` | 触发来源降级评估（T1→T2 或 T2→T3） |
| 某来源连续 5 条 `user_rating ≥ 4` | 触发来源升级评估（T2→T1 或 T3→T2） |
| `user_note` 标注"摘要不准" | 回溯检查提取逻辑，修正 Skill 的处理规则 |
| `user_note` 标注"分类错误" | 检查分流关键词表是否需要调整 |
| 过滤日志中被标记"不该过滤" | 调整 value_score 评分规则或来源层级 |

### 周度质量复盘

每周自动生成质量报告（作为周报的一部分）：

```
本周入库：X 条 | 过滤：Y 条 | 过滤率：Z%
按来源统计：
  GameLook: 入库 12 / 过滤 3 / 用户评分均值 4.2
  游戏葡萄: 入库 8 / 过滤 1 / 用户评分均值 3.8
  ...
用户反馈汇总：
  rating ≤ 2 的条目：N 条（列出标题+来源）
  标注"摘要不准"的条目：M 条
待处理：
  来源降级候选：...
  分流规则调整建议：...
```
